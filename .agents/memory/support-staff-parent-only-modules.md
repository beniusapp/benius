---
name: Support Staff parent-only modules
description: Parent-only module grants, registry action grants, and Support Staff actor-attribution boundaries.
---

For Support Staff, Timetable Master (`timetable`), School Calendar (`school-calendar`), Attendance Overview (`attendance`), Exam Controller (`exam-controller`), Complaint Hub (`complaint-hub`), Noticeboard (`noticeboard`), Performance Analytics (`analytics`), Audit Logs (`audit-logs`), Visitor Log (`visitor-log`), ID Card Gen (`id-card-gen`), Assets & Inventory (`assets`), and Faculty Mapping (`faculty-mapping`) remain parent-only grants.

Teacher Registry (`teacher-registry`) and Student Registry (`student-registry`) use parent-plus-action grants: the parent unlocks base/read access, while each mutation requires both that parent and its exact `:add`, `:edit`, or `:delete` child. The permission editor must not auto-grant those actions when a parent is checked. A child without its parent is ineffective and is removed when permissions are saved. Legacy registry `:deactivate` maps to `:delete`; stale `:view`, `:export`, and unknown action children do not authorize registry access or mutations. A legacy parent-only grant remains read-only until a Principal explicitly grants actions.

For Web Teacher Registry, Delete means write the existing `removed_teachers_log` profile/assignment snapshot, then physically delete the Teacher and linked User through the existing storage path. This applies to Principal/Admin and Support Staff with the Teacher Registry parent plus exact Delete action. Let existing foreign-key cascade, SET NULL, or restrictive behavior govern; never delete unrelated rows to force removal. Do not show the hard-deleted row as Inactive or offer Reactivate for it.

Visitor Log and Assets & Inventory can safely identify Support Staff through the existing role-aware `audit_logs` pattern: positive Staff ID, `support_staff` role, action, entity, and authenticated school. For assets, keep `asset_logs.user_id` exclusively for Admin actors because it references Admin users; never write a Staff ID there or attribute Staff changes to a Principal. Record Support Staff asset create/edit/delete actions in `audit_logs` and preserve school-scoped asset operations.

**Why:** The user's latest product decision restores the snapshot-then-hard-delete lifecycle for both Admin and explicitly authorized Support Staff. Registry action grants remain independent, and the existing `audit_logs` table can preserve role-aware actor attribution without putting a Support Staff ID in an Admin-user foreign key.

**How to apply:** Keep the permission editor, dashboard visibility, UI controls, and API authorization aligned. Preserve school and academic-session checks; canonicalize legacy grants without converting registry parent grants into mutation grants. For Teacher Delete, verify the authenticated actor's own password, enforce same-school ownership, write the snapshot, then call the existing hard-delete method without bypassing foreign keys; write role-aware audit attribution using the positive Staff ID where supported. Leave separate deactivate/reactivate APIs intact if other features use them. Student Delete remains soft deactivation. The shared paginated Student roster may be read by either the exact `student-registry` or `id-card-gen` parent grant; child grants alone do not authorize it. Keep the `asset_logs` foreign-key path unchanged for Admins and Web as the source of truth before Mobile feature work resumes.
