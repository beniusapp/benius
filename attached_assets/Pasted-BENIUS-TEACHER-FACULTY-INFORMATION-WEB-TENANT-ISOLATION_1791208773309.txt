PROBLEM IDENTIFIED

The previous Teacher Web ↔ Mobile parity audit found a potential HIGH-severity tenant-isolation problem in:

Teacher Portal → Faculty Information

The audit reported that the Web Faculty Information frontend calls an API similar to:

"/api/faculty/:schoolId"

and that the backend authenticates the request but may not verify that the requested "schoolId" actually belongs to the authenticated Teacher.

If confirmed, this could potentially allow:

Teacher from School A
→ manually request School B schoolId
→ receive School B Faculty Information.

This must NEVER be possible in BENIUS.

---

PERMANENT BENIUS TENANT RULE

BENIUS is a multi-tenant application.

A Teacher authenticated under:

School A

may access Faculty Information only for:

School A

They must NEVER be able to access:

School B faculty data

even if they manually modify:

- URL
- path parameter
- API request
- browser developer tools
- frontend state
- request payload
- query parameter

Frontend controls alone are NOT sufficient.

The backend must enforce tenant isolation.

STEP 2 — REQUIRED SECURITY BEHAVIOR

If the vulnerability is confirmed, correct it with the smallest safe backend change.

The backend must derive/trust the Teacher's school from the authenticated server-side Teacher identity.

Conceptually:

Authenticated Teacher
→ resolve actual Teacher record
→ obtain trusted "teacher.schoolId"
→ authorize Faculty Information only for that school.

Never trust a client-supplied school ID as authorization.

---

PATH PARAMETER

If the existing endpoint remains:

"/api/faculty/:schoolId"

then the backend must verify:

"requestedSchoolId === authenticatedTeacher.schoolId"

before retrieving faculty data.

If they do not match:

REJECT THE REQUEST.

Do not query the foreign school's faculty first and filter afterward.

---

IMPORTANT

Do NOT silently replace a foreign requested school ID with the Teacher's real school ID.

For example, this is NOT desired:

Teacher School A requests School B
→ backend silently changes it to School A
→ returns School A.

Instead:

Teacher School A requests School B
→ REJECT

This makes unauthorized requests explicit and prevents hidden authorization mistakes.

Use the project's existing appropriate authorization error convention/status.

Do not invent inconsistent error handling if BENIUS already has a standard.

---

AUTHENTICATED IDENTITY

Authorization must be based on trusted server-side authentication/session information.

Do NOT authorize using client-controlled values such as:

- "schoolId" supplied by frontend
- "teacherId" supplied by frontend
- query parameters
- request body identity fields
- localStorage/sessionStorage values

The frontend may send routing/context information, but it must not determine authorization.

---

STORAGE / DATABASE

Faculty query must remain strictly school-scoped.

Conceptually:

Faculty
WHERE school_id = authenticatedTeacher.schoolId

Do not return cross-school records.

If the existing storage function already requires schoolId, pass only the validated/trusted school ID after authorization.

Do NOT redesign the schema.

---

WEB FRONTEND

Do not redesign Faculty Information.

If the Web frontend already sends the logged-in Teacher's schoolId correctly, leave the normal UI behavior unchanged.

This task is primarily about ensuring that manually altering the request cannot bypass tenant isolation.

Only make a Web frontend change if genuinely necessary for correctness.
