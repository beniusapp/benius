STEP 2L-3 — FIX ARCHIVED SELF-ATTENDANCE GET STATUS-HEALING

We are continuing Attendance hardening.

STEP 2L-3A READ-ONLY AUDIT RESULT:
READY FOR IMPLEMENTATION

The audit established the existing authoritative Session writability rule:

A Session is writable only when:

  selected/record-owned Session belongs to authenticated school
  AND
  academic_sessions.isActive === true

Do NOT redesign this rule.

The existing global checkSessionContext() already protects normal HTTP mutation routes.

The confirmed defect is narrower:

GET Teacher self-attendance endpoints can perform persistent status-healing UPDATEs.

This allows an archived Session's Attendance record to be modified merely by being read.

==================================================
THIS STEP'S ONLY OBJECTIVE
==================================================

Prevent archived/inactive Teacher self-attendance records from being persistently modified by GET requests.

Affected routes identified by the audit:

1. GET /api/teacher/self-attendance/today

2. GET /api/teacher/self-attendance/history

Relevant code:
  server/teacher-routes.ts

The paginated history route already demonstrates the safe pattern:
recalculate status for the response without persisting the recalculated status.

==================================================
NON-NEGOTIABLE REQUIREMENTS
==================================================

1. HISTORICAL READS MUST REMAIN AVAILABLE

Archived Sessions must still be readable.

Do NOT return ARCHIVE_READ_ONLY merely because the selected Session is inactive.

The following must continue to work for archived Sessions:

- today/history reads where applicable
- historical self-attendance history
- correction history/read-only information

The fix is ONLY about preventing database mutation during GET.

2. TENANT ISOLATION MUST REMAIN

Continue deriving school from authenticated Teacher/session context.

Never trust browser-supplied schoolId.

Continue requiring the selected Session to belong to the authenticated school.

3. SESSION ISOLATION MUST REMAIN

Continue requiring:

- authenticated teacher
- authenticated school
- validated selected Session
- attendance date/session identity

Legacy NULL-session records must remain excluded from Session-scoped operations.

4. ACTIVE SESSION BEHAVIOR

Preserve existing active-Session status-healing behavior ONLY if the current implementation intentionally relies on persistent healing for the active Session.

Do not remove active-session functionality unnecessarily.

For an active Session:

- existing status recalculation behavior may remain
- existing tenant/session predicates must remain

For an inactive/archived Session:

- status may be recalculated for display
- BUT the recalculated status must NOT be persisted to the database.

5. DO NOT MODIFY NORMAL MUTATION ROUTES

Do NOT change:

- POST /api/attendance
- POST /api/teacher/self-attendance/check-in
- POST /api/teacher/self-attendance/check-out
- POST /api/teacher/self-attendance/correction

The Step 2L-3A audit confirmed those are already protected by global Session mutation middleware.

Do not duplicate that middleware logic into these routes.

6. DO NOT MODIFY DATE RULES

Preserve:

- Student Attendance marking: today through exactly seven calendar days ago
- Teacher self correction: today through exactly seven calendar days ago
- Self check-in/check-out: today only

Do not introduce Session startDate/endDate writability rules.

7. DO NOT TOUCH LEAVE APPROVAL

Do NOT modify:
- Teacher leave approval
- Student leave approval
- leave synchronization

The separate question of whether leave belonging to an archived Session may still be approved will be handled separately.

==================================================
IMPLEMENTATION GUIDANCE
==================================================

First inspect the existing implementation carefully.

For:

GET /api/teacher/self-attendance/today

and:

GET /api/teacher/self-attendance/history

identify the exact UPDATE/status-healing block.

Then implement the smallest change needed so that:

IF selected Session is active:
    preserve existing persistent status-healing behavior
ELSE:
    calculate the correct status for the response
    DO NOT UPDATE the database

Prefer reusing the already existing paginated-history response-only status pattern if appropriate.

Do not create a second status calculation implementation.

Use the existing canonical Attendance policy/status calculation utilities.

If the existing status-healing helper can be safely changed to support a non-persisting/read-only mode, prefer that over duplicating logic.

Do not refactor unrelated code.

==================================================
IMPORTANT READ-ONLY PRINCIPLE
==================================================

A GET request against an archived Session must be observational only.

The request must not:

- UPDATE the Attendance record
- change status
- change checkout/check-in values
- create a record
- delete a record
- alter audit history

It may calculate the status in memory for display.
