

This must be corrected.

# ATOMIC CONSISTENCY

A Student must NEVER be committed as a successful import if the required active-session enrollment for that Student was not successfully created.

The invariant is:

```text
Successful imported Student
        ↓
MUST HAVE
        ↓
matching active-session enrollment
```

If the Student/enrollment operation for a row fails:

```text
Student Profile ❌
Enrollment ❌
```

Do NOT leave:

```text
Student Profile ✅
Enrollment ❌
```

or:

```text
Student Profile ❌
Enrollment ✅
```

Use database transactions appropriately.

---

# IMPORTANT — DO NOT USE ONE MASSIVE TRANSACTION FOR 100,000 STUDENTS

BENIUS is intended to support large installations.

Do NOT solve consistency by putting an entire potentially huge CSV import into one enormous transaction.

That could create:

- long database locks
- excessive memory usage
- huge rollback cost
- timeout risk
- poor concurrency

Instead implement a scalable bounded/chunked approach.

---

# BOUNDED BATCHING

Design the import to process validated rows in reasonable bounded batches/chunks.

Choose a sensible batch size based on the existing stack/database.

Do NOT hard-code architecture around the Development dataset size.

Conceptually:

```text
CSV
 ↓
Validation
 ↓
Batch 1
  Student + Enrollment pairs
 ↓ commit

Batch 2
  Student + Enrollment pairs
 ↓ commit

Batch 3
  ...
```

Within a committed batch, Student/enrollment consistency must be maintained.

If the existing storage architecture makes per-row atomic Student+Enrollment operations safer initially, explain the trade-off and avoid uncontrolled parallelism.

The important requirements are:

- bounded memory
- bounded transaction size
- no half-created Student/enrollment pair
- deterministic error reporting
