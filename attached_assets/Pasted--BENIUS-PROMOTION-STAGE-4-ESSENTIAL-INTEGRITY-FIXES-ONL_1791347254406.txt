# STAGE 4 SCOPE

Implement ONLY these 3 items:

## 1. MAKE PROMOTION EXECUTION IDEMPOTENT

Confirmed problem:

Some Students can be processed again if `/api/admin/promote` is replayed, especially when no source Promotion decision row exists.

This can create duplicate `academic_history` records even though the target enrollment already exists.

### Required behavior

The same logical Promotion execution for the same:

- school
- source Academic Session
- target Academic Session
- Student

must NOT create duplicate Promotion history or duplicate target-placement preparation.

Example:

First request:

Student A
2026–27 Class 5A
→
2027–28 Class 6A

Result:

SUCCESS

If the exact same execution request is replayed:

DO NOT create another `academic_history` row.

DO NOT create another enrollment.

DO NOT modify the Student Registry.

Return a safe already-executed/idempotent result.

### Important

Do not depend only on an existing Teacher Promotion decision having `adminExecuted=true`.

The protection must also work for:

- default Promotion outcomes
- override-only Promotion outcomes
- Students without an existing Teacher Promotion decision row

Preserve transaction atomicity.

Do NOT delete existing historical records.

---

# 2. PROTECT EXECUTED PROMOTION DECISIONS

Confirmed problem:

Some routes can still update/delete Promotion decision rows after Admin Promotion execution.

This can make:

Promotion decision
≠
prepared target enrollment
≠
academic history

### Required behavior

Once a Promotion decision has been executed by Admin:

`adminExecuted = true`

normal Promotion decision mutation must be rejected.

Protect executed decisions against:

- update
- overwrite/upsert
- individual delete
- cohort/bulk delete
- term-level/broad delete
- unlock/clear operations

where those operations affect executed Promotion decisions.

### Important

Enforce this at the backend/storage level wherever practical.

Do not rely only on hiding buttons in the Web UI.

Return a clear conflict/error response when someone attempts to modify an executed decision.

### DO NOT build a reversal system

A controlled Promotion reversal/correction workflow is OUT OF SCOPE.

For Stage 4:

Executed Promotion = locked.

---

# 3. VALIDATE TARGET CLASS + SECTION BEFORE PREPARING ENROLLMENT

Confirmed problem:

The server can currently accept target class/section values from the Promotion request without fully validating that the destination is valid for that school.

Stage 3 may later catch invalid placement, but invalid target enrollment should not be created in the first place.

### Required behavior

Before creating or accepting the target-session Enrollment, backend must verify:

- target Academic Session belongs to authenticated school
- target Academic Session is already valid under existing Promotion rules
- target Class exists/configured for that school
- target Section is valid/configured for that Class/school

If destination placement is invalid:

REJECT THE PROMOTION TRANSACTION.

Do NOT create target enrollment.

Do NOT create academic history.

Do NOT change Promotion execution state.

Do NOT change Student Registry.

Transaction must roll back completely.
