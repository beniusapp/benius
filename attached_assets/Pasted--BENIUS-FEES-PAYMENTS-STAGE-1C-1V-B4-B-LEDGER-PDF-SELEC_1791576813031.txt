## 4. PHASE B — STRICT REQUEST VALIDATION

For:

`POST /api/admin/fees/ledger/pdf`

Define two explicit modes.

### MODE 1 — EXPLICIT SELECTED INVOICES

When `selectAllMatching` is explicitly false or omitted under the existing documented contract:

- `selectedIds` must be an array.
- It must contain at least one ID.
- Every ID must be a valid positive safe integer, consistent with the actual database ID type.
- Reject malformed values.
- Reject zero and negative values.
- Reject duplicate IDs.
- Reject empty arrays.
- Reject missing arrays.
- Reject mixed valid and invalid values.
- Reject unexpected conflicting selection parameters.

Never silently discard invalid IDs.

Never remove the selected-ID predicate because validation produced an empty list.

Never fall back to exporting all matching invoices.

Return a clear HTTP 400 validation response for malformed selections.

### MODE 2 — SELECT ALL MATCHING

When `selectAllMatching` is explicitly true:

- Preserve the existing all-matching export behavior.
- Preserve the existing Class/Section and other fee filters.
- Preserve the existing exclusion mechanism.
- Validate `excludedIds` as an array when provided.
- Reject malformed exclusions.
- Reject invalid, non-positive or duplicate exclusion IDs.
- Reject conflicting explicit selected-ID parameters.
- Do not silently discard invalid exclusions.

The existing legitimate select-all export population must remain unchanged.

### IMPORTANT COMPATIBILITY RULE

Before enforcing the new contract, inspect actual Web callers and tests.

If a legitimate current caller relies on a payload shape that would be broken, STOP and report it instead of silently changing unrelated workflows.

## 5. PHASE C — ALL-OR-NOTHING AUTHORIZATION

For explicit selected invoice IDs:

Validate every requested ID against the authorized export population.

The authorized population must be determined by:

- Authenticated school ID from the server session.
- Validated selected Academic Session.
- Existing fee-record access restrictions.
- Existing Ledger PDF filters.
- Existing historical-placement filter behavior.

Required behavior:

1. All requested IDs authorized: proceed.
2. One unauthorized ID: reject the entire request.
3. Foreign-school ID: reject.
4. Foreign-session ID: reject.
5. Nonexistent ID: reject.
6. ID outside the applied filters: reject.
7. Mixed authorized and unauthorized IDs: reject the entire request.

Do not silently omit unauthorized IDs.

Do not reveal whether an unauthorized ID exists in another school.

Use a generic error response consistent with existing API conventions.

For select-all exclusions, ensure that exclusions cannot alter the authorized population or disclose foreign-school records. Preserve the established select-all semantics, and document how unknown or out-of-scope exclusions are handled.

Avoid N+1 database queries; prefer set-based validation.

Do not alter the underlying financial calculations or report-row projection.
