# EXPECTED USER EXPERIENCE

Example:

Teacher/Admin publishes a new Notice that is visible to Student A.

Student A opens the Student Portal dashboard.

Noticeboard card:

🔴 RED DOT

It must remain cleared until another NEW relevant Notice arrives.

Same principle for Homework and Classwork.

# COMPLAINTS SPECIAL RULE

Complaints are different.

The red dot should NOT appear simply because the Student created/sent their own Complaint.

For Complaints, the red dot should appear only when there is a **new Teacher/Admin-side update relevant to that Student**.

Examples could include, depending on current BENIUS Complaint architecture:

- Teacher reply
- Admin reply
- Teacher/Admin status update
- Teacher/Admin action/message

Audit the actual Complaint model first.

Do NOT invent reply/message concepts if they do not exist.

Determine what existing Complaint events genuinely represent a new Teacher/Admin update visible to the Student.

---

# CORE BUSINESS RULE

The notification state must be:

**PER STUDENT + PER MODULE**

Example:

```text
Student A opens Noticeboard
→ Student A Noticeboard dot clears

Student B has not opened Noticeboard
→ Student B Noticeboard dot remains
```

Never use one global school-wide read flag.

---

# IMPORTANT — CLICK/OPEN BEHAVIOR

When the Student clicks a module that currently has a red dot:

- visually clear the dot immediately
- persist the seen/read state safely
- returning to Dashboard must keep it cleared
- refreshing/relogging must keep it cleared
- another NEW relevant item/update after that must make the dot appear again

This cannot be only temporary React component state.

It needs persistent per-Student state.

# RACE CONDITION / CORRECTNESS

1. Dashboard says Homework has something new.
2. Student clicks Homework.

Do not overengineer, but identify the correct minimal behavior.
