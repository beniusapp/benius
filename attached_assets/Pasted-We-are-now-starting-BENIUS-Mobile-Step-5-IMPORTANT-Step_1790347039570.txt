==================================================
STEP 5 — STUDENT MOBILE DASHBOARD
=================================

Build the first real BENIUS mobile application module:

**Student → Home / Dashboard**

This is an incremental implementation.

DO NOT build the entire Student module.
DO NOT build Student Examination yet.
DO NOT build Teacher or Admin modules yet.
DO NOT redesign the application.

The objective is to establish the first complete end-to-end Student mobile screen using the real BENIUS backend and the existing BENIUS web application's actual responsive/mobile UI as the source of truth.

==================================================

1. ABSOLUTE PRODUCT REQUIREMENTS
   ==================================================

BENIUS is a multi-tenant / multi-school application.

This requirement is permanent.

Every Student API request, database query, calculation, cache entry, navigation decision, Academic Session operation, and displayed record must remain constrained to:

1. authenticated school/tenant
2. authenticated student
3. selected Academic Session where the existing backend functionality is session-sensitive

NEVER trust schoolId, studentId, role, or similar identity values supplied by the mobile client when the server can derive them from the authenticated mobile credential.

NEVER allow a Student from School A to retrieve or display School B data.

NEVER allow one Student to retrieve another Student's private data.

Do not weaken existing authorization.

==================================================
2. EXISTING WEB APPLICATION IS THE UI SOURCE OF TRUTH
=====================================================

This is extremely important.

The existing BENIUS WEB application's actual responsive/mobile appearance is the visual and interaction source of truth.

We are NOT creating a newly designed mobile dashboard.

We are reproducing the existing BENIUS web application's Student experience in native React Native.

Before writing the screen:

1. Locate the existing Student dashboard/home page.
2. Locate the relevant Student routes.
3. Locate all components used by that page.
4. Inspect the responsive/mobile behavior.
5. Inspect:

   * layout
   * navigation
   * header
   * cards
   * buttons
   * icons
   * typography
   * spacing
   * colors
   * labels
   * wording
   * badges
   * loading states
   * empty states
   * error states
   * dialogs/modals if present
   * menus
   * session indicator
   * logout behavior
6. Render the existing web Student dashboard at a mobile viewport and inspect it.
7. Use that actual screen as the reference.

Do NOT invent a new dashboard layout.

Do NOT replace existing cards with arbitrary mobile cards.

Do NOT simplify functionality merely because the target is mobile.

Do NOT use WebView.

Use native React Native components.

Where exact HTML/CSS behavior cannot be reproduced, use the closest native equivalent while preserving the same visual hierarchy and interaction behavior.

Document any unavoidable deviation.

==================================================
3. FIRST AUDIT BEFORE CODING
============================

Before changing code, perform a READ-ONLY audit.

Identify and report:

A. Existing Student web entry route.

B. Existing Student dashboard/home page.

C. All API endpoints called by that page.

D. All React Query hooks used by that page.

E. All shared components used by that page.

F. All Student-specific navigation destinations visible from that page.

G. Which dashboard data is:

* school scoped
* student scoped
* Academic Session scoped
* not session scoped

H. Which data already has a mobile-compatible backend endpoint.

I. Which endpoint, if any, needs a minimal mobile integration wrapper.

J. Existing responsive/mobile appearance.

K. Exact mobile viewport used for the inspection.

Do not modify code during this audit phase.

After the audit, continue with implementation in the same task.

==================================================
4. AUTHENTICATION
=================

Use the Step 3/4 mobile authentication foundation already implemented.

DO NOT create a second authentication system.

Use:

* mobile access credential
* mobile refresh credential
* SecureStore
* AuthContext
* existing mobile /me validation
* existing generation-aware refresh coordinator

Do not store:

* password
* PIN
* sensitive authentication secrets in AsyncStorage

The Student dashboard must only render after the authenticated Student identity has been verified.

Server identity remains authoritative.

==================================================
5. STUDENT IDENTITY
===================

The mobile app must obtain Student identity from the authenticated server principal.

Do NOT allow the dashboard to accept arbitrary:

studentId
schoolId
role
userId

from navigation parameters or ordinary client-controlled state.

If an API requires the Student ID, derive/use it only through the authenticated server context or an already-authorized existing endpoint.

A user must never be able to alter a route parameter and view another Student's dashboard.

==================================================
6. ACADEMIC SESSION
===================

Use the existing Step 4 Academic Session foundation.

The dashboard must use the selected Academic Session when the underlying web functionality is session-sensitive.

Do NOT invent a second session selector.

Do NOT treat Academic Session as authentication.

Keep these concepts separate:

Authentication
Tenant / School
Student identity
Academic Session

If the existing web Student dashboard displays the current Academic Session or depends on it, reproduce that behavior.

If the user changes Academic Session, invalidate/refetch session-sensitive dashboard queries.

Do not display stale data from the previous session.

==================================================
7. API IMPLEMENTATION
=====================

Reuse existing backend endpoints wherever possible.

Do NOT duplicate business logic in the mobile application.

Do NOT calculate academic results, attendance summaries, fees, timetable information, etc. in the mobile client if the web/backend already calculates them.

The backend remains the source of truth.

If an existing endpoint is suitable:

reuse it.

If the existing endpoint needs a minimal mobile wrapper:

create the smallest safe wrapper possible.

Any new mobile endpoint must:

* authenticate the mobile credential
* derive school/tenant from the authenticated principal
* derive Student identity from the authenticated principal
* enforce Academic Session where applicable
* never trust client-supplied school identity
* never expose cross-school data
* never expose another student's data
* use existing domain/business logic where possible

Do not perform unrelated backend hardening.

==================================================
8. TANSTACK QUERY
=================

Use the existing TanStack Query foundation.

Every session-sensitive Student dashboard query must have a cache key that distinguishes at least:

resource
school
student/principal
role
Academic Session

Do not allow School A / Student A / Session A cached data to appear under School B / Student B / Session B.

When Academic Session changes:

* invalidate appropriate session-sensitive queries
* refetch
* avoid stale previous-session dashboard information

Follow the cache-key rules established in Step 4B.

==================================================
9. NATIVE NAVIGATION
====================

Use the existing Expo Router structure.

Reproduce the existing web Student navigation hierarchy.

Do NOT invent a new navigation architecture merely because this is mobile.

The mobile navigation should feel like the existing BENIUS responsive web application.

Only implement navigation destinations required for the Student dashboard in this step.

Do not implement the destination modules yet unless a minimal placeholder is necessary to preserve navigation behavior.

If a destination is not implemented yet, make the behavior explicit and safe rather than pretending the module is complete.

Do not implement another refresh mechanism inside the dashboard.

Mobile is an additional client.

==================

7. Expired access credential is rejected or refreshed through the existing mechanism.

8. Refresh-token reuse protection remains intact.

9. Logout invalidates the mobile session.

10. Academic Session selection cannot select a session belonging to another school.
