Offline Payment — Complete Payment Method Details & Audit Requirements

I want you to review and improve the Record Offline Payment → Ledger & Transactions → Student/Invoice Payment Details flow.

This is specifically for offline payments recorded by the school:

- Cash
- Bank Transfer
- Demand Draft
- Cheque
- UPI / QR

1. Main Requirement

Currently, when I expand a paid invoice in Fees & Payments → Ledger & Transactions, the payment details are too generic.

For example, it currently shows something like:

- Method: DemandDraft
- Reference: Dddd
- Receipt No.: OF44
- Notes: S...

This is NOT enough for a proper school accounting and audit system.

I want the system to preserve every meaningful detail that was captured when the offline payment was recorded.

The payment method must determine which fields are displayed and stored.

Do NOT simply store everything as a generic "reference" or "notes" field.

The data must be structured and method-specific.

---

2. Cash Payment

When the administrator selects:

Offline → Cash

the system should capture the complete cash information.

Required/appropriate fields

- Total Amount
- Cash Received Date
- Cash Received Time
- Cash denomination breakdown
- Total number of notes/coins by denomination
- Calculated denomination total
- Received By / Recorded By
- Cash Counter / Collection Location, if applicable
- Notes
- Receipt Number
- Invoice Number
- Student
- DSID
- Fee Record ID
- Academic Session

Cash denomination example

If the payment is ₹1,600, the administrator should be able to enter something like:

- ₹500 × 2 = ₹1,000
- ₹200 × 2 = ₹400
- ₹100 × 2 = ₹200
- Total = ₹1,600

The system must automatically calculate the denomination total.

It must validate:

Denomination Total = Payment Amount

Do not allow the payment to be finalized if the denomination total does not match the actual payment amount, unless there is an explicitly designed over/short handling mechanism.

The saved payment record must preserve the denomination breakdown permanently.

When viewing the payment later, show the denomination details clearly.

Example:

Cash Breakdown

- ₹500 × 2 = ₹1,000
- ₹200 × 2 = ₹400
- ₹100 × 2 = ₹200
- Total Cash: ₹1,600

14. Database Requirement

Before changing the UI, inspect the current database/schema and determine exactly where offline payment information is currently stored.

Do not create duplicate or conflicting fields unnecessarily.

If the current schema uses generic fields such as:

- method
- reference
- notes

retain them where appropriate for compatibility, but introduce a properly structured representation for method-specific details.

Use a clean structure such as a dedicated offline-payment details object/table rather than putting all information into one JSON/string field if the existing architecture supports normalized fields.

The final architecture must support:

paymentMethod = offline

offlinePaymentMethod =
  cash
  bank_transfer
  demand_draft
  cheque
  upi_qr

Then method-specific data should be stored in structured fields.

Do not break existing online Razorpay payment records.

Online Razorpay payments and offline payments must remain clearly distinguishable.

---

15. Data Integrity

This is extremely important.

The information displayed in Ledger & Transactions must come from the persisted payment record, not from temporary frontend state.

Refreshing the page must not lose anything.

Opening the same invoice later must show the exact same payment information.

The receipt must also use the persisted payment information.

Do not fabricate missing values.

If a field was genuinely not provided, display "Not provided" or "—" rather than inventing a value.

---

16. Payment Receipt

Review the offline payment receipt as well.

The receipt should show the appropriate payment method:

- Offline (Cash)
- Offline (Bank Transfer)
- Offline (Demand Draft)
- Offline (Cheque)
- Offline (UPI / QR)

For method-specific receipts, show the relevant identifying information.

For example:

Demand Draft
DD Number, DD Date, Issuing Bank, etc.

Cheque
Cheque Number, Cheque Date, Bank, etc.

Bank Transfer
UTR / Transaction Reference, Transfer Date, Bank, etc.

UPI / QR
UPI Transaction ID / Reference, Transaction Date, etc.

Cash
Cash received information and denomination breakdown where appropriate.

Do not overload the receipt with irrelevant fields. Show only the fields relevant to that payment method.

17. Attachment / Proof Support

Please inspect whether the existing architecture supports uploading supporting evidence for offline payments.

If appropriate, allow an authorized administrator to attach supporting proof such as:

- Cheque image
- Demand Draft image
- Bank transfer proof
- UPI payment screenshot

The attachment must be associated with the specific payment record, not merely the student.

Do not make this mandatory unless the existing business rules require it.

---

18. Security & Audit

Only authorized administrative users should be able to view or modify sensitive offline-payment information.

Never expose unnecessary bank/account information to students or unauthorized users.

Payment records must remain tenant/school scoped.

A payment belonging to School A must never appear in School B.

---

19. Important: Do Not Break Existing Payment Architecture

Before implementation:

1. Inspect the current offline payment schema.
2. Inspect the Record Offline Payment modal.
3. Inspect the API used to record offline payments.
4. Inspect the Ledger & Transactions payment-details component.
5. Inspect the receipt generation code.
6. Inspect existing tests.
7. Identify exactly what information is currently captured.
8. Identify what information is currently being discarded or only stored generically.

Then implement the improvement.

Do NOT modify the Razorpay online payment verification, webhook, capture, refund, or online payment-history logic unless absolutely necessary for compatibility.

Do NOT change:

- Fee calculation
- Invoice numbering
- Receipt numbering
- Academic-session logic
- Online Razorpay lifecycle
- Existing payment-attempt audit logic

unless a schema compatibility change is genuinely required.

20. Final Goal

The goal is simple:

When an administrator records an offline payment, every important piece of information about that actual transaction must be captured, structured, persisted, auditable, and later visible from the Ledger & Transactions payment details.

I do not want a generic:

«Method: Offline
Reference: XXXXX
Notes: XXXXX»

I want a professional school ERP accounting record where the system can answer:

What payment method was used? Who paid? How much? When? Which bank? Which cheque/DD/UTR/UPI transaction? Which denominations for cash? Who recorded it? Which invoice? Which receipt? When was it deposited/cleared where applicable? What supporting proof exists?

That level of detail is what I want.

First audit the current implementation and provide a concise gap analysis of:

Currently Captured → Currently Stored → Currently Displayed → Missing

Then implement the required changes carefully.

After implementation, run the relevant type checks and tests and report:

- Files changed
- Database/schema changes
- New fields added
- UI changes
- Validation added
- Audit/security considerations
- Tests passed
- Any fields that cannot be captured because the underlying payment method/provider genuinely does not provide them
