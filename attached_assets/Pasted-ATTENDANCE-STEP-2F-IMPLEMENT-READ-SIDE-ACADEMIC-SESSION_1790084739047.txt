ATTENDANCE STEP 2F — IMPLEMENT READ-SIDE ACADEMIC SESSION ISOLATION ONLY

IMPORTANT:
This is a focused implementation step.

Attendance Step 2E is already COMPLETE and PASS.

Current canonical Attendance identity:

    school_id + session_id + student_id + date

Current guarantees:

- attendance_records.session_id is NOT NULL
- UNIQUE(school_id, session_id, student_id, date)
- Attendance -> Academic Session no longer uses ON DELETE SET NULL
- Teacher Attendance writes receive the authenticated school's active Session server-side
- Student Registry remains GLOBAL and session-independent
- Enrollment is NOT an Attendance prerequisite
- Faculty Mapping is NOT an Attendance restriction
- Any authenticated Teacher belonging to the school may mark Attendance
- Attendance remains tenant-specific
- Production must NOT be modified

This step is ONLY for READ-SIDE Academic Session isolation.

==================================================
CORE REQUIREMENT
==================================================

Every Student Attendance, Teacher Attendance, and Admin Attendance READ must be explicitly scoped to:

    authenticated school_id
    + selected/authoritative academic session_id

No Attendance reader may silently read Attendance across multiple Academic Sessions.

A missing or invalid Session must NEVER mean:

    "read all Sessions"

There must be no fallback from:

    selected Session -> all Sessions

For Attendance reads, Session isolation is mandatory.

==================================================
IMPORTANT SCOPE BOUNDARY
==================================================

DO NOT implement any of the following in Step 2F:

- Historical Student Registry redesign
- Student archival/deletion redesign
- Enrollment integration
- Faculty Mapping integration
- Attendance calculation redesign
- Working-day/calendar redesign
- Holiday/Sunday redesign
- Leave percentage redesign
- Status redesign
- Edit-count redesign
- Attendance correction workflow
- Attendance writer changes
- Student Registry changes
- Database schema changes
- New Attendance tables
- Production deployment

Historical roster fidelity is a known future problem.

Calculation differences between Admin and Student are a known future problem.

Only Session isolation is being implemented now.

==================================================
STEP 1 — SERVER-SIDE SESSION RESOLVER
==================================================

Create or reuse one server-side helper for Attendance READS.

The helper must validate:

1. A Session ID was provided/resolved.
2. The Academic Session exists.
3. The Academic Session belongs to the authenticated school.
4. The Session ID is therefore valid for that tenant.

The helper MUST NOT trust a browser Session ID without validating ownership.

Do not use browser-selected Session as authority until it passes tenant validation.

The resolver should return the validated Session record/ID.

If no valid Session can be resolved:

    fail closed

Do NOT:

- read all Sessions
- silently use another Session
- silently fall back to an unscoped date-range query

Use the project's existing Session-context architecture where appropriate instead of creating a second conflicting mechanism.

If an existing helper can safely be reused after strengthening it for READ validation, prefer that rather than duplicating logic.

Do not rely only on Student IDs to establish tenant isolation.

Do not remove existing date filters.

Do not redesign existing calculations.

    records from other Academic Sessions are excluded.
