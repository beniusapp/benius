Implement **BENIUS STUDENT PORTAL — STEP 1: ACADEMIC SESSION FOUNDATION / ENFORCEMENT**.

This is a narrowly scoped foundation change.

Do NOT start fixing individual Student modules such as Homework, Classwork, Examination, Archives, Timetable, Noticeboard, Complaints, Leave, Dashboard, Fees, Attendance or Profile unless a tiny compatibility adjustment is strictly necessary for the new foundation.

The purpose of this step is to establish **one safe, reusable Student Academic Session boundary** that later module-specific fixes can use.

---

# 1. PERMANENT BENIUS RULE

BENIUS is a multi-school / multi-tenant application.

For every Student operation that is Academic Session based, the trusted server-side scope must be:

**Authenticated Student**
→ **derive Student's School/Tenant server-side**
→ **Selected Academic Session ID**
→ **verify Academic Session belongs to that same School**
→ **verify Student/session relationship where the operation requires enrollment**
→ **perform the read/write inside that scope**

Never trust a client-supplied school ID.

Never allow a Student from School A to use an Academic Session belonging to School B.

Never allow omission or invalidity of a required Academic Session to silently remove the session predicate.

---

# 2. IMPORTANT AUDIT FINDINGS

The previous read-only forensic audit established:

1. `StudentSessionProvider` fetches `/api/student/academic-sessions`.

2. The frontend stores the selected Student Academic Session in `sessionStorage` and validates restored IDs against the Student's available school sessions.

3. Session-aware request helpers can send:

`x-view-session-id`

4. Ordinary frontend `fetch()` calls do NOT automatically send that selected-session header.

5. Global middleware parses the header into `req.viewSessionId`.

6. GET middleware does not universally establish that the requested session is valid for the authenticated Student's school; individual routes currently have different behavior.

7. Student login stores:

`req.session.studentId`

but does NOT necessarily populate:

`req.session.schoolId`

8. Therefore the existing shared write/archive guard must NOT be treated as sufficient protection for Student requests merely because it checks `req.session.schoolId`.

9. Some APIs currently:
- validate the selected session,
- some fall back to active session,
- some accept nullable session IDs,
- and some omit the session predicate entirely when the header is absent.

This inconsistency is what Step 1 must address at the **foundation/helper level**.

---

# 3. DO NOT CHANGE THE STUDENT LOGIN MODEL UNNECESSARILY

Do NOT simply add/trust a client-provided school ID.

The authenticated Student identity must remain the authority.

The safe model is:

`req.session.studentId`
→ load authenticated Student
→ derive `student.schoolId`
→ validate requested Academic Session against that school.

If adding `schoolId` to the server-side Student login session is genuinely necessary, first determine whether that would affect existing Admin/Teacher/shared middleware behavior.

Prefer deriving the Student's school from the authenticated Student record unless there is a strong architectural reason otherwise.

Do NOT create a second authentication system.

Do NOT modify mobile bearer authentication unless strictly required for compatibility.

---

# 4. CREATE/CONSOLIDATE A REUSABLE STUDENT SESSION RESOLVER

Inspect the existing helpers first.

There may already be logic such as:

`student-examination-session.ts`

or equivalent session-resolution utilities.

Reuse/consolidate existing logic rather than creating duplicate competing session systems.

Create or strengthen a reusable server-side Student Academic Session resolver whose conceptual contract is:

Input:
- authenticated Student identity
- optional/required `x-view-session-id`
- operation mode

Output:
- authenticated Student
- trusted `schoolId`
- validated Academic Session
- validated `academicSessionId`
- optionally the Student's enrollment for that session when required

The resolver must derive school ownership server-side.

---

# 5. SUPPORT EXPLICIT OPERATION MODES

Do NOT force exactly the same behavior onto every Student API.

The foundation should support clear modes such as:

### GLOBAL

No Academic Session required.

Used for genuinely global Student data.

Examples:
- account/security
- permanent profile identity
- Gallery
- Faculty Info
- School Calendar
- E-Library

Do NOT force an Academic Session onto these.

### SELECTED_SESSION_REQUIRED

The operation requires an explicitly selected/validated Academic Session.

If the header is:
- missing,
- malformed,
- nonexistent,
- or belongs to another school,

the operation must fail safely.

Do NOT silently remove the session predicate.

### SELECTED_OR_ACTIVE_SESSION

Use only where existing BENIUS product behavior intentionally permits active-session fallback.

The selected session must still be validated against the authenticated Student's school.

Fallback must be explicit in code, not accidental.

### SELECTED_SESSION_ENROLLMENT_REQUIRED

For operations that depend on the Student's class/section/roll/status for the selected year:

Resolve:

**school + student + academic session**

against the `enrollments` table.

Return the selected-session placement such as:
- class
- section
- roll number
- enrollment status

Do NOT use current `students.class` / `students.section` as the historical placement when a selected-session enrollment is required.

---

# 6. FAIL-CLOSED BEHAVIOR

For a Student Academic Session operation, never use logic equivalent to:

`if session exists → filter by session`
`else → return records without session filtering`

when the operation requires a session.

That is precisely the cross-session behavior we are trying to eliminate.

For a required-session operation:

Missing session
→ controlled error.

Invalid session
→ controlled error.

Foreign-school session
→ controlled authorization/validation error.

Missing required Student enrollment
→ controlled error/empty behavior appropriate to the existing API contract.

Do NOT silently query all sessions.

---

# 7. TENANT ISOLATION

This is non-negotiable.

The resolver must verify:

`academic_sessions.school_id === authenticatedStudent.schoolId`

or the equivalent existing schema relationship.

Never accept:

`schoolId`

from Student request body/query/header as the authority.

Never resolve an Academic Session by ID alone and then use it without checking school ownership.

---

# 8. STUDENT IDENTITY

Student-specific operations must continue deriving the Student from authenticated server state.

Never trust a request parameter such as:

`studentId`

as a replacement for the authenticated Student identity.

The foundation should make it difficult for future Student routes to accidentally operate on another Student.
