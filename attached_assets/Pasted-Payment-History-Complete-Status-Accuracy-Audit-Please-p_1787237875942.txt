Payment History — Complete Status & Accuracy Audit

Please perform a thorough, read-only audit first of the entire payment-history system in this multi-tenant school application.

Do NOT make changes until the audit is complete and you have identified exactly how each payment/checkout attempt is created, updated, stored, and displayed.

Current Payment History Categories

The UI currently shows three main types:

1. Payment Paid
2. Payment Failed
3. Payment Cancelled

I want you to verify whether these three categories are technically and functionally correct.

Do NOT assume that the UI labels are correct simply because they look correct.

Trace the complete lifecycle from:

Student Portal → payment initiation → Razorpay Checkout → Razorpay response/webhook → backend processing → database → payment attempt/history record → Student/Admin History UI.

1. PAYMENT PAID — AUDIT COMPLETELY

Verify exactly what condition causes a payment to become Paid.

Determine whether the application marks a payment as paid only after a genuine successful/captured Razorpay payment.

Verify the relationship between:

- Razorpay Payment ID
- Razorpay Order ID
- Razorpay payment status
- "authorized"
- "captured"
- payment webhook events
- fee record
- payment attempt
- receipt
- receipt number
- invoice number

The application must NOT mark a fee as paid merely because:

- Checkout opened
- Order was created
- Payment was initiated
- Payment authorization was attempted
- Frontend received a temporary success response

The authoritative successful-payment condition must be clearly defined and consistently enforced.

Verify that:

- Amount paid is correct.
- Captured amount is correct.
- Fee record is correctly marked paid.
- Receipt is generated only when appropriate.
- Receipt number is generated correctly.
- Invoice number remains unchanged.
- Payment ID and Order ID belong to the same transaction.
- The payment cannot accidentally be recorded twice.
- Duplicate webhooks do not create duplicate payments or receipts.
- A successful payment after an earlier failed attempt is represented as a new successful attempt while preserving the failed attempt.

Check the actual Razorpay payment/webhook information and database records.

Verify that the application preserves:

- Payment ID, when Razorpay provides one
- Order ID
- Fee Record ID
- Payment Attempt ID
- Attempt number
- Timestamp

- Error code

- Error description

- Auth code, when available
- Refund information, when applicable

The UI should not invent a failure reason.

If Razorpay does not provide a particular field, display "—" rather than fabricating a value.

- Does NOT generate a successful payment receipt.
- Does NOT overwrite the invoice number.
- Does NOT overwrite previous payment attempts.
- Does NOT delete the failed attempt after a later successful payment.

A later successful payment must create/preserve its own successful payment record while the earlier failed attempt remains in history.

3. PAYMENT CANCELLED — VERY IMPORTANT AUDIT

This requires special attention.

Do NOT automatically treat every cancelled Checkout session as a Razorpay payment failure.

Determine exactly what our application currently means by:

Payment Cancelled

For example, the current UI says:

«Checkout dismissed by student (no payment attempted)»

Verify from the actual application flow whether this statement is technically true.

A cancelled attempt should be used for cases such as:

- Razorpay Checkout opened
- Student closed/dismissed Checkout
- No successful payment occurred
- No genuine Razorpay payment failure occurred

If there was actually a Razorpay payment attempt and Razorpay returned a genuine failure, that should be classified as Payment Failed, not merely Cancelled.

Therefore, clearly separate:

Checkout Cancelled

Student closed/dismissed the checkout before completing payment.

Payment Failed

A genuine payment attempt reached the payment gateway and failed.

These must not be mixed together.

Verify whether a cancelled checkout creates:

- Order ID
- Payment ID
- Payment Attempt ID
- Fee Record ID
- Timestamp
- Amount
- Cancellation reason
- Checkout/session information

Store only information that actually exists.

Do not fabricate a Payment ID for a cancellation where no payment was attempted.

5. PAYMENT ATTEMPT HISTORY MUST NEVER BE OVERWRITTEN

This is extremely important.

Every payment attempt must remain an independent historical record.

Example:

Attempt 1 → Failed
Attempt 2 → Cancelled
Attempt 3 → Paid

The history must preserve all three records:

- Payment Failed — Attempt #1
- Payment Cancelled — Attempt #2
- Payment Paid — Attempt #3

Do NOT collapse them into one record.

Do NOT overwrite the failed/cancelled record with the successful payment.

Do NOT delete previous attempts after successful payment.

The invoice number must remain the same across attempts because all attempts relate to the same invoice.

Payment ID and Order ID must remain tied to their respective attempt.
