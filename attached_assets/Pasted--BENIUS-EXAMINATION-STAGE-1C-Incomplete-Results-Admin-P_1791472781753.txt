# FIX 1 — TEACHER REPORT CARD: INCORRECT SUBJECT FAILURE COUNT

### Current problem

The examination calculation engine correctly identifies a Student with no applicable examination marks as:

- `resultStatus = incomplete`
- `promoted = null`
- No weighted average
- No grade

However, the Teacher Report Card still displays:

`0 fails`

This is misleading because the Student has not been evaluated.

### Required correction

For a Student whose result status is Incomplete:

- Weighted Average: `No data`
- Grade: `—`
- Subject Failures: `—` or `Not evaluated`
- Result Status: `Incomplete / Pending Result`
- Promotion Gate: `Pending — No marks`

Do not display a numeric failure count for an incomplete result.

### Preserve existing behavior

- A Student who legitimately scores zero must still receive an evaluated result.
- An explicitly Absent Student must retain existing examination behavior.
- A Student with partial marks must retain the currently configured calculation behavior.
- Completed results must continue to use existing grading and failure-count rules.

Prefer a narrow presentation correction.

Do not change the underlying calculation engine unless absolutely necessary.

# FIX 2 — ADMIN FINAL PROMOTION SUMMARY: INCOMPLETE STUDENTS SHOWN AS PROMOTED

### Current problem

The Admin Exam Controller Final Promotion Summary currently defaults to `promote` when no override or retained Teacher decision exists.

It does not consistently check the calculated `resultStatus`.

Therefore, an incomplete Student can appear as Promoted in the Admin preview.

The backend execution transaction already rejects incomplete results, but the UI must not display an invalid promotion suggestion.

### Required correction

For a Student with `resultStatus = incomplete`:

- Display `Incomplete / Pending Result`.
- Do not display Promoted.
- Do not display Retained.
- Do not show a promotion destination.
- Do not include the Student in Promoted totals.
- Do not include the Student in Retained totals.
- Do not indicate that the Student is eligible for execution.

### Important calculation rule

The Final Promotion Summary must distinguish:

1. Promoted
2. Retained
3. Pending / Incomplete

Do not automatically classify Pending Students as Retained.

Do not invent a promotion decision for an incomplete Student.

### Preserve existing behavior

For Students with completed examination results:

- Preserve existing promotion policy calculations.
- Preserve authorized Admin overrides.
- Preserve valid Teacher ledger decisions.
- Preserve existing configured pass/fail rules.

The Admin preview must agree with the authoritative backend execution eligibility.

# FIX 3 — LOCKED TEACHER LEDGER: INCORRECT READY STATUS

### Current problem

The Admin ledger-status calculation currently counts locked decisions as Ready without sufficiently checking current eligibility.

This allows inactive Students with no applicable examination marks to appear Ready.

The Admin UI can also offer `Review & Execute` for a cohort containing ineligible decisions.

### Required correction

A locked decision must not automatically mean that the Student is eligible for promotion execution.

Determine readiness using authoritative backend information, including:

- Authenticated School ID
- Source Academic Session ID
- Student ID
- Student active status for executable current-session operations
- Exact source-session Enrollment
- Enrollment active status
- Source Class and Section
- Selected examination term
- Applicable examination marks
- Calculated result completeness
- Existing locked Teacher decision
- Compatibility between the stored decision and calculated eligibility

### Required status behavior

For an eligible locked decision:

`Ready`

For an ineligible or conflicting locked decision:

`Ineligible / Requires Review`

For a missing or undecided decision:

`Pending`

Do not count an ineligible decision as Ready.

Do not count an incomplete Student as Promoted or Retained.

Do not present a partially eligible cohort as fully Ready.

If an execution action remains available for eligible Students in a mixed cohort, clearly identify the executable subset and ensure the backend independently validates the exact submitted batch. Never imply the entire cohort is ready.

### ABSOLUTELY DO NOT

### Backend design requirement

Do not implement a separate frontend-only eligibility calculation that can drift from the execution rules.

Prefer a shared authoritative backend eligibility evaluator or safe read-only projection of the existing execution requirements.

However, do not invoke a write-producing promotion transaction merely to calculate readiness.

If the current backend cannot expose trustworthy readiness without a substantial architectural redesign, STOP and report the blocker before proceeding.

### Historical session safeguard

Historical locked ledgers must remain visible under existing authorization.

Do not treat a Student's current inactive status as grounds to erase or hide their historical decision.

Distinguish historical record visibility from current promotion execution eligibility.
