# BENIUS — EXAMINATION STAGE 3B-4
## PHASE B1 — LOCAL POSTGRESQL ISOLATION PREPARATION
### LIMITED IMPLEMENTATION AUTHORIZATION

BENIUS is in DEVELOPMENT, not Production.

The owner authorizes Stage 3B-4 Phase B1 ONLY.

This authorization covers:
1. Preparing a disposable local PostgreSQL 16 test environment.
2. Implementing test-only database identity and safety guards.
3. Verifying that the disposable environment is isolated.
4. Reporting readiness for a separately approved Phase B2.

It DOES NOT authorize running Examination integration tests, authenticated UI tests, promotion execution, Academic Session activation, or changing existing BENIUS records.

## BACKGROUND

Previous audits established:

- PostgreSQL 16.10 server utilities are installed in the Replit workspace.
- `.replit` already includes the `postgresql-16` module.
- The existing BENIUS application uses `DATABASE_URL`.
- Stage 2B and Stage 3 activation database tests use that general connection setting.
- Their existing enablement flags do not establish database isolation.
- The activation test creates a PostgreSQL function and trigger.
- Existing Development records must not be exposed to these tests.
- No isolated test database has previously been confirmed.
- `/tmp` is available for disposable storage, but local PostgreSQL startup has not yet been tested.

# PART 1 — PRE-FLIGHT SAFETY INSPECTION

Before starting PostgreSQL:

- Confirm that the installed PostgreSQL utilities are available.
- Confirm their major version is 16.
- Confirm a suitable temporary data-directory location.
- Confirm the intended temporary directory does not already contain another database.
- Confirm an unused local port or isolated Unix-socket path can be selected.
- Confirm the workspace has sufficient memory and disk space for a minimal temporary cluster.
- Confirm that the PostgreSQL process will not use the managed Replit Development database.
- Confirm that no existing PostgreSQL service will be stopped, restarted or reconfigured.

Use only safe inspection commands.

Do not inspect existing database contents or connection-string values.

Record the pre-flight findings.

# PART 2 — CREATE A DISPOSABLE LOCAL POSTGRESQL CLUSTER

Only if Part 1 passes:

1. Create a new, uniquely named temporary directory under `/tmp`.
2. Initialize a new PostgreSQL 16 cluster in that directory using the installed PostgreSQL tools.
3. Do not reuse an existing data directory.
4. Configure PostgreSQL to accept connections only through a dedicated Unix-domain socket in the temporary directory, if supported.
5. If a TCP listener is necessary, bind only to loopback and use a dedicated unused port.
6. Never bind to `0.0.0.0` or expose PostgreSQL publicly.
7. Do not use the existing Development database connection settings.
8. Use a dedicated local test role with a nonblank test-only password and only the permissions needed for the disposable environment.
9. Do not reuse existing BENIUS credentials.
10. Keep database files, socket files and process metadata separate from the main application.
11. Do not modify system-wide PostgreSQL configuration.
12. Do not start or stop any existing database service.
13. Do not enable persistent automatic startup.

Use the least privileged OS account supported by the environment. Do not run the PostgreSQL server as root.

If any of these conditions cannot be met, stop and report the blocker.

# PART 3 — DATABASE IDENTITY AND FAIL-CLOSED GUARDS

Implement a dedicated test-only isolation mechanism.

Use a variable named:

`BENIUS_STAGE3B4_TEST_DATABASE_URL`

Requirements:

- Never default it to the existing `DATABASE_URL`.
- Never silently use the application's general database connection.
- Never overwrite the existing Development `DATABASE_URL`.
- Never log connection strings or passwords.
- Reject missing or malformed test configuration.
- Reject any test URL that is not explicitly associated with the disposable local cluster.
- Reject nonlocal hosts and unexpected ports or socket paths.
- Reject database identity mismatches.
- Reject use of a non-test database role.
- Reject missing or incorrect test-owned identity evidence.
- Reject connections if the isolated cluster cannot be positively identified.
- Do not rely only on the database name containing "test".
- Do not rely only on a URL string comparison as proof of isolation.

Create a test-owned identity marker only inside the disposable database.

Verify identity using a dedicated local test connection, not the existing application's database pool.

Use a combination of:
- Expected database name.
- Expected database role.
- Expected local socket or port.
- Test-owned identity marker.
- A unique cluster identifier or similarly strong independent evidence.

The identity check must occur before any future schema initialization, fixture insertion or integration test execution.

Ensure that a future test process cannot accidentally fall back to the existing Development database.

Do not read or compare secret values from the existing Development connection.
