CONFIRMED PRODUCT DECISIONS
===========================

The following decisions are FINAL for this audit:

### DECISION 1 — HISTORICAL STUDENT ATTENDANCE

Historical Attendance MUST remain visible even if the Student's current Student Registry row is physically deleted.

Therefore:

Student Registry
=
Global / Permanent Student Master

BUT

Historical Attendance
=
must remain independently recoverable for the selected Academic Session.

Example:

Student Registry:

```
RAM JAISWAL
student_id = 123
```

Academic Session:

```
2021–2022
```

Attendance:

```
student_id = 123
session_id = 2021–2022
date = historical date
status = Present
```

Later:

```
Student Registry row 123 is physically deleted.
```

When:

```
Academic Session 2021–2022
```

is selected, the historical Attendance record MUST still be displayable.

IMPORTANT:

Do NOT implement this requirement.

ONLY audit whether the CURRENT implementation satisfies it.

Determine exactly what happens when the Student Registry row is physically deleted.

Determine whether Attendance data itself survives.

Determine whether Admin/Student/Teacher historical Attendance reads can still retrieve the record.

Determine whether the historical Student name/identity can still be displayed.

Do NOT assume that a foreign key cascade is acceptable merely because it is currently implemented.

==================================================
DECISION 2 — SUNDAY ATTENDANCE
==============================

A Sunday MAY be a valid Attendance day.

If Attendance is deliberately marked on Sunday:

```
the Attendance record counts.
```

Therefore:

Sunday itself MUST NOT automatically invalidate an Attendance record.

The audit must determine:

* whether Teacher marking on Sunday is currently allowed
* whether the Attendance record is stored
* whether the server calculation counts it
* whether Student calculation counts it
* whether Admin calculation counts it
* whether Student UI hides it
* whether calendar logic incorrectly excludes it

IMPORTANT:

Do NOT redesign the calendar.

Do NOT introduce a new Sunday policy.

Simply compare current behavior against the confirmed requirement:

```
DELIBERATELY MARKED SUNDAY ATTENDANCE COUNTS.
```

DECISION 3 — ACTIVE SESSION 7-DAY CORRECTION WINDOW
===================================================

The existing 7-day correction/edit behavior is intentional.

Therefore:

### ACTIVE SESSION

A Teacher may correct/edit Attendance for dates within the existing 7-day correction window.

That behavior MUST remain.

### ARCHIVED SESSION

Attendance belonging to an archived Academic Session MUST be read-only.

Therefore:

```
Active Session
    ↓
current Attendance + existing 7-day correction behavior

Archived Session
    ↓
read-only
```

IMPORTANT:

Do NOT remove the 7-day correction window.

Do NOT redesign correction.

Do NOT change correction behavior in this step.

ONLY verify current behavior.

STEP 2D — CRITICAL VERIFICATION
===============================

Step 2D was previously implemented with the following intended behavior:

```
Authenticated Teacher
        ↓
authenticated school
        ↓
server resolves ACTIVE Academic Session
        ↓
sessionId determined server-side
        ↓
same sessionId applied to ALL Attendance records
        ↓
Attendance records persisted
```

The previous audit now reports that the current POST appears to use:

```
x-view-session-id
```

as the Session source.

This MUST be investigated before ANY implementation.

DO NOT change Step 2D.

DO NOT fix it.

DO NOT redesign it.

ONLY determine the exact current behavior.

Inspect the complete current:

```
POST /api/attendance
```

flow.

Trace:

1. Authentication.
2. Authenticated school resolution.
3. Academic Session resolution.
4. `x-view-session-id`.
5. Any other Session headers/body/query parameters.
6. Active Session lookup.
7. Session ownership validation.
8. Archived Session validation.
9. Which exact `sessionId` is ultimately passed to Attendance creation.
10. Whether one `sessionId` is resolved once and reused for every Student in the request.
11. Behavior when `x-view-session-id` is:

    * absent
    * the active Session
    * another Session belonging to the same school
    * an archived Session
    * a Session belonging to another school
    * invalid/nonexistent
12. Behavior if the browser attempts to manipulate the header.

IMPORTANT:

Do NOT confuse:

```
"browser may provide a Session ID"
```

with:

```
"browser is authoritative."
```

Determine whether the server independently resolves and enforces the authenticated school's active Session.

The question is NOT whether the header is validated.

The question is:

```
WHO determines the Session used for the Attendance write?
```

SERVER
or
BROWSER

Report the exact current behavior.
