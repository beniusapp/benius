# BENIUS — FEES & PAYMENTS
## STAGE 1C-1 — HISTORICAL STUDENT PLACEMENT DISPLAY CORRECTION
### IMPLEMENTATION PROMPT — AWAITING OWNER APPROVAL

IMPORTANT: This prompt is prepared for owner review. Do not execute it until the owner explicitly authorizes Stage 1C-1 implementation.

BENIUS is a multi-tenant School Management Information System currently in DEVELOPMENT.

The owner has approved the following business policies:

1. Historical financial placement uses the exact Academic Session enrollment (Option A).
2. Missing historical placement must display as unavailable, never guessed from current Registry.
3. Unresolved financial rows must remain in grand totals and later appear in a separately identifiable unresolved report group.
4. Mismatched payment/invoice Session IDs must be flagged, not silently repaired.
5. Shared Mobile Admin analytics may eventually receive corrected class attribution without changing Mobile files or API response shape.
6. Direct document session-authorization hardening belongs to Stage 1C-3, not Stage 1C-1.
7. Student Profile must continue showing current Registry placement.

## OBJECTIVE

Correct historical Student class, section and roll-number display in the approved Principal and Student Fees & Payments surfaces.

Example:

Student Ram Jaiswal:

- 2026–2027 enrollment: Class 1-A.
- 2027–2028 enrollment: Class 2-A.
- Current Student Registry: Class 2-A.

When viewing 2026–2027 financial records, the displayed placement must be Class 1-A.

When viewing 2027–2028 financial records, the displayed placement must be Class 2-A.

This stage must not modify financial values or existing data.

## PHASE B — HISTORICAL PLACEMENT RESOLUTION

Implement a narrowly scoped backend resolution mechanism.

For every session-specific fee record, resolve placement using:

- Authenticated school ID.
- Fee record Student ID.
- Fee record Session ID.

Match against the exact `enrollments` record.

Requirements:

1. Enforce all three identity keys.
2. Never join enrollment by Student ID alone.
3. Never substitute the selected UI session for the fee record's actual Session ID.
4. Never fall back to current `students.class`, `students.section`, or `students.rollNumber`.
5. Preserve Student ownership and existing school authorization.
6. Preserve archived-session read-only behavior.
7. Do not mutate enrollment, Registry, invoices or payments.
8. Preserve existing financial values.
9. Avoid N+1 database queries in lists.
10. Prefer a school/session/student-keyed LEFT JOIN for bulk queries.
11. Keep unresolved fee records visible.
12. Do not arbitrarily select one row if multiple conflicting historical enrollments are detected.

The existing resolver is located around:

`artifacts/api-server/src/storage.ts:11900–11925`

Reuse it only where its behavior is safe for this purpose.

## PHASE C — UNRESOLVED PLACEMENT

If a fee record has no matching enrollment:

- Keep the fee record.
- Return an explicit unresolved placement state.
- Display "Historical placement unavailable".
- Do not show the current Registry class as historical.
- Do not assign the fee record to a guessed class or section.
- Do not modify the financial record.
- Do not automatically create or backfill enrollment.

If the fee record has a NULL Session ID:

- Treat historical placement as unresolved.
- Do not infer the active session.
- Do not assign it to a selected session.
- Preserve existing record-selection and authorization behavior.

Use backward-compatible response fields wherever possible.

Ensure unresolved class, section and roll values are represented consistently and do not accidentally render as "undefined", "null", or the current Registry placement.

Do not add the unresolved financial-report grouping in this stage; that belongs to Stage 1C-2.
