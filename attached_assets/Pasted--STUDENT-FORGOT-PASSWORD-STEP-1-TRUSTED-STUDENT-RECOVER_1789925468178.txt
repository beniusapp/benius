==================================================
B. SECURITY OBJECTIVE
==================================================

The current Student email field is NOT a trusted recovery factor.

An email address entered by a school administrator does NOT prove that the Student or guardian controls that mailbox.

Therefore:

students.email
MUST NOT become trusted merely because it is populated.

Do NOT add a boolean such as:

emailVerified = true

and allow administrators to manually mark arbitrary addresses as verified.

That would create a false security boundary.

A recovery email must become trusted only after the recipient successfully completes an actual verification challenge sent to that exact email address.

==================================================
G. OTP SECURITY
==================================================

Use the existing cryptographic primitives already accepted in Admin/Teacher recovery where appropriate.

Do NOT duplicate insecure OTP generation.

OTP requirements:

- cryptographically secure
- exactly 6 digits
- 10-minute expiry
- maximum 5 failed attempts
- atomic attempt increments
- counter capped at 5
- HMAC/hash only in database
- timing-safe comparison
- single-use
- replay-resistant
- replacement invalidates previous active challenge
- never log plaintext OTP
- never return OTP through an API response
- never store plaintext OTP

Do not use Math.random().

Do not expose development OTPs through console logs.

==================================================
H. VERIFICATION FLOW
==================================================

The verification process should conceptually be:

1. Authorized school administrator selects a specific Student.
2. Administrator enters/sets the recovery email through the existing Student-management workflow.
3. The application creates a verification challenge for that exact Student + school + email.
4. The application sends the six-digit verification code to that exact email.
5. Recipient enters the OTP into a verification UI.
6. Server verifies the challenge transactionally.
7. On success:
   - the exact recovery contact becomes verified
   - verified_at is recorded
   - the verification challenge is consumed
8. Future changes to the email must invalidate the existing verified state.

IMPORTANT:

The administrator must NOT be able to simply click:

"Mark Email Verified"

without an actual email ownership challenge.

The actual recipient must complete the verification challenge.

==================================================
I. EMAIL CHANGE INVALIDATION
==================================================

A verified email must not remain trusted after the underlying email changes.

Therefore:

If the Student's recovery email changes:

1. Existing verified recovery contact for the previous address must no longer be authoritative.
2. New email must require a new verification challenge.
3. The previous verification state must not automatically transfer.
4. Previously issued verification challenges for the old address must be invalidated.
5. Future Forgot Password must use only the currently verified contact.

Do not silently carry verification from one email address to another.

==================================================
L. ATOMIC VERIFICATION
==================================================

OTP verification must be transactional.

Inside the transaction:

1. Lock the exact challenge.
2. Validate school.
3. Validate Student.
4. Validate contact.
5. Validate challenge purpose.
6. Validate not consumed.
7. Validate not expired.
8. Validate attempt count < 5.
9. Compare OTP using HMAC/timing-safe comparison.
10. On incorrect OTP:
    - increment attempt count atomically
    - cap at five
11. On correct OTP:
    - mark contact verified
    - set verified_at
    - consume challenge
    - invalidate other active verification challenges for that same Student/contact
12. Commit.

If any operation fails:

- no partial verification
- no partially consumed challenge
- no inconsistent contact state

==================================================
M. CONCURRENCY REQUIREMENTS
==================================================

Test concurrent verification.

For two simultaneous correct OTP submissions:

- exactly one may succeed
- the other must fail because the challenge has already been consumed

For simultaneous wrong OTP attempts:

- attempt count must never exceed five
- no lost increments
- no race may bypass the five-attempt limit

For replacement:

- issuing a new verification challenge must invalidate the previous active challenge atomically.
