# BENIUS MOBILE STEP 6

## STUDENT NAVIGATION + FIRST REAL DESTINATION

This remains an incremental implementation.

DO NOT build the entire Student application.

DO NOT build Teacher or Admin.

DO NOT redesign BENIUS.

==================================================

1. PRIMARY OBJECTIVE
   ==================================================

Establish the real native Student navigation hierarchy and implement the FIRST genuine Student destination reachable from the existing BENIUS Student Home/navigation.

The existing BENIUS WEB APPLICATION remains the source of truth.

The objective is:

Existing BENIUS Student responsive/mobile navigation
↓
faithful native React Native navigation
↓
same backend
↓
same database
↓
same business rules
↓

↓

Do not invent navigation simply because this is a mobile application.

==================================================
2. READ-ONLY AUDIT FIRST
========================

Before changing code, inspect the existing web application.

Identify:

A. Student web routes.

B. Student dashboard navigation.

C. Student mobile/responsive navigation behavior.

D. Header/menu/navigation components.

E. Bottom navigation, drawer, tabs, menus, or other navigation mechanisms if present.

F. Every destination directly reachable from Student Home.

G. Which destination the web application presents as the primary/first destination.

H. API calls used by that destination.

I. Existing React Query hooks.

J. Existing reusable components.

K. Responsive behavior at approximately:

390 × 844

L. Authentication requirements.

M. Academic Session requirements.

Do not guess.

Use the actual web implementation.

==================================================
3. CHOOSE THE FIRST DESTINATION
===============================

After inspecting the web application, select the first destination according to this rule:

1. Prefer the first Student destination directly reachable from the actual responsive/mobile navigation.
2. Prefer a destination whose web implementation is sufficiently self-contained to reproduce safely.
3. If Student Profile is directly exposed and is the first appropriate destination, use Student Profile.
4. If another destination is clearly first in the existing navigation, use that destination instead.

Document why that destination was selected.

Do NOT start Student Examination merely because it is a major module.

==================================================
4. NO FAKE DESTINATIONS
=======================

Do not create fake working screens.

For destinations that are not implemented yet:

* preserve their navigation presence if the real web UI exposes them
* make unavailable destinations clearly indicate that implementation is pending
* do not display fake data
* do not create fake APIs

The user must never believe an unfinished module is fully implemented.

==================================================
5. NATIVE NAVIGATION
====================

Use the existing Expo Router architecture.

Use native navigation patterns appropriate to the existing web navigation hierarchy.

Do not use WebView.

Do not embed the entire web application inside the native app.

Preserve:

* screen hierarchy
* back behavior
* active destination indication
* header behavior
* menu behavior
* session controls
* logout behavior

Where the web uses an interaction that has no exact native equivalent, use the closest native interaction while preserving the same user flow.

==================================================
7. AUTHENTICATION
=================

Reuse the existing mobile authentication system.

Do not create another login/session system.

Use:

* AuthContext
* SecureStore
* mobile access credential
* mobile refresh credential
* /api/mobile/auth/me
* existing generation-aware refresh coordinator
* existing logout/revocation behavior

Do not store passwords or PINs.

The server remains authoritative for identity.

==================================================
8. TENANT ISOLATION
===================

This is mandatory.

Every request must remain constrained to the authenticated Student's school.

Never accept a client-supplied schoolId as authority.

Never allow:

Student A / School A
↓
Student B / School B

data access.

If the selected destination exposes Student-specific information, the server must derive the Student identity from the authenticated mobile credential.

==================================================
9. ACADEMIC SESSION
===================

Reuse the existing Step 4/5 Academic Session foundation.

Keep separate:

* authentication
* school/tenant
* Student identity
* Academic Session

If the destination is session-sensitive:

* include the selected Academic Session
* use the existing session-scoped API helpers
* include session identity in query keys
* refetch when session changes
* prevent stale previous-session data

If the destination is not session-sensitive, do not artificially make it session-sensitive.

Follow the existing web behavior.

==================================================
10. API IMPLEMENTATION
======================

Prefer existing backend endpoints.

Do not duplicate backend business logic in React Native.

If an existing endpoint cannot safely serve the mobile screen, create the smallest possible:

GET /api/mobile/student/...

endpoint.

Any new endpoint must:

* authenticate the mobile bearer credential
* derive school from authenticated principal
* derive Student identity from authenticated principal
* enforce Academic Session where required
* reject cross-school access
* reject cross-student access
* reuse existing domain/business logic
* return only the data needed by the screen

Do not perform unrelated backend refactoring.

==================================================
11. TANSTACK QUERY
==================

Follow the Step 4B and Step 5 cache-key rules.

For session-sensitive data, the query key must distinguish:

resource
school
Student/principal
role
Academic Session

Avoid duplicate requests.

Invalidate/refetch correctly when:

* Academic Session changes
* Student logs out
* authenticated identity changes

Do not allow previous Student/session data to survive an identity change.

==================================================
12. LOADING / EMPTY / ERROR / OFFLINE

Implement:

* loaded
* empty
* API error
* retry
* offline
* authentication failure
* failed image/photo fallback where applicable

Do not use fake values.

Use the existing API/cache architecture.
