ATTEMPT LIMIT
==================================================

Use the existing Admin OTP attempt policy.

- maximum 5 failed OTP attempts

Do not change this policy.

On an incorrect OTP:

1. Increment the challenge attempt counter atomically.
2. Do NOT mark the challenge verified.
3. Do NOT generate/activate a reset stage.
4. Do NOT consume the challenge unless the existing Admin design explicitly requires it at lockout.

→ write attempts

==================================================
CONCURRENT OTP VERIFICATION
==================================================

Protect against concurrent verification attempts.

Two concurrent requests using:

same challenge
same user
same school
same correct OTP

must not produce inconsistent state.

At most one should transition:

The other must observe that the challenge is already verified and fail safely.

Use database transaction/locking or an atomic conditional update.

Similarly, concurrent wrong OTP attempts must not allow the attempt counter to exceed the configured limit incorrectly.

==================================================
REPLAY PROTECTION
==================================================

After successful OTP verification:

A second OTP verification using the same challenge must fail.

A second verification must NOT:

- modify verifiedAt
- reset the attempt counter
- issue another reset token
- alter the challenge
- consume another challenge

The challenge remains in:

verifiedAt != NULL
consumedAt = NULL

until Step 5 password reset.
