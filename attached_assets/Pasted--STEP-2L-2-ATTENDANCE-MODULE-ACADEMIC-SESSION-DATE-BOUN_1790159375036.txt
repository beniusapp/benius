# STEP 2L-2 — ATTENDANCE MODULE

## ACADEMIC SESSION DATE-BOUNDARY ENFORCEMENT

### CONTROLLED AUDIT + IMPLEMENTATION

We have completed and accepted Step 2L-1.

Step 2L-1 changed Teacher Attendance writes so the server resolves the ACTIVE Academic Session from the authenticated school's `req.session.schoolId`. The browser's `x-view-session-id` can no longer override the write Session.

Now implement ONLY the next Attendance fix identified by the audit:

> **Teacher Attendance dates must be inside the Academic Session's start/end date boundaries.**

---

# 1. HARD REQUIREMENTS — DO NOT CHANGE

These are permanent Attendance requirements.

### Multi-tenant isolation

* `req.session.schoolId` is authoritative.
* Never trust a browser-provided school ID for ownership.
* Never allow cross-school Attendance access, calculation, or writes.
* Academic Session must belong to the authenticated school.

### Student Registry

* Student Registry is GLOBAL/PERMANENT.
* Do NOT recreate/reset Students per Academic Session.
* Do NOT make Enrollment a prerequisite for Attendance marking.

### Teacher authorization

Any authenticated Teacher belonging to the same school may mark Attendance.

Do NOT introduce:

* Faculty Mapping restrictions
* class assignment restrictions
* subject assignment restrictions

unless such a check already existed and is required for security.

### Existing correction window

KEEP the existing active-Session correction rule exactly as it currently works:

* Today is writable.
* Previous 7 days are writable.
* Therefore today through today-minus-seven-days inclusive remains allowed.
* Older dates remain rejected.
* Future dates remain rejected.
* Existing holiday/edit restrictions remain unchanged.

**Do not replace the 7-day rule.**

We are adding a Session-boundary check in addition to the existing rules.

### Archived Sessions

Archived Academic Sessions remain read-only.

Do not weaken the existing archived-session mutation protection.

### Sunday

A Sunday can be a valid Attendance date.

If a Sunday is deliberately marked and:

* it belongs to the active Academic Session,
* it passes the existing Attendance rules,
* and it is not blocked by an existing holiday restriction,

then it must remain valid and count as Attendance.

Do NOT make every Sunday automatically a working day.

### Timezone

All Attendance business dates must continue using:

**IST / Asia/Kolkata**

Do not introduce UTC date comparisons for Attendance business-date validation.

### Scope

This step is ONLY about enforcing Academic Session date boundaries on Attendance writes.

Do NOT implement the other pending Attendance fixes yet:

1. Physical Student deletion/history preservation.
2. Student UI Sunday display/counting.
3. NULL Session investigation for Teacher Self-Attendance/correction records.

---

# 2. REQUIRED BEHAVIOR

For every Teacher Student-Attendance write:

```text
Authenticated Teacher
        ↓
Authenticated School
        ↓
Server resolves ACTIVE Academic Session
        ↓
Validate Attendance date
        ↓
7-day correction rules
        +
Academic Session start/end boundaries
        ↓
Write Attendance using resolved Session ID
```

The Attendance date must satisfy BOTH:

### Rule A — Existing correction/date rule

Keep the existing rules exactly as they are.

AND

### Rule B — Academic Session boundary

The Attendance date must be:

```text
session.start_date <= attendance_date <= session.end_date
```

assuming the Session has both boundaries.

The comparison must be by **IST business date**, not timestamp/UTC conversion.

# 5. IMPLEMENTATION REQUIREMENT

The server must use the SAME active Academic Session resolved in Step 2L-1.

Do not:

* resolve one Session for validation and another Session for writing;
* use `x-view-session-id`;
* trust a browser-selected Session;
* query another school;
* silently switch to another Session.

The resolved Session should be the single authoritative Session for this request.

Conceptually:

```text
const activeSession = await storage.getActiveSession(authenticatedSchoolId);

validate attendanceDate against activeSession.startDate/endDate;

write all Attendance rows using activeSession.id;
```

Use the project's existing architecture and naming conventions rather than copying this pseudocode literally.

---

# 6. DATE COMPARISON REQUIREMENT

Be very careful about date/time handling.

Attendance dates are business dates.

Academic Session boundaries are business dates.

Compare them as IST/date-only values.

Do NOT introduce logic such as:

```text
new Date(attendanceDate).toISOString()
```

if that can cause a timezone boundary shift.

Do NOT compare arbitrary UTC timestamps against Session date-only values.

Use the project's existing date-only/IST utilities where appropriate.
