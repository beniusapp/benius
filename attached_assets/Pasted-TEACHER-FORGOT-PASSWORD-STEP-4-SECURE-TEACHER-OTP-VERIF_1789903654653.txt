==================================================
APPROVED DESIGN DECISION
==================================================

Use the following design:

GENERATE A NEW RESET TOKEN ONLY AFTER SUCCESSFUL OTP VERIFICATION.

Do NOT retain the Step 3 plaintext reset token.

Do NOT store plaintext reset tokens in the database.

Do NOT create an in-memory token store.

Do NOT use browser state.

Do NOT weaken the HMAC-only storage model.

The lifecycle becomes:

Step 3:
Teacher recovery challenge created
→ OTP hash stored
→ initial reset-token hash may exist as currently implemented

Step 4:
Correct OTP
→ verify OTP
→ generate NEW cryptographically secure reset token
→ HMAC the new token
→ replace resetTokenHash
→ set resetTokenExpiresAt = now + 15 minutes
→ mark verifiedAt
→ return plaintext NEW reset token only to the trusted server-side caller

Step 5:
Trusted server-side recovery state will later hold/use that reset token
→ password reset
→ Step 2 atomically consumes the challenge

This is the ONLY reset-token lifecycle change permitted in this step.

==================================================
OTP VERIFICATION
==================================================

The supplied OTP is plaintext only in transient memory.

Calculate its HMAC using the existing recovery HMAC helper.

Compare against the stored OTP HMAC using the existing secure/timing-safe mechanism.

Never compare plaintext OTP against plaintext database data.

Never use:

Math.random()

Never log:

- OTP
- OTP hash

==================================================
ATTEMPT LIMIT
==================================================

Use the existing established Admin policy:

MAXIMUM 5 FAILED OTP ATTEMPTS.

On an incorrect OTP:

- increment attempt count atomically
- do not verify the challenge
- do not rotate the reset token
- do not consume the challenge

Once the maximum is reached:

- further OTP attempts fail
- even a correct OTP must not succeed

The attempt counter must be concurrency-safe.

Do NOT implement:

read → increment in JavaScript → write

Use a database transaction/row lock/atomic conditional update.

==================================================
SUCCESSFUL OTP VERIFICATION
==================================================

When the OTP is correct:

Within ONE database transaction:

1. Lock/revalidate the challenge and Teacher/user account.

2. Revalidate tenant identity.

3. Revalidate:
   - Teacher role
   - user active
   - Teacher active
   - challenge unverified
   - challenge unconsumed
   - OTP unexpired
   - attempts below limit

4. Verify the OTP HMAC.

5. Generate a NEW cryptographically secure reset token.

6. HMAC the NEW reset token using the existing recovery HMAC helper.

7. Replace:

resetTokenHash

with the new token's HMAC.

8. Set:

resetTokenExpiresAt = now + 15 minutes

9. Set:

verifiedAt = now

10. Keep:

consumedAt = NULL

11. Return the NEW plaintext reset token only to the trusted server-side caller.

The plaintext reset token must NEVER be stored in the database.

==================================================
ATOMICITY
==================================================

The following MUST be one atomic database transaction:

- challenge locking/revalidation
- Teacher/user revalidation
- OTP verification
- reset-token generation
- reset-token HMAC replacement
- reset-token expiry update
- verifiedAt update

If any database operation fails:

ROLLBACK

No partial state is allowed.

In particular, if reset-token replacement fails:

- verifiedAt must remain NULL
- old resetTokenHash must remain unchanged
- challenge must remain unverified
