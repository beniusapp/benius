FIX 4B — DECIMAL GRADING BOUNDARY SUPPORT
STEP 1: IMPLEMENTATION

We have completed a read-only investigation of the current Academic Policy / grading system.

Root cause confirmed:
The Examination calculation engine can produce decimal percentages such as 59.7, but grading_rules currently support only integer min/max boundaries. Therefore selectGrade(59.7) fails against a policy such as C = 35–59 and B = 60–79.

Implement ONLY the decimal grading-boundary capability described below.

LOCKED BUSINESS CONTRACT
========================

1. Grading rule min_percent and max_percent must support values from 0.00 to 100.00.

2. Maximum precision is exactly 2 decimal places.

3. Grade ranges are inclusive:
   percentage >= minPercent AND percentage <= maxPercent

4. The intended two-decimal closed-band model is supported, for example:
   D = 0.00–34.99
   C = 35.00–59.99
   B = 60.00–79.99
   A = 80.00–100.00

5. Grade-selection input must be canonically normalized to at most 2 decimal places before matching.

6. Validation must NOT use floating-point +0.01 arithmetic to determine continuity.
   Prefer integer hundredths internally:
   59.99 => 5999
   60.00 => 6000

7. Existing integer policy values such as 35, 59, 60 must remain exactly equivalent:
   35 => 35.00
   59 => 59.00
   60 => 60.00

8. DO NOT automatically transform existing policies such as:
   C = 35–59
   into:
   C = 35.00–59.99

   Existing tenant policy data must remain unchanged unless a user explicitly edits it.

9. pass_percentage remains INTEGER for this fix.
   Do not convert pass_percentage to decimal.

10. Do not change:
    - Absent/Missing semantics
    - cumulative calculation
    - calculation-engine consolidation
    - Academic Session isolation
    - promotion rules
    - weighting rules
    - attendance rules

MULTI-TENANT REQUIREMENT
========================

This is a true multi-tenant SaaS application.

Every grading policy remains owned by its authenticated school/tenant.

Never trust a client-supplied schoolId for authorization.

Preserve the existing authenticated-user -> schoolId ownership model.

A grading tier/rule from School A must never be readable, editable, or applied to School B.

Do not weaken any existing tenant/session authorization.

DATABASE
========

Change grading_rules.min_percent and grading_rules.max_percent from integer-only storage to an appropriate PostgreSQL NUMERIC representation supporting 0.00–100.00 with 2 decimal places.

NUMERIC(5,2) is acceptable if consistent with the existing schema conventions.

Preserve all existing values exactly.

Before running any migration:

- inspect the existing schema
- inspect the existing migration setup
- verify how Drizzle/PostgreSQL numeric values are returned by the current project
- make the application mapping explicit and safe

Do not silently round or truncate values.

If the existing migration architecture cannot safely support this change without a destructive or ambiguous operation, STOP and report the blocker instead of improvising.

API / VALIDATION
================

Grading-rule API input must:

- accept integers and valid decimal values
- accept at most 2 decimal places
- accept 0.00 through 100.00
- reject values below 0
- reject values above 100
- reject more than 2 decimal places
- reject NaN/infinite/non-numeric values
- never silently round excessive precision

Use strict decimal parsing rather than parseFloat() alone.

Do not change pass_percentage behavior in this fix.

Update validateGradingRules() so it supports the new decimal contract.

Use integer hundredths for boundary comparisons/continuity validation where appropriate.

Continue enforcing:

- min <= max
- no overlaps
- no gaps when complete coverage is required
- valid 0.00–100.00 bounds
- valid grading policy structure

59.7

Do not introduce a universal fallback grade.

Do not invent a grade when no configured rule matches.
