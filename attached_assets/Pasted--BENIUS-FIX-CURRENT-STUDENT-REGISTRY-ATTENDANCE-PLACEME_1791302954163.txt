## CONFIRMED PRODUCT DECISION

For the CURRENT / ACTIVE Academic Session:

**Student Registry is the human-managed source for the Student's current academic placement.**

When the current Student's:

- Class
- Section
- Roll Number

is created or changed through Student Registry, BENIUS must automatically keep that Student's **ACTIVE Academic Session enrollment** synchronized.

Normal users must NOT have to separately manage an enrollment.

However:

**Session Enrollment remains the authoritative placement record used by session-sensitive academic modules such as Attendance.**

Historical Academic Session enrollments must remain preserved.

# RULE 1 — CURRENT STUDENT REGISTRY PLACEMENT

For the ACTIVE Academic Session, the current Student Registry placement must automatically synchronize to the Student's active-session enrollment.

Conceptually:

```text
Student Registry

Class
Section
Roll Number

        ↓ SAVE

ONE BACKEND OPERATION

        ↓

Current Student Profile
+
Active Academic Session Enrollment
```

Both must agree after a successful operation.

---

# RULE 2 — SAME TRANSACTION

This synchronization must be atomic.

Do NOT do:

```text
Update Student
→ success

Update Enrollment
→ failure

Return success
```

Instead:

```text
BEGIN TRANSACTION

Validate authenticated school
Validate Student belongs to school
Resolve active Academic Session
Validate placement

Update Student current placement
Create/update active-session enrollment

COMMIT
```

If either operation fails:

```text
ROLLBACK
```

The Student profile and active-session enrollment must never be left half-synchronized.

Fix the effective Web Student Registry Edit path:


# RULE 8 — HISTORICAL SESSIONS MUST NEVER CHANGE

This is extremely important.

Suppose:

```text

```


```text

```

Previous Academic Sessions remain historical/read-only.

No current Student Registry edit may rewrite historical placement.

---

# RULE 9 — DANGEROUS GET SIDE EFFECT

The audit found:

```text
GET /api/student/exam/enrollment-history
```

can UPSERT the active-session enrollment using the current Student profile.

This is unsafe.

A GET/read request must NOT silently modify Student academic placement.

Correct this.

The enrollment-history GET must become READ-ONLY.

It may read and return enrollment history.

It must NOT:

- create enrollment
- update enrollment
- overwrite Class
- overwrite Section
- change status
- synchronize profile into enrollment

Enrollment synchronization belongs only in explicit authorized write operations.
