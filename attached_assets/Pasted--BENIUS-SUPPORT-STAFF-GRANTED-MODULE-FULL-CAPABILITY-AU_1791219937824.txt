# PRODUCT INTENT

Principal/Admin creates a Support Staff account.

While creating/managing that Support Staff account, Principal/Admin selects which modules that Support Staff is allowed to access.

Example:

Principal grants:

- Student Registry
- Teacher Registry
- Visitor Log
- Fees & Payments

Support Staff then logs in using the credentials created/provided by Principal/Admin.

My intended concept is:

> Support Staff is an operational assistant to the Principal/Admin.

Therefore, when Principal/Admin explicitly grants a module to Support Staff, the Support Staff should be able to perform the normal operational tasks available to Principal/Admin INSIDE THAT GRANTED MODULE.

Example:

If Student Registry is granted, Support Staff should not merely be able to open Student Registry.

They should be able to perform the Student Registry operations that the Principal normally performs, subject to any action that is intentionally defined as Principal-only for security/account ownership reasons.

The same principle applies to other granted operational modules.

However:

> A Support Staff member must NEVER gain access to a module that Principal/Admin did not grant.

---

# IMPORTANT DISTINCTION

I am NOT asking you to automatically make Support Staff equal to Principal everywhere.

Principal/Admin account-level/security functionality may remain Principal-only, such as:

- Principal/Admin personal profile
- Principal/Admin password

- recovery/security settings
- security log
- Support Staff account/permission administration itself, if currently intended as Principal-only
- other genuinely account-owner/security-sensitive operations

### MODULE OPERATION

An operation belonging to a module explicitly granted to Support Staff.

versus

### PRINCIPAL-ONLY ACCOUNT/SECURITY OPERATION

An operation that should remain restricted even if Support Staff can access operational modules.

Do not invent new restrictions.

# VERY IMPORTANT — DIRECT API SECURITY

For every grantable module verify BOTH directions:

### Granted module

Support Staff WITH permission:

→ required operational APIs should work according to intended module access.

### Non-granted module

Support Staff WITHOUT permission:

→ frontend module hidden/rejected
AND
→ direct API request rejected.

It is NOT sufficient to hide a module from the sidebar.

Backend must enforce `allowedModules`.

For example:

```text
Support Staff allowedModules:
student_registry
visitor_log

Student Registry API → ALLOW
Visitor Log API → ALLOW

Teacher Registry API → REJECT
Fees API → REJECT
```

even if the Support Staff manually calls the API.
