## 1. CONFIRMED ISSUE

Example:

Student: Ram Jaiswal

Academic Session 2026–2027:
- Historical placement: Class 1-A.
- Fee invoices, ledger and payments belong to this session.

Academic Session 2027–2028:
- Student promoted to Class 2-A.
- Current Student Registry now shows Class 2-A.

When the Principal switches back to 2026–2027, historical Fees & Payments screens incorrectly show Class 2-A.

Expected:
- 2026–2027 financial records display Class 1-A.
- 2027–2028 financial records display Class 2-A.

The same issue affects historical class-wise financial reports and certain Student invoice/receipt documents.

The Stage 1A-1 investigation confirmed the source-level root cause:

Fee queries correctly filter financial records by Academic Session, but their placement joins read current class/section/roll from the session-independent `students` Registry.

The existing `enrollments` table stores:
- schoolId
- studentId
- sessionId
- className
- sectionName
- rollNo
- status

The existing historical enrollment resolver is located around:

`artifacts/api-server/src/storage.ts:11900–11925`

Financial records currently do not store their own class/section/roll snapshots.

This stage must design the safest correction.

## 3. DESIGN THE AUTHORITATIVE HISTORICAL PLACEMENT RESOLUTION

Investigate the exact implementation approach for resolving placement using:

- Authenticated school ID.
- Fee record's Student ID.
- Fee record's Academic Session ID.
- Exact matching `enrollments` row.

The proposed design must:

1. Use the fee record's own Session ID as the authoritative session context.
2. Validate school/tenant identity.
3. Resolve the matching Student enrollment for that same session.
4. Return historical class, section and roll number.
5. Never silently substitute current Registry placement.
6. Preserve existing financial values and transaction behavior.
7. Avoid introducing cross-school or cross-session joins.
8. Preserve archived-session read-only behavior.

Assess whether the existing resolver can be reused safely or whether a separate bulk-query/helper is preferable.

Investigate potential N+1 database query risks for large fee lists and reports.

Do not implement the helper.
