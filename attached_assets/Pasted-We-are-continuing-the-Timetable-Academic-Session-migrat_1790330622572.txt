# 2. STUDENT TIMETABLE API REQUESTS

Trace every request made by Student Timetable.

At minimum inspect:

* `GET /api/student/timetable`
* any structure/bell/period request used by Student Timetable
* any other Timetable request made by the Student page

For every request determine:

* Does it send the selected Academic Session ID?
* Which header/transport is used?
* Does it use native `fetch`?
* Does it rely on a mutable global session header?
* Is the Session captured at request time?
* Can the request accidentally fall back to the active Session?
* Can the request return data from multiple Sessions?

Important:

The canonical Student behavior must be:

`selected Session → selected Session ID`

and only when no Session is selected:

`active Session → active Session ID`

If neither exists:

`NO TIMETABLE REQUEST`

Do not assume this is implemented. Verify it.

# 3. QUERY / CACHE ISOLATION

Inspect every React Query/query key used by Student Timetable.

Determine whether the Academic Session ID is part of the key.

Example:

BAD:
`["/api/student/timetable"]`

GOOD:
`["/api/student/timetable", sessionId]`

Check:

* timetable entries
* structure/bell data
* any related Timetable data

Determine whether Session A data can remain cached and appear when Student switches to Session B.

Also inspect invalidation after session switching or Timetable changes.

---

# 4. SESSION SWITCHING

Audit this exact scenario:

### Scenario A → B

1. Student opens Session A.
2. Student Timetable loads.
3. Student switches to Session B.
4. Timetable must immediately stop representing A.
5. B must load using B's Session ID.
6. A's response must not populate B's UI/cache.
7. No A data may remain visible as B data.
8. Any in-progress A request must not corrupt B.

Also test conceptually:

### B → A

The same protections must work in reverse.

Report PASS/FAIL with exact evidence.

---

# 5. FRESH ACADEMIC SESSION

Audit:

1. Create/select a brand-new Academic Session.
2. It has no Timetable data.
3. Student Timetable must show an empty/new timetable.
4. It must NOT show the previous Session's timetable.
5. No previous Session structure/bell data may appear.
6. No previous Session cache may leak into the new Session.

Because this project is in BUILDING/DEVELOPMENT phase, do not suggest recreating old data merely to hide a Session isolation problem.
