FIX 10A-1 — TEACHER EXAMINATION ADD MARKS: PREVENT ABOVE-100% GRADING CRASH

We have completed a read-only investigation of a Teacher Examination → Add Marks runtime crash.

IMPORTANT:
This is a narrowly scoped FRONTEND VALIDATION-ORDER FIX.

DO NOT change the shared grading engine.
DO NOT weaken grading validation.
DO NOT add fallback grades.
DO NOT clamp percentages.
DO NOT change database data.
DO NOT change schema or migrations.
DO NOT change session isolation.
DO NOT change Fix 4.
DO NOT change Fix 10A.
DO NOT change promotion, cumulative calculation, attendance, or any other Examination behavior.

==================================================
CONFIRMED ROOT CAUSE
==================================================

Teacher Examination → Add Marks currently calculates a grade before checking whether the entered mark exceeds Total Marks.

The current conceptual order is:

const pct = Math.round((val / maxMarks) * 100);
const g = computeGrade(pct, addMarksGradingRules);
const isOverMax = val > maxMarks;

If the teacher enters a mark greater than Total Marks, the percentage can become greater than 100.

Example:

mark > totalMarks
→ percentage = 193
→ computeGrade(193, valid 0–100 grading rules)
→ strict grading selector correctly throws:
   "No configured grading rule matches percentage 193."

The grading engine is behaving correctly.

The Add Marks UI is performing validation in the wrong order.

==================================================
EXPECTED BEHAVIOR
==================================================

For every student row in Add Marks:

1. Parse the mark.
2. Parse Total Marks.
3. Validate the mark BEFORE calling computeGrade().
4. If the mark is invalid:
   - below 0
   - above Total Marks
   - non-finite
   - otherwise invalid

   then DO NOT call computeGrade().

5. Show the existing controlled validation state/warning.
6. Do not display a grade badge for the invalid row.
7. Save must remain disabled while any mark is invalid.
8. Do not clamp the mark or percentage.
9. Do not invent a grade.
10. Do not modify the grading rules.

For valid marks:

0 <= mark <= Total Marks

the existing percentage calculation and strict configured grading policy must continue unchanged.

==================================================
IMPORTANT BOUNDARY BEHAVIOR
==================================================

These must remain valid:

0/20   → 0%   → D
6/20   → 30%  → D
7/20   → 35%  → C
12/20  → 60%  → B
16/20  → 80%  → A
20/20  → 100% → A

This must NOT crash:

21/20 → invalid input, no grade calculation

A value producing 193% must NOT crash.

It must instead produce the normal controlled invalid-mark state.

The important requirement is:

NO impossible percentage may reach computeGrade().

==================================================
IMPLEMENTATION GUIDANCE
==================================================

Find the Add Marks student-row rendering/calculation path where the code currently does approximately:

const pct = Math.round((val / maxMarks) * 100);
const g = computeGrade(pct, addMarksGradingRules);
const isOverMax = val > maxMarks;

Change the logic so validation occurs BEFORE grade selection.

Conceptually:

const isValidMark =
  Number.isFinite(val) &&
  val >= 0 &&
  val <= maxMarks;

const pct = isValidMark
  ? Math.round((val / maxMarks) * 100)
  : null;

const g =
  isValidMark
    ? computeGrade(pct, addMarksGradingRules)
    : null;

Use the project's existing validation conventions where appropriate.

Do not blindly copy this pseudocode if the surrounding code requires a slightly different implementation.

The key invariant is:

computeGrade() MUST NEVER receive a percentage outside 0–100 from Add Marks.

Also ensure maxMarks itself is valid before performing division.

Do not hide a genuine configuration error.

For example, if the selected class has no configured grading policy, preserve the existing controlled configuration behavior. Do not catch the error and silently assign a grade.

The fix is specifically for invalid student mark input occurring before grade selection.
