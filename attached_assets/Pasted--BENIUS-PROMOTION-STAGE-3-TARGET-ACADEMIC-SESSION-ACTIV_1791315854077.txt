# CORE PRODUCT CONTRACT

BENIUS placement architecture is:

```text
Student Registry
=
CURRENT placement

Academic Session Enrollment
=
placement for a specific Academic Session
```

Therefore when a new Academic Session becomes the school's ACTIVE session:

```text
that session's Active Enrollments
        ↓
become the CURRENT placement
        ↓
Student Registry synchronizes
```

Example:

Before activation:

```text
ACTIVE SESSION: 2026–27

Student Registry
MIS-0003 → Class 5/A, Roll 80

2026–27 Enrollment
MIS-0003 → Class 5/A, Roll 80

2027–28 Enrollment
MIS-0003 → Class 6/B, Roll NULL
```

Principal activates 2027–28.

After successful activation:

```text
ACTIVE SESSION: 2027–28

Student Registry
MIS-0003 → Class 6/B, Roll NULL

2026–27 Enrollment
MIS-0003 → Class 5/A, Roll 80   ← PRESERVED

2027–28 Enrollment
MIS-0003 → Class 6/B, Roll NULL ← PRESERVED
```

The Registry now reflects the newly active Academic Session.

# 3 — TENANT ISOLATION

The session being activated must:

```text
exist
AND
belong to authenticated school
```

Never trust request-supplied:

```text
schoolId
```

A Principal/Admin from School A must never activate School B's session or synchronize School B's Students.

Every Enrollment used for synchronization must be scoped to:

```text
authenticated school
+
target session
```

Every Student update must also be scoped to authenticated school.

---

# 4 — ACTIVATION SOURCE OF TRUTH

When Session B becomes active, Registry synchronization must use:

```text
Session B Enrollment
```

as the placement source.

Do NOT use:

- Promotion history target class
- Promotion decision
- current Student Registry class
- source-session enrollment
- latest enrollment regardless of session
- session name/year inference

The authoritative placement is:

```text
authenticated school
+
newly activated session
+
Student
+
Active Enrollment
```

---

# 5 — WHICH ENROLLMENTS SYNCHRONIZE

Only use target-session enrollments satisfying:

```text
enrollment.school_id = authenticated school
enrollment.session_id = session being activated
enrollment.status = Active
```

Then validate the associated Student belongs to the same school.

Do not use another school's Student.

Do not use inactive/cancelled/invalid Enrollment as current placement.

---

# 6 — STUDENT ACTIVE STATUS

Do NOT automatically reactivate an inactive Student merely because an Active Enrollment exists.

If:

```text
Student.is_active = false
```

do not change that status in Stage 3.

Do not silently turn them active.

For Registry placement synchronization, inspect the existing Student model and intended behavior.

Preferred safe rule:

```text
Active Student
+
Active target-session Enrollment
→ synchronize Registry placement
```

Inactive Students should remain inactive and should not be brought into live academic operations by activation.

Report how inactive Students are handled.

# 7 — STUDENTS WITHOUT TARGET ENROLLMENT

This is critical.

A school may contain an active Student who has no Enrollment in the newly activated session.

Do NOT guess their placement.

Do NOT copy their old Registry placement into the new session automatically.

Do NOT create an Enrollment during activation unless an existing explicit BENIUS business rule already requires it.

Preferred behavior:

```text
No Active target-session Enrollment
→ no Registry placement synchronization for that Student
```

But the activation flow must surface this clearly.

Before activation, calculate/report:

```text
Active Students:
Active target-session Enrollments:
Active Students missing target enrollment:
```

If missing target enrollments exist, inspect the existing product flow.

For safety, prefer preventing activation with a clear validation response if activating would leave current Registry inconsistent with the newly active session.

If this requires a product decision because current BENIUS semantics are ambiguous, STOP and report:

```text
PRODUCT DECISION REQUIRED — MISSING TARGET ENROLLMENTS
```

Do not invent placement.

# 10 — ROLL NUMBER

Stage 2 intentionally allows:

```text

```

Therefore Stage 3 must NOT invent one.



- auto-increment roll
- generate roll
- copy source roll

The newly active session's Enrollment is authoritative.

# 16 — TRANSACTION ATOMICITY

This is critical.

Do NOT allow:

```text
new session activated
BUT
only half of Student Registry synchronized
```

or:

```text
Registry synchronized
BUT
session activation failed
```

The core activation operation should be atomic.

Within the same DB transaction, where technically feasible:

1. lock/validate school session state;
2. validate target session;
3. validate target enrollments;
4. validate no blocking conflicts;
5. deactivate previous active session;
6. activate target session;
7. synchronize eligible Student Registry placement;
8. perform essential activation state writes.

If any essential synchronization fails:

```text
ROLL BACK
```

The previous active session and Registry placement should remain unchanged.

Do not leave partial activation.
