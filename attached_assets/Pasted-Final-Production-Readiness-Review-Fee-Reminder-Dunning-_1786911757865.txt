3. Exact automatic reminder logic

The automatic cron must use exact-day matching.

For a fee due on 20 August:

- 18 August → D-2
- 20 August → D0
- 23 August → D+3
- 27 August → D+7
- 3 September → D+14

No other automatic reminder should be generated.

The system must calculate this using IST calendar dates, not the Replit/server timezone.

The server may run in UTC, but reminder eligibility must always be based on India Standard Time.

4. IMPORTANT — missed reminder protection

The current implementation has a significant reliability limitation:

If the server is unavailable for the entire exact reminder day, the reminder can be permanently missed.

I do NOT want this behavior.

Implement a safe catch-up mechanism.

Example:

If D+7 was supposed to be sent yesterday but the server was unavailable, when the server comes back today it should determine whether the D+7 reminder was missed and safely send it.

However:

Do not send duplicate reminders.

Before sending a catch-up reminder, check the dunning history for that specific:

"feeRecordId + channel + stage"

If a successful reminder already exists, do not send it again.

The catch-up mechanism must work across:

- server restart
- Replit restart
- temporary outage
- deployment
- cron failure
- temporary database connection failure

Design this carefully so that catch-up does not accidentally send an old reminder weeks later.

7. API timeout protection

This must be fixed.

Currently provider "fetch()" calls do not have an explicit timeout.

A provider API hanging must NEVER block the entire dunning job indefinitely.

Implement a reasonable timeout using "AbortController" or equivalent.

For example:

- provider timeout: approximately 10–15 seconds
- after timeout → mark attempt as "failed"
- store a meaningful error
- continue with the next channel/fee
- release the advisory lock normally

A single MSG91 or SendGrid outage must never freeze the complete reminder engine.

It must be recorded as:

"failed"

with the provider's error message.

There must never be a false-positive "sent" record.

13. Deduplication must be stronger

The current application-level "sentSet" is good, but I want stronger protection.

Prevent duplicate automatic sends for:

"feeRecordId + channel + stage"

However, do not allow this to prevent legitimate retries after a failed attempt.

The desired behavior is:

- "sent" → never automatically send same stage/channel again
- "failed" → eligible for retry
- "simulated" → does not block real sending
- "skipped" → does not block real sending

Manual "Send Reminder" may intentionally override automatic deduplication, but this behavior must be clearly documented and visible to the admin.

14. Retry system

Implement a proper safe retry strategy.

A temporary provider/network failure should not permanently lose a reminder.

At minimum:

- timeout → retry
- network error → retry
- HTTP 429 → retry with backoff
- HTTP 5xx → retry with backoff
- HTTP 4xx configuration error → do not repeatedly hammer provider

Retries must have a maximum limit.

Do not create duplicate successful sends.

Use the dunning log to determine whether a successful send already happened.
