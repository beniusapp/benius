### Core rule

Every Timetable API operation must resolve exactly ONE Academic Session:

1. If a valid selected `x-view-session-id` (`H`) is supplied, use that Session.
2. Otherwise resolve the authenticated school's active Session (`A`).
3. If neither exists, reject the request.
4. Never pass `null`.
5. Never use an all-Sessions fallback.

For Teacher Timetable specifically:

**Selected Session H takes priority over active Session A for BOTH reads and writes.**

Do not use active Session A merely because an older Teacher batch route previously did so.

### Session resolution

Where a route performs multiple related Storage calls, resolve the Session ONCE and reuse the exact same Session ID.

Examples:

* lookup → delete
* lookup → update
* validation → save
* class entries → structure
* batch collision check → batch save/delete
* student entries → structure

Do not resolve different Sessions between calls in the same request.

### School isolation

Preserve and strengthen the existing authenticated-school checks.

For every request:

* authenticated school must be used
* selected Session must belong to that school
* Storage ownership validation must remain active
* never trust a client-provided school ID to select another school's Session

Pay particular attention to:

* `/api/timetable/teacher/:teacherId`
* shared timetable/structure routes

Do not weaken their existing authorization while adding Session handling.

### Archived Sessions

For mutations:

* selected archived/inactive Session → reject
* active Session → allow subject to existing authorization
* no selected Session → use active Session
* no valid Session → reject

Do not rely only on the middleware header check. Storage's inactive-session protection must remain the final server-side protection.

### Reads

They must never return Timetable data from multiple Sessions.
