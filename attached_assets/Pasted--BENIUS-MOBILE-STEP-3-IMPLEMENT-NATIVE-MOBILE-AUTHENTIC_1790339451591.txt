Implement a secure, server-issued authentication mechanism specifically for native mobile clients.

The mobile authentication mechanism must coexist with the existing web authentication.

# NON-NEGOTIABLE BENIUS RULES

---

## 1. MULTI-TENANT SCHOOL ISOLATION

BENIUS is permanently multi-tenant.

Every mobile authenticated identity must be server-derived.

The mobile client must NEVER be authoritative for:

* schoolId
* role
* permissions
* studentId
* teacherId
* adminId
* staffId

A client-supplied school ID must never grant access.

The backend must determine the authenticated user's school from the authenticated credential.

Every mobile API operation must remain constrained to that authenticated school.

Never allow cross-school access.

---

## 2. ACADEMIC SESSION ISOLATION

Academic Sessions are school-scoped.

The mobile application must eventually support:

Authenticated School
→ Available Academic Sessions
→ Selected Academic Session

A selected Academic Session must be verified by the backend as belonging to the authenticated school.

Do NOT trust a client-supplied Academic Session ID merely because it exists.

For session-sensitive operations, the backend must verify:

authenticated principal
+
authenticated school
+
selected Academic Session

The Admin → Exam Controller requirement is especially strict:

Every Exam Controller operation must be scoped to:

* authenticated school
* selected Academic Session ID

Previous-session operational data must never leak into a new session.

---

## 3. IST

All BENIUS application/business/display time handling must use:

`Asia/Kolkata`

Do not introduce device-local timezone behavior for BENIUS business dates.

---

## 4. WEB APPLICATION MUST CONTINUE WORKING

The current web application must remain operational.

Existing browser authentication must continue to work.

Existing web session cookies must continue to work.

Existing web login flows must continue to work.

Do not migrate web authentication to the mobile mechanism.

---

Create an additive server-side representation for mobile authentication sessions/credentials.

The design should support at minimum:

* unique mobile session/device identifier
* authenticated principal/user identity
* role
* schoolId
* hashed refresh credential
* refresh credential family/rotation identity
* createdAt
* lastUsedAt

# SERVER-SIDE PRINCIPAL

---

After successful mobile authentication, every request using the mobile access credential must resolve a server-side principal.

The principal should contain the minimum required information such as:

* principal/user ID
* role
* schoolId
* relevant entity ID
* mobile session/device ID
* credential issuance information

Do not trust role or school identity supplied by the mobile request body.

Do not trust role or school identity supplied through arbitrary headers.

---

# MOBILE AUTH MIDDLEWARE

---

Create dedicated middleware for mobile bearer authentication.

It should:

1. Read the Authorization header.
2. Validate the access credential.
3. Verify expiration.
4. Verify signature/authority if applicable.
5. Resolve the mobile session/device identity.
6. Verify that the mobile credential has not been revoked.
7. Resolve the authenticated BENIUS principal.
8. Resolve the principal's school from server-side data.
9. Attach the verified principal to the request.
10. Reject invalid credentials with HTTP 401.

Do not use:

`schoolId` from request body

as authentication authority.

Do not use:

`role` from request body

as authentication authority.

---

# REFRESH TOKEN ROTATION

---

Implement refresh rotation safely.

The intended lifecycle is:

Login
↓
Access Credential + Refresh Credential
↓
Mobile API requests use Access Credential
↓
Access Credential expires
↓
Refresh Credential submitted
↓
Server validates refresh credential
↓
Old refresh credential becomes invalid
↓
New refresh credential issued
↓
New access credential issued

Implement reuse detection where practical.

If a rotated refresh credential is reused, revoke the affected credential family/session appropriately.

Do not allow indefinite refresh-token reuse.

---

# LOGOUT

---

Mobile logout must revoke the server-side mobile credential/session.

After logout:

* existing access authority should no longer be accepted once the server-side revocation model requires rejection
* refresh credential must no longer work
* local SecureStore credentials must be cleared

Do not destroy the user's existing web browser session when mobile logout occurs.

Mobile logout and web logout must remain independent.

---

# PASSWORD CHANGE / ACCOUNT REVOCATION

---

Inspect existing password-change and account-revocation behavior.

Where an existing BENIUS password change or account deactivation requires invalidating authenticated sessions, integrate the mobile credential records into that revocation model where appropriate.

Do not weaken current revocation behavior.

Do not assume that changing a web session automatically revokes a mobile credential.

Do not leave indefinitely valid mobile refresh credentials after an account has been revoked.

# SECURITY REQUIREMENTS

---

The implementation must include protections appropriate for native mobile authentication.

At minimum:

### HTTPS expectation

Mobile authentication must require HTTPS outside local development.

Do not allow production credentials over HTTP.

### Credential secrecy

Never log:

* password
* PIN
* access credential
* refresh credential
* Authorization header

### Refresh credential storage

Store only a hash server-side.

### Expiration

Access credentials must be short-lived.

Refresh credentials must have an explicit expiration.

### Revocation

Support server-side revocation.

### Device/session isolation

A mobile session must be independently revocable.

### Tenant isolation

Every authenticated principal must remain school-bound.

### Role isolation

The server must determine role.

### Replay protection

Rotated refresh credentials must not remain reusable.
