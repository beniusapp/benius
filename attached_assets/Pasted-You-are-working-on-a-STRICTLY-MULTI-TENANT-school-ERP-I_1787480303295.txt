SECURITY REQUIREMENTS

This MUST NOT be implemented as a frontend-only password popup.

The password verification must be performed server-side against the currently authenticated admin account.

Do NOT:

- hard-code a password;
- compare the password in frontend JavaScript;
- store the password anywhere;
- store the plaintext password in logs;
- store the password in localStorage;
- store it in sessionStorage;
- put it in the URL;
- send it back to the browser;
- expose password hashes to the frontend.

Use the application's existing secure password-hashing/verification mechanism.

Do not introduce a second password system if the application already has a standard authentication/password verification service.

---

Multi-tenant requirement — CRITICAL

This application is STRICTLY MULTI-TENANT.

The verification must always operate within the currently authenticated administrator's identity and school/tenant context.

School A must NEVER be able to use this mechanism to access or modify School B's External Portal configuration.

Do NOT trust:

- school ID supplied by the browser;
- tenant ID supplied by the browser;
- arbitrary user ID;
- arbitrary admin ID;
- arbitrary External Portal record ID.

Resolve authorization from the authenticated server-side session/user context.

The backend must independently verify that the authenticated administrator has permission to manage the External Payment Portal for their own school.

---

Protect the backend, not only the UI

After implementing the UI verification, inspect every existing backend endpoint used by the External Payment Portal.

The actual configuration APIs must remain protected by normal:

1. authentication;
2. tenant/school authorization;
3. administrator permission checks.

The password verification must not become a substitute for authorization.

If the current External Portal API returns sensitive configuration data before verification, change only that access path so that protected configuration cannot be obtained simply by directly calling the API.

A user must not be able to bypass the password modal by manually calling the API.

Also protect configuration mutations appropriately.

For example:

- GET/view configuration → requires authenticated authorized admin + successful recent re-authentication where appropriate.
- SAVE/update configuration → requires authenticated authorized admin + appropriate authorization.

Do not weaken any existing authorization.

Re-authentication state

After successful verification, allow the administrator to use the External Portal settings without entering the password for every individual field interaction.

Use a short-lived server-recognized re-authentication state tied to the authenticated administrator/session.

It must:

- belong to the current authenticated admin;
- belong to the current tenant/school context;
- expire after a reasonable short period;
- not be transferable to another user;
- not authorize another school;
- not survive logout;
- be invalidated when the authenticated session ends.

Do not create a long-lived permanent “verified” flag.

If the application already has a secure recent-authentication/re-authentication mechanism, reuse it instead of creating another mechanism.

---

Session and tenant switching

Because this is a multi-tenant, academic-session-based application, verify that changing school/session context cannot accidentally reuse an old verification state.

A verification obtained for:

Admin A + School A

must not become valid for:

School B

or another authenticated user.

If tenant/session context changes, the protected External Portal access must be revalidated as necessary.
