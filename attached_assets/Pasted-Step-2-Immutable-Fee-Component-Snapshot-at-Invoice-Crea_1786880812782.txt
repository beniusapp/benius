2. AUTHORITATIVE SOURCE

For structure-based invoice generation, the source is:

fee_structures.breakdown

Its existing shape is:

Array<{
  name: string;
  purpose: string;
  amount: number;
}>

At invoice creation time, copy this data into:

fee_records.breakdown_snapshot

The snapshot must represent the exact component data that existed at invoice creation.

After that, the receipt will eventually read only the snapshot.

---

3. IMPORTANT — COPY, DO NOT REFERENCE

The invoice must receive an independent snapshot.

Do not store a reference to the original JavaScript array/object.

Do not mutate the source structure.

Conceptually:

const breakdownSnapshot = structure.breakdown
  ? structure.breakdown.map(component => ({
      name: component.name,
      purpose: component.purpose,
      amount: component.amount,
    }))
  : [];

Use the project's existing validation/type conventions.

The important requirement is that the database receives a snapshot of the values, not a live configuration object.

9. VALIDATION

Before writing a non-empty snapshot, validate the component data.

The validation must be conservative and must not change existing financial behavior.

Validate:

Component name

Every component must have a valid name.

If a component has an empty/missing name:

BLOCK creation of that invoice and return a clear validation error.

Do not silently create a fabricated name.

---

Component amount

Amounts must be finite numbers.

Reject:

NaN
Infinity
-Infinity

Reject negative component amounts.

Zero is allowed.

A zero amount may represent a legitimate placeholder component.

---

Purpose

"purpose" may be empty if the existing schema allows it.

Do not invent a purpose.

If missing, preserve it as an empty string or the existing canonical representation used by the application.

---

Duplicate names

Do not block invoice creation merely because two components have the same name.

Duplicates are an edge case.

If the existing project has an appropriate logging mechanism, a warning may be logged.

Do not introduce a new logging framework.

---

10. COMPONENT SUM

Do NOT require:

SUM(breakdown_snapshot.amount) === fee_records.amount

as a hard requirement.

This is intentional.

The forensic audit established that the existing database does not enforce:

SUM(fee_structures.breakdown.amount) = fee_structures.amount

Therefore existing fee structures may contain:

Components = ₹2,800
Fee amount = ₹3,000

or another difference.

Do NOT block invoice generation solely because of this mismatch.

The authoritative invoice amount remains:

fee_records.amount

The snapshot must faithfully preserve the configured component values.

If useful and consistent with the existing logging system, emit a warning when the sums differ.

But:

WARNING ONLY — NEVER BLOCK THE INVOICE.
