1. NO-NOTES REFUND / DISPUTE WEBHOOKS

Current gap

Some Razorpay "refund.*" or "payment.dispute.*" webhook payloads may not contain:

- "feeRecordId"
- school/tenant information in notes

The system must still safely process/retain these events when a trusted Razorpay identity can be resolved.

Required resolution order

For a signed and otherwise valid webhook:

First: Payment ID

If the webhook contains a Razorpay payment ID:

1. Find the existing tenant-scoped "payment_attempts" record by:
   - "razorpay_payment_id"
   - trusted tenant context
2. Resolve:
   - "school_id"
   - "student_id"
   - "fee_record_id"
   - "session_id"

If found, mark the event:

resolution_status = resolved
resolution_source = payment_id

Second: Order ID

If payment ID is unavailable or cannot resolve the attempt:

1. Use the Razorpay order ID.
2. Find the corresponding tenant-scoped payment attempt/order relationship.
3. Resolve the invoice and tenant if safely possible.

Mark:

resolution_status = resolved
resolution_source = order_id

Third: Payment record fallback

If appropriate and safely tenant-scoped, resolve through the existing "payment_records" relationship.

Mark:

resolution_source = payment_record

Fourth: Unresolved

If no safe relationship exists:

resolution_status = unresolved

Do not invent:

- school ID
- student ID
- invoice ID
- payment attempt
- order relationship

The event must never be attached to the wrong tenant or invoice.

2. IMPORTANT SECURITY REQUIREMENT

Do not weaken webhook HMAC verification.

The system must continue to verify the Razorpay webhook signature before trusting/persisting the webhook payload as an authenticated Razorpay event.

However, the lack of "feeRecordId" in the webhook notes must not automatically cause the signed event to be discarded.

A valid signed event may be retained as:

tenant resolved
invoice resolved

or:

tenant resolved
invoice unresolved

depending on what can safely be established.

Never cross-link a payment from School A to School B.

Add regression tests for:

- valid signed refund with no feeRecordId
- valid signed dispute with no feeRecordId
- payment-ID resolution
- order-ID resolution
- unresolved event
- cross-tenant payment ID
- cross-tenant order ID
- invalid HMAC
- valid HMAC + unresolved invoice

3. EVERY WEBHOOK DELIVERY MUST BE IMMUTABLE

This is the second and very important remaining gap.

A single retry counter on one webhook row is not sufficient for the required forensic audit.

We need to know about each actual delivery separately.

For example:

INV-00079

Webhook Delivery #1
Event: payment.captured
Received: 19:40:14
Provider Event Time: 19:40:12
HMAC: Verified
Result: Processed

Webhook Delivery #2
Event: payment.captured
Received: 19:40:18
Provider Event Time: 19:40:12
HMAC: Verified
Result: Duplicate

Webhook Delivery #3
Event: payment.captured
Received: 19:41:03
Provider Event Time: 19:40:12
HMAC: Verified
Result: Reconciliation

These must be three separate immutable delivery records.

Do not overwrite Delivery #1 with Delivery #2.

Do not merely increment:

retry_count = 3

and discard the individual delivery information.

6. DUPLICATE WEBHOOKS

Duplicate webhook deliveries must NOT create:

- duplicate payment attempts
- duplicate payment records
- duplicate receipts
- duplicate invoice payments

But they must create their own immutable delivery-history record.

Example:

Payment Attempt #4
    Captured

Webhook Delivery #1
    Processed

Webhook Delivery #2
    Duplicate

The payment attempt remains one attempt.

The webhook delivery history contains two deliveries.

This distinction is mandatory.
