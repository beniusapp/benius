1. STORED PROVIDER IDENTITY MUST OVERRIDE WEBHOOK NOTES
   ==================================================

This is the highest-priority security requirement.

When a signed Razorpay webhook arrives, NEVER trust Razorpay notes alone to determine the tenant/school if a stored provider identity already exists.

For tenant attribution, use this precedence:

1. Verified stored Razorpay payment ID → existing payment_attempt/payment/payment-record identity
2. Verified stored Razorpay order ID → existing order/attempt/payment identity
3. Only if no stored provider identity exists, use verified Razorpay notes/metadata
4. If the identity cannot be resolved unambiguously:
   - DO NOT guess the school
   - DO NOT attribute the webhook to a tenant based on conflicting notes
   - Retain the verified webhook delivery safely as UNRESOLVED
   - Record exactly why resolution failed
   - Do not expose it to another tenant

Critical security case:

If a webhook contains:

payment_id = pay_xxx
order_id = order_xxx
notes.school_id = SCHOOL_B

but the database already proves:

pay_xxx/order_xxx belongs to SCHOOL_A

then SCHOOL_A MUST win.

The notes MUST NOT be allowed to override the stored provider identity.

Likewise, if payment ID says SCHOOL_A but order ID says SCHOOL_B, treat this as a tenant/security mismatch.

Do NOT silently select either tenant.

Record the event as a security/reconciliation anomaly and keep it unresolved or quarantined according to the existing architecture.

The final tenant-resolution result must itself be persisted with the immutable delivery receipt, including:

- resolution_status
- resolution_source
- resolved_school_id when safely known
- provider_payment_id
- provider_order_id
- resolution_reason
- verified status
- provider event timestamp if available
- application receipt timestamp

The immutable delivery row must contain the FINAL safe resolution facts at INSERT TIME.

Do NOT insert an incomplete delivery row and later UPDATE it with the verification/resolution result.
