IMPORTANT:
THIS IS A CONTROLLED IMPLEMENTATION STEP.

The purpose of this step is ONLY to stop existing Teacher Self-Attendance records from being reinterpreted using the current shared Attendance Policy during READ operations.

DO NOT redesign Attendance Policy.

==================================================
CONFIRMED PRODUCT CONTRACT
==========================

The following decisions are already finalized:

1. Attendance policy has HISTORICAL SEMANTICS.

2. Existing Teacher Self-Attendance must preserve its STORED HISTORICAL STATUS.

   A later change to the school's shared Attendance Policy must NOT reinterpret
   an existing Teacher Self-Attendance record.

3. Attendance Policy remains SHARED ACROSS ACADEMIC SESSIONS.

   Do NOT create a separate Attendance Policy per Academic Session.

4. Student Attendance target remains the CURRENT SCHOOL TARGET.

   Do NOT change Student Attendance target behavior.

==================================================
CORE RULE BEING IMPLEMENTED
===========================

For an EXISTING Teacher Self-Attendance record:

```
persisted attendance.status
        ↓
   historical truth
        ↓
      READ
        ↓
   response/aggregate
```

A READ operation must NOT do:

```
persisted status
        ↓
current Attendance Policy
        ↓
   recomputeStatus()
        ↓
   different status
        ↓
   response
```

And a READ operation must NEVER do:

```
GET
  ↓
recompute
  ↓
UPDATE database
```

because of a current policy change.

The persisted status is authoritative for existing records when they are read.

==================================================
WHY THIS CHANGE IS REQUIRED
===========================

The Step 2L-5 audit found that current Teacher Self-Attendance READ paths can call
current-policy recomputation.

This can cause:

1. An archived record to display a status different from the stored status.
2. An active-session historical record to be recalculated using today's policy.
3. An active-session GET to write the recalculated status back to the database.
4. A current Teacher assignedClass to influence interpretation of an old record.
5. Historical counts, late flags, rates, streaks and KPIs to change after policy edits.

This violates the confirmed historical-status contract.

STEP 2 — CHANGE TEACHER TODAY READ
==================================

Inspect the Teacher Self-Attendance Today GET.

The current implementation may:

```

    ↓
resolve current policy
    ↓
recompute status
    ↓
possibly update database
    ↓

```

Change it so that an existing stored attendance row is read as-is.

Required behavior:

```
existing row
    ↓
stored status
    ↓
response
```

Do NOT call current Attendance Policy merely to determine the historical status
of an existing row.

Do NOT call recomputeStatus for this purpose.

Do NOT update the row merely because the current policy produces a different
result.

If the existing row has:

```

```

and the current policy would produce:

```
"Late"
```

the GET must still return:

```
"Present"
```

and must NOT update the database.

If the existing row has:

```

```

the GET must return:

```
"Half Day"
```

regardless of later policy changes.

If the stored status is:

```
"Leave"
```

return "Leave".

If the stored status represents an existing legitimate status according to the
current data model, preserve it.

Do not invent a new status vocabulary.
