# PHASE B — IMPLEMENT FINAL-DECISION EXECUTION

Proceed only after Phase A passes.

## B1. Authoritative final-decision resolver

Create or reuse one authoritative server-side function that resolves:

- Locked Teacher recommendation.
- Latest valid audited Web proposal, if any.
- Effective final Promote/Retain outcome.
- Valid target destination.
- Readiness status.
- Relevant actor/reason evidence.

Do not duplicate examination calculations.

Reuse the shared examination engine and existing promotion validation.

Do not use client-supplied override state as authority.

Reject stale proposals if underlying eligibility or locked recommendation has changed.

If a saved proposal is no longer valid, block execution with a clear conflict response requiring review.

## B2. Server-approved preview and readiness

Make the Web Principal Exam Controller preview and execution use the same authoritative final-decision resolver.

The Web must distinguish:

- Teacher recommendation.
- Saved Principal/Support Staff proposal.
- Validated final outcome.
- Pending or blocked readiness.
- Executed final outcome.

Never display a proposal as executed before the transaction commits.

If a Student is incomplete, missing marks, missing a valid locked ledger or has a stale decision, show Pending/Blocked.

Never silently fall back to the Teacher recommendation when an invalid or stale saved proposal exists. Require explicit resolution.

## B3. Execution transaction

Inside the execution transaction:

1. Authenticate and authorize the execution actor.
2. Validate the authenticated school.
3. Validate the explicit active source Academic Session.
4. Validate the exact source-session Student enrollment.
5. Validate the examination term.
6. Recompute or validate authoritative examination completeness.
7. Validate the locked Teacher recommendation.
8. Resolve the latest valid audited final proposal.
9. Validate the target Academic Session and destination.
10. Validate target class and section against school configuration.
11. Check for previous execution or conflicting target enrollment.
12. Apply the final outcome, not an untrusted client destination.
13. Prepare the target-session enrollment.
14. Persist final-decision history and mandatory audit evidence atomically.
15. Commit all related changes together.

If any validation fails, roll back the entire transaction.

Preserve idempotent retries for the exact same previously executed decision.

Reject conflicting repeated execution attempts.

Do not update `students.class`, `students.section` or `students.rollNumber` here.

## B4. Promote and Retain semantics

Preserve the existing configured promotion destination rules.

For Promote, prepare the validated destination class/section.

For Retain, prepare the valid retained class/section according to existing promotion rules.

Do not invent a new class, section or roll number.

If the correct destination cannot be derived unambiguously, block the operation and report the required configuration or owner decision.

Do not use the current Student Registry placement as a substitute for source-session enrollment.

## B5. Grace and legacy preservation

Do not introduce new Grace overrides.

Do not convert existing Grace records into Promote or Retain.

Preserve existing Grace semantics and historical decisions.

Unaudited legacy overrides must not silently control execution.

If an existing legacy override conflicts with the new audited decision, block and report rather than guessing.

## B6. Mobile compatibility

Mobile execution must continue using its existing Teacher-ledger-based contract.

Do not modify Mobile-specific files, endpoint payloads or authorization.

Shared helper changes must be backward-compatible.

Add regression tests demonstrating that Mobile does not consume Web-only audited proposals.

Do not assume unchanged Mobile files prove unchanged Mobile behavior.

## B7. Principal Analytics and history

After execution:

- Show the actual executed final outcome.
- Preserve the Teacher recommendation separately.
- Identify an applied override where authorized.
- Preserve actor/reason audit evidence.
- Avoid labeling an unexecuted proposal as final.

Use existing server-side result/history services where possible.

Do not expose internal Principal override or audit details through Student examination APIs.

Do not introduce a Student-facing promotion feature in this stage.
