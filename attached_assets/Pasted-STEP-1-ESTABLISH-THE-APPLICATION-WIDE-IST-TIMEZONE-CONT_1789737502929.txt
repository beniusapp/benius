Do NOT modify database schema.

APPLICATION REQUIREMENT — NON-NEGOTIABLE:

This is an Indian school MIS application.

The application's business/user-facing timezone is:

Asia/Kolkata

IST (UTC+05:30)

The application must NEVER depend on the server/container/browser timezone for Indian business dates or times.

1. CREATE ONE CLEAR APPLICATION-WIDE TIMEZONE CONTRACT

Use:

Asia/Kolkata

as the canonical application/business timezone.

If `shared/ist-time.ts` already defines:

SCHOOL_TIME_ZONE = "Asia/Kolkata"

keep and reuse that existing constant.

Do NOT create competing timezone constants.

2. RUNTIME TIMEZONE

Inspect the current Node.js/runtime configuration.

Determine whether setting:

TZ=Asia/Kolkata

at the application runtime level is safe with the current architecture.

IMPORTANT:

Before changing it, verify whether existing database code relies on:

SET TIME ZONE 'UTC'

or any UTC-based persistence convention.

The database currently uses UTC as its persistence convention.

DO NOT change:

SET TIME ZONE 'UTC'

Do NOT change timestamp storage semantics.

If an application-level TZ setting could alter legacy timestamp persistence behavior or cause data corruption/interpretation changes, STOP and report the conflict instead of implementing it.

If it is safe, configure the application runtime so local JavaScript date operations use Asia/Kolkata.

3. SCHEDULER TIMEZONE FOUNDATION

Inspect all cron/background scheduler definitions.

For every scheduler that represents a wall-clock business time, determine whether it currently depends on the process/server timezone.

Do NOT redesign the jobs yet.

For now, only establish a reliable mechanism for explicitly specifying:

Asia/Kolkata

for scheduler wall-clock execution.

Do NOT change the actual intended schedule times unless the current code clearly indicates the intended time.

Example:

If the existing job is intended to run at 01:00, preserve 01:00 but ensure that it means:

01:00 Asia/Kolkata

not server-local time.
