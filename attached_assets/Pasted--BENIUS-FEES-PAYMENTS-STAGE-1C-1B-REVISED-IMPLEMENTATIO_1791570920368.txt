## 2. APPROVED BUSINESS RULE

Historical placement must come from the enrollment matching:

**Authenticated School ID + Fee Record Student ID + Fee Record Academic Session ID**

For example:

Student: Ram Jaiswal

Academic Session 2026–2027:
- Enrollment: Class 1-A.

Academic Session 2027–2028:
- Enrollment: Class 2-A.
- Current Student Registry: Class 2-A.

When Principal Fees is viewing 2026–2027:

- Fee list displays Class 1-A.
- Class 1 filter includes the correct historical invoice.
- Class 2 filter does not include it merely because the current Registry says Class 2-A.
- Ledger CSV and PDF use the same historical placement.
- Payment PDF filters its linked invoice population using the same historical placement.

When viewing 2027–2028, the corresponding records use Class 2-A.

Apply this generically to all Academic Sessions.

Do not hardcode years, Students, classes or sections.

## 4. HISTORICAL ENROLLMENT RESOLUTION

Reuse the existing Stage 1C-1 historical placement resolver where suitable.

For bulk queries, implement a safe set-based SQL approach if needed.

Requirements:

- Match schoolId, studentId and feeRecord.sessionId.
- Use authenticated school context.
- Never use another school's enrollment.
- Never use another Student's enrollment.
- Never use another session's enrollment.
- Do not substitute current Registry placement.
- Do not guess missing placement.
- Do not create, update or delete enrollments.
- Do not backfill legacy data.
- Avoid N+1 queries.
- Avoid duplicate fee records from joins.
- Fail closed for duplicate or incomplete enrollment matches.

Historical placement is session-level placement, not an immutable invoice-issuance snapshot.

Do not change the existing active-session enrollment synchronization behavior.
