# ABSOLUTE ARCHITECTURE RULES

BENIUS is a **multi-school / multi-tenant School MIS**.

Tenant isolation is mandatory.

A Teacher from:

**School A must NEVER read, write, calculate, modify, or receive data belonging to School B.**

Every Teacher Academic Session operation must derive the school from the **authenticated Teacher identity**.

Never trust a client-supplied:

- schoolId
- teacherId
- class
- section
- session ownership

without server-side validation.

# REQUIRED SESSION BEHAVIOR

The foundation must distinguish between:

## GLOBAL

No Academic Session required.

Use for genuinely global Teacher data.

---

## SELECTED SESSION REQUIRED

A valid explicit selected Academic Session is required.

The session must:

- exist
- belong to the authenticated Teacher's school

Historical/inactive same-school sessions may be valid for READ operations where the module supports historical viewing.

---

## SELECTED OR ACTIVE SESSION

Only use this mode where existing Teacher product behavior genuinely requires active-session fallback.

Do NOT use fallback simply for convenience.

Future corrected session-sensitive Teacher pages should prefer explicit selected-session behavior.

---

## CURRENT SESSION WRITE

For operations that must only modify the current/active Academic Session.

Requirements:

- selected session must exist
- selected session must belong to Teacher's school
- selected session must be active/current according to existing BENIUS rules
- historical-session writes must fail

Do NOT silently redirect an attempted historical write into the active session.

---

# TEACHER ASSIGNMENT / MAPPING

Academic Session validation and Teacher authorization are NOT the same thing.

Example:

Teacher belongs to School A
+
Session X belongs to School A

does NOT automatically mean the Teacher may operate on every class/section/subject in Session X.

Later module corrections may need:

- Teacher class assignment
- section assignment
- subject assignment
- faculty mapping
- timetable assignment
- class teacher mapping

Step 1 should identify how these mappings currently work.

Do NOT globally invent new mapping rules.

Create the foundation so module-specific authorization can validate assignments where necessary.

---

# STUDENT PLACEMENT RULE

When a Teacher module operates on Students for a selected Academic Session, later corrections should normally derive historical Student placement from:

`enrollments`

using:

- authenticated Teacher school
- Student
- selected Academic Session

Do NOT assume `students.class` / `students.section` represent historical placement.

However, Step 1 should NOT rewrite individual Teacher modules yet.

Document this requirement for later steps.

---

# SESSION VALIDATION

For a session-aware Teacher request, validate:

1. Teacher is authenticated.
2. Teacher exists.
3. Teacher's school is resolved server-side.
4. Raw selected-session value is syntactically valid.
5. Academic Session exists.
6. Academic Session belongs to Teacher's school.
7. Operation mode permits active/inactive session.
8. Module-specific assignment validation can happen after session resolution.

---

# FAILURE BEHAVIOR

Fail closed.

Use consistent behavior.

Examples:

### No Teacher authentication
401

### Required session missing
400

### Malformed session ID
400

### Session does not exist
Do not leak useful cross-tenant information.

### Session belongs to another school
403

The response must not reveal sensitive information about the foreign school's Academic Session.

### Historical session used for current-only write
Reject clearly.

Do NOT silently fall back to active session.
