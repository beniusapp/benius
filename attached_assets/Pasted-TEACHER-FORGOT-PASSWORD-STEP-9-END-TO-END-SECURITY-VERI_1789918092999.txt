PART 4 — OTP SECURITY
==================================================

Verify:

1. OTP is six digits.

2. OTP is generated using cryptographically secure randomness.

3. OTP plaintext is not persisted in the database.

4. OTP plaintext is not written to logs.

5. OTP plaintext is not returned in API responses.

6. OTP expiry is enforced.

7. OTP is single-use.

8. Wrong OTP increments attempt count.

9. Attempt count is capped.

10. Correct OTP after maximum failed attempts is rejected.

11. Correct OTP before expiry succeeds.

12. OTP exactly at expiry boundary is rejected according to the implemented expiry rule.

13. OTP verification cannot be replayed.

14. Concurrent correct OTP submissions result in exactly one successful verification.

15. Concurrent wrong OTP submissions cannot exceed the configured maximum attempt count.

16. OTP verification cannot cross tenants.

Do not change the attempt limit or expiry values.

Verify against the existing implementation.

PART 5 — RECOVERY SESSION SECURITY
==================================================

Verify the server-side recovery session.

Test:

1. Forgot Password creates OTP_PENDING state.

2. OTP_PENDING contains only expected server-side identity/state.

3. OTP_PENDING does not contain resetToken.

4. OTP verification changes the state to PASSWORD_RESET.

5. PASSWORD_RESET contains the reset token only server-side.

6. Reset token is not returned to the browser.

7. Recovery session expires according to the existing TTL.

8. Expired recovery session cannot be used.

9. Malformed recovery session cannot be used.

10. Future-dated/backdated invalid state cannot be used if those protections exist.

11. Wrong recovery stage cannot call the wrong operation.

Examples:

PASSWORD_RESET state must not be usable for OTP verification.

OTP_PENDING state must not be usable for password reset.

12. Recovery state cannot be replaced by another teacher's state through browser-supplied identifiers.

13. Recovery session cannot cross school boundaries.

PART 6 — RESET TOKEN SECURITY
==================================================

Verify:

1. Reset token is cryptographically random.

2. Plaintext reset token is never persisted.

3. Database contains only the HMAC/hash representation.

4. Reset token is never returned to frontend.

5. Reset token is never stored in localStorage.

6. Reset token is never stored in sessionStorage.

7. Reset token is never put in URL/query parameters.

8. Reset token is not logged.

9. Reset token expiry is enforced.

10. Reset token cannot be reused after successful reset.

11. Wrong reset token cannot reset the password.

12. Reset token from Teacher A cannot reset Teacher B.

13. Reset token from School A cannot reset School B.

14. Concurrent password resets using the same valid reset state result in exactly one success.
