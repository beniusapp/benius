## 3. Correction A — Harden payment-to-invoice joins

For the Ledger payment-list read path, a linked invoice must be considered valid only when all of the following match:

- `payment_records.fee_record_id = fee_records.id`
- `payment_records.school_id = fee_records.school_id`
- `payment_records.student_id = fee_records.student_id`

The authenticated School ID must continue to scope the payment query.

Never accept a client-supplied School ID as authority.

### Required behavior

For a valid same-school, same-student invoice link:

- Preserve existing invoice-number display.
- Preserve payment amount.
- Preserve payment method.
- Preserve received date.
- Preserve existing authorized response fields.

For an invalid cross-school link:

- Do not expose the foreign invoice number.
- Do not expose foreign invoice metadata.
- Do not expose foreign Student information.
- Do not treat the link as verified.

For an invalid cross-student link:

- Do not associate another Student's invoice number with the payment.
- Do not treat the link as verified.
- Do not use that invoice's Academic Session for NULL-session fallback.

Preserve the payment's original stored `fee_record_id`; do not rewrite or delete it.

If the existing response includes the raw `feeRecordId`, inspect whether retaining that identifier for an invalid link would disclose a foreign invoice identifier. Prevent foreign invoice identifiers from being exposed in the response, while preserving legitimate payment identifiers and existing valid-link behavior.

Do not introduce new sensitive response fields.

## 4. Correction B — Verified NULL-session payment visibility

Current issue:

The Ledger payment list filters directly on `payment_records.session_id`.

This can omit legacy payments whose own session ID is NULL even though their linked invoice identifies the correct archived Academic Session.

Implement a narrow read-time fallback.

### Allowed fallback

A payment with `payment_records.session_id IS NULL` may appear in the selected Academic Session only if:

1. The payment belongs to the authenticated school.
2. The linked invoice exists.
3. The invoice belongs to the same school.
4. The invoice belongs to the same Student.
5. The invoice has a non-NULL Academic Session ID.
6. The invoice's session ID equals the selected Academic Session ID.
7. The selected Academic Session is authorized for the authenticated school.

Do not modify the stored payment session ID.

Do not automatically backfill it.

Do not treat NULL as global.

### Required result

Example:

School A
Student STU-101

Invoice:
- Academic Session 2026–2027.
- Amount ₹5,000.

Payment:
- Amount ₹5,000.
- `session_id = NULL`.
- Valid link to that invoice.
- Same School ID.
- Same Student ID.

When Ledger selects 2026–2027:

- Payment must appear in the Ledger payment list.
- Payment must not appear in 2027–2028.
- No stored record is changed.
- No financial amount is recalculated.
