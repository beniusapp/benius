BLOCKER 1 — WEBHOOK DELIVERY RECORDS MUST BE TRULY IMMUTABLE

The current implementation creates separate webhook delivery rows, but the processing outcome can still be updated on that same row after insertion.

That does NOT satisfy the forensic requirement.

Required architecture

A webhook delivery must behave as an immutable historical fact.

Once a delivery record is inserted:

«It must NEVER be updated or deleted.»

For example:

Delivery #1
Delivery #2
Delivery #3
Delivery #4

must each remain exactly as originally recorded.

Do NOT do this:

delivery_id = X
status = received

later:

delivery_id = X
status = processed

That destroys the original historical state.

---

Separate delivery receipt from processing outcome

If the application needs to know what happened while processing a delivery, separate the two concepts.

Immutable webhook delivery

Stores what was actually received:

- delivery ID
- event ID
- event type
- payment ID
- order ID
- refund ID
- dispute ID
- provider timestamp
- received timestamp
- signature verification result
- raw/safely retained payload reference
- tenant resolution result
- invoice resolution result
- delivery fingerprint
- original delivery metadata

This record must never change.

Immutable processing event/history

If processing changes over time, append another event instead of modifying the original delivery.

For example:

Webhook Delivery #1
    ↓
Processing Started
    ↓
Processing Failed
    ↓
Processing Retried
    ↓
Processing Succeeded

These must be separate immutable events/records.

The exact existing schema can be reused/extended if appropriate; do not create unnecessary duplicate architecture.

---

Database-level immutability

Do not rely only on application code.

The database must prevent ordinary:

UPDATE
DELETE

against immutable webhook delivery history.

Use the same append-only/immutability approach already implemented for lifecycle events.

If controlled tenant deletion requires cascading deletion, preserve the existing explicit cleanup mechanism rather than weakening normal immutability.

Normal application requests must not be able to modify or delete historical delivery rows.

IMPORTANT DISTINCTION

The final architecture must maintain three separate layers:

1. Payment attempt projection

Represents the current state of an individual payment attempt.

Example:

Attempt #2
payment_id = pay_xxx
outcome = failed

2. Immutable lifecycle events

Represents every observed lifecycle transition.

Example:

payment.failed
payment.authorized
payment.captured
refund.created
refund.processed

3. Immutable webhook deliveries

Represents every actual webhook delivery received from Razorpay.

Example:

Delivery #1
Delivery #2
Delivery #3

Never merge these concepts just to simplify the implementation.
