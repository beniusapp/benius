CONTEXT:

Stage SC-1 confirmed:

1. The From Teachers badge currently uses inboxData.length, which counts all teacher complaints, including Resolved records.

2. GET /api/student/complaints/inbox returns teacher-to-student complaints scoped to the authenticated Student, School, and selected Academic Session.

3. Opening a complaint currently displays its details but does not persist an individual read receipt.

4. The existing Student module-level notification cursor is separate and must remain unchanged.

5. The complaints table has no individual read/seen timestamp.

OBJECTIVE:

Introduce persistent, per-complaint read receipts so that:

- A new unread teacher complaint increases the From Teachers badge.
- Opening its details marks that complaint read.
- The unread badge decreases after successful acknowledgement.
- Previously read complaints remain read after logout, refresh, and login on another device.
- Resolved complaints remain visible in history.
- New complaints remain unread until opened.
- Read receipts cannot cross Student, School, or Academic Session boundaries.

PART A — DATA MODEL AND MIGRATION PREPARATION

Design the smallest safe persistent read-receipt model.

Prefer a dedicated receipt table rather than changing the existing complaint records or complaint status fields.

The model must:

- Identify the complaint using its existing stable primary key.
- Identify the authenticated Student.
- Scope records to the correct School and Academic Session.
- Store the first successful read timestamp.
- Prevent duplicate receipts for the same complaint and Student within the same School/Session.
- Use appropriate foreign keys and indexes consistent with existing BENIUS schema conventions.
- Preserve historical complaints and their statuses.
- Avoid modifying existing complaint data.

Prepare the schema definition and an explicit, reviewable migration file.

- DO NOT drop, rename, truncate, or rebuild existing tables.

PART B — BACKEND READ RECEIPT LOGIC

Prepare a secure authenticated endpoint to mark one teacher complaint as read.

Requirements:

1. Resolve Student identity from the existing authenticated server session.

2. Do not accept a Student ID or School ID supplied by the browser as authorization.

3. Resolve the selected Academic Session using the existing Student Portal session mechanism.

4. Verify the complaint belongs to the authenticated Student, School, and selected Academic Session.

5. Verify it is a valid teacher-to-student inbox complaint.

6. Reject unauthorized, deleted, cross-school, cross-student, or cross-session records.

7. Make the mark-read operation idempotent.

8. Store the read timestamp once; repeated opens must not create duplicate receipts or reset the original timestamp.

9. Do not change complaint status, resolution, comments, or complaint ownership.

10. Use existing backend authentication and error-response conventions.

PART D — FRONTEND BADGE CORRECTION

In student-complaints.tsx:

Replace the current total-record badge logic with the number of unread teacher complaints.

Expected behavior:

- New unread complaint → badge increases.
- Student opens complaint details → mark-read request is sent.
- Successful acknowledgement → badge decreases.
- Failed acknowledgement → badge remains unread and an appropriate retry/error state is available.
- Already-read complaint → no duplicate write.
- Resolved but unread complaint → remains unread until viewed.
- Resolved and read complaint → no unread badge.
- Complaint history remains visible regardless of read status.

Do not automatically mark every inbox item read merely because the student opens Conduct & Grievance.

Do not mark hidden or unopened complaint cards read.

Preserve the existing details drawer, comments, complaint statuses, and navigation.
