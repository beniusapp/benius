==================================================
J. OTP VERIFICATION STORAGE
==================================================

Create a transaction-safe storage method equivalent to:

verifyStudentPasswordResetOtp(
  challengeId,
  studentId,
  schoolId,
  otp,
  now?
)

Inside one database transaction:

1. Lock exact challenge FOR UPDATE.
2. Verify school.
3. Verify Student.
4. Verify purpose.
5. Verify not consumed.
6. Verify not already verified.
7. Verify OTP expiry.
8. Verify attemptCount < 5.
9. HMAC the supplied OTP.
10. Compare using timing-safe comparison.

Wrong OTP:

- increment attempt count atomically
- cap at 5
- never reveal remaining attempts
- fail generically

Correct OTP:

- generate a cryptographically secure reset token
- store only its HMAC/hash
- set verifiedAt
- set resetTokenExpiresAt = now + 15 minutes
- leave consumedAt null
- return the plaintext reset token ONLY to the trusted server-side caller

IMPORTANT:

The plaintext reset token must NEVER be:
- stored in DB
- logged
- returned from an HTTP endpoint in this step
- placed in URL
- placed in localStorage
- placed in sessionStorage

The later recovery-session implementation will hold it server-side.

==================================================
M. CONCURRENCY
==================================================

Correct OTP verification must be race-safe.

Two simultaneous correct OTP submissions against the same challenge:

- exactly one succeeds
- exactly one generates the reset token
- the other fails

Five-attempt enforcement must be race-safe.

Concurrent wrong OTP submissions must never produce:

- attemptCount > 5
- lost increments
- successful verification after the fifth failed attempt

Concurrent challenge creation for the same Student must leave only the newest challenge active.
