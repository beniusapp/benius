STEP 1 ONLY — FIX TEACHER EXAMINATION ROSTER

IMPORTANT ARCHITECTURE REQUIREMENT:
This application is MULTI-TENANT. School/tenant isolation is mandatory.

Do not make any change that could allow a teacher, student, admin, API request, query, or database operation from one school/tenant to access another school's data.

GOAL OF THIS STEP:

In the Teacher Portal → Examination → Add Marks screen, when a teacher selects:

- Academic Session
- Class
- Section
- Subject
- Exam Type

the student roster must be fetched LIVE from the Student Registry.

The Student Registry is the source of truth for the current active student list.

For roster display, DO NOT require an enrollment record.

CURRENT PROBLEM:

Teacher 6, School 1, selecting:

Class: 6
Section: A
Subject: Physics

currently shows:

"No students found"

because the current examination roster query depends on session-specific enrollments.

We want to remove that dependency for the roster only.

NEW ROSTER LOGIC:

For GET:

/api/examination/roster/:schoolId/:class/:section

the student query should use the Student Registry directly.

The effective filtering should be:

students.school_id = authenticated teacher's school
AND students.is_active = true
AND students.class = requested class
AND students.section = requested section

The roster must NOT require a matching row in enrollments.

The academic session must remain part of the Examination UI/context, but the roster itself should come from the live Student Registry.

MULTI-TENANT SECURITY:

This is critical.

Do NOT trust the schoolId supplied in the URL by itself.

The authenticated teacher must belong to the requested school.

The query must be tenant-scoped.

A teacher from School 1 must NEVER be able to request School 2's roster by changing schoolId in the URL.

Verify that:

authenticatedTeacher.school_id === requested schoolId

and then query students belonging to that same school.

Do not remove school authorization.

TEACHER AUTHORIZATION:

For THIS STEP, do not change the existing teacher authentication or authorization logic unless it is technically required to make the roster work.

In particular, do NOT accidentally remove:

isTeacherAuthorizedForAssignment(...)

or any existing school-level teacher security.

We will decide separately, in a later step, whether the business rule should become:

"Any authenticated teacher belonging to the school can add marks."

Do NOT make that authorization-policy change in this step.

SUBJECT:

Subject should NOT be used to filter the student roster.

Physics, Mathematics, English, etc. should not change which students belong to Class 6/A.

Subject remains Examination context only.

ACADEMIC SESSION:

Do NOT remove Academic Session from Examination.

The Examination module must continue to have academic-session context because marks/results are historical and must ultimately be associated with an academic session.

However, do NOT use the enrollment table as a prerequisite for displaying the live student roster in this step.
