# BENIUS — TEACHER PORTAL RED-DOT NOTIFICATION
# IMPLEMENTATION STAGE

Implement the Teacher Web Portal red-dot notification feature based on the completed audit and the CONFIRMED product rules below.

DO NOT perform another architecture redesign.

---

# 1. EXACT MODULES

Add red notification dots ONLY to these Teacher Dashboard modules:

1. Noticeboard
2. Complaints
3. Leave
4. Approval Center

DO NOT add dots to any other Teacher module.

---

# 2. CORE MEANING OF THE DOT

The dot means:

> New relevant activity has occurred since this Teacher last opened this module.

It does NOT mean:

> There are still pending/unresolved items.

Example:

```text
3 Student Leave Requests exist
        ↓
Teacher sees Leave 🔴
        ↓
Teacher opens Leave
        ↓
🔴 clears immediately
        ↓
Teacher processes NONE of the requests
        ↓
Returns to Dashboard
        ↓
NO 🔴
        ↓
A new Student submits another Leave Request
        ↓
Leave 🔴 appears again
```

This distinction is mandatory.

---

# 3. CLEARING RULE

When the Teacher opens one of these modules:

- Noticeboard
- Complaints
- Leave
- Approval Center

the corresponding dashboard red dot must clear immediately.

The Teacher does NOT need to:

- open an individual Notice
- open an individual Complaint
- approve/reject a Leave
- approve/reject a profile
- process every pending item

Opening the MODULE is enough.

Persist the seen state so it remains cleared after:

- returning to Dashboard
- refresh
- logout/login

until genuinely newer qualifying activity occurs.

---

# 4. STATE SCOPE

Persistent state must be:

```text
School
+ Teacher
+ Academic Session
+ Module
```

Therefore:

```text
Teacher A opens Leave
→ only Teacher A's Leave dot clears

Teacher B
→ unaffected
```

And:

```text
Teacher opens Noticeboard in 2026–2027
→ clears only 2026–2027 Noticeboard state

2025–2026
→ independent state
```

Use the explicitly selected Academic Session.

Never silently substitute the active session.

# 6. ACTIVITY CURSOR

Use deterministic activity cursors.

Cursor must contain enough information to safely order activity, conceptually:

```text
timestamp
+ source type
+ source record ID
```

Persist monotonically.

An older mark-seen request must never move the Teacher's cursor backwards.

DO NOT use:

`server now()`

as the seen point.

---

# 7. RACE-CONDITION PROTECTION

Example:

```text
Dashboard observed Leave Request A
        ↓
Teacher clicks Leave
        ↓
Student submits Leave Request B simultaneously
```

Opening Leave must mark only through:

**Leave Request A's observed cursor.**

Request B must remain newer and therefore still be capable of showing 🔴.

Use the same safe observed-cursor principle already established for Student dots.

---

# 8. NOTICEBOARD — CONFIRMED RULE

The Noticeboard red dot should trigger for a NEW Notice that is actually visible to the Teacher in the Noticeboard module.

This includes eligible Notices from:

- Teacher/Admin feed
- Student-targeted Notice feed visible in the Teacher's Student tab

Use the EXISTING Noticeboard visibility rules.

Do not expand visibility.

---

# 9. NOTICEBOARD — SELF-CREATED NOTICE

A Notice created by the CURRENT Teacher must NOT trigger that same Teacher's red dot.

Example:

```text
Teacher A creates Notice
→ Teacher A: NO new dot because of own Notice
```

If Teacher B is legitimately allowed to see that Notice under existing visibility rules:

```text
Teacher B
→ Noticeboard 🔴
```

Use existing:

- `createdById`
- `creatorRole`

and existing visibility rules.

Do not guess identity from display names.

# 21. DIRECT MODULE OPEN

Do not rely only on Dashboard-card clicks.

- Noticeboard
- Complaints
- Leave
- Approval Center

### Dashboard-card entry

### Direct module entry

Use the latest qualifying cursor known from the module/state request associated with that entry.

Do NOT blindly save `now()`.

---

# 22. OPTIMISTIC CLEARING

When Teacher opens a module with a dot:

1. Clear the dot immediately in Web UI.
2. Persist the observed cursor.
3. Navigate/open module.
4. Keep state cleared if persistence succeeds.

If persistence fails:

invalidate/refetch server state so the UI does not permanently pretend the notification was cleared.

# 24. MARK-SEEN API

`POST /api/teacher/module-dot-state/seen`
