---

AUTHENTICATION REQUIREMENT

Web and Mobile do NOT need to authenticate in exactly the same way.

Keep the concept:

WEB

HTTP-only cookie / server session

MOBILE

Bearer access token / refresh token

But after authentication, both mechanisms should resolve to a common trusted authenticated identity.

Conceptually:

Web Cookie

→ Authentication Layer
/
Mobile Bearer Token

        ↓

Authenticated principal:

- user ID

- role

- school ID

- Teacher/Student/Admin identity as applicable
  
        ↓

Same authorization/business logic.

The business layer should NOT need separate rules simply because the request came from Web or Mobile.

TENANT ISOLATION

Any future shared API must preserve strict multi-tenancy.

Authenticated School A user:

→ School A resources only.

School A:

→ School B resources = REJECT.

Never trust client-supplied:

- schoolId
- teacherId
- studentId
- role

as authorization.

Derive trusted identity and tenant from authentication/server-side records.

---

ACADEMIC SESSION

Session-sensitive shared APIs must preserve:

- explicit selected Academic Session
- school ownership of session
- selected-session reads
- active-session writes
- historical sessions strictly read-only
- no silent active-session fallback
- selected-session Student enrollment where required

SHARED ROUTE VS SHARED SERVICE

OPTION A — SAME API ROUTE

Web and Mobile call the exact same endpoint.

Example:

"POST /api/teacher/attendance"

The endpoint supports both cookie/session and bearer authentication.

OR:

OPTION B — SEPARATE ENTRY ROUTES, SHARED SERVICE

Web and Mobile retain separate HTTP routes/authentication adapters, but both call the exact same internal business service.

Example:

Web route ──┐
→ AttendanceService
Mobile route┘

Business rules must not be duplicated.
