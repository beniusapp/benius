TEACHER AUTHENTICATED PASSWORD CHANGE — STEP 10A
RACE-SAFE SECURITY REMEDIATION

Step 10 was completed and was BLOCKED by one confirmed, production-reachable security defect:

POST /api/teacher/change-password
    → storage.updateTeacherPassword()

The confirmed vulnerability is a stale authenticated password-change request that can overwrite a password established by the secure Forgot Password recovery flow.

==================================================
CONFIRMED VULNERABILITY
==================================================

Current vulnerable sequence:

1. Teacher has an authenticated session.
2. Teacher starts POST /api/teacher/change-password using the current password.
3. Request verifies the current password.
4. Request remains in flight before the final password update.
5. Teacher completes the secure Forgot Password flow.
6. Forgot Password reset commits a new password.
7. Recovery revokes existing Teacher sessions.
8. The already-running /api/teacher/change-password request resumes.
9. updateTeacherPassword() unconditionally updates the password by userId.
10. The stale request can overwrite the password established by recovery.

The affected implementation currently lacks the necessary race protection.

==================================================
OBJECTIVE
==================================================

Secure the authenticated Teacher password-change path so that:

A stale authenticated password-change request can NEVER overwrite a newer password established by:

- Forgot Password recovery
- another authenticated password change
- another valid credential mutation

The password-change operation must be atomic with respect to concurrent credential mutations.

Tenant isolation must remain enforced.

Existing secure Forgot Password behavior from Steps 1–9 must remain unchanged.

==================================================
PART 4 — ATOMIC PASSWORD MUTATION
==================================================

Replace the vulnerable unconditional password update with an atomic transactional operation.

The exact implementation may use row locking or a compare-and-swap strategy, but it must satisfy ALL of the following.

### Required properties

A. Password verification and credential mutation must have a well-defined concurrency boundary.

B. A newer password reset must not be overwritten by an older in-flight password-change request.

C. Concurrent password changes must have deterministic single-winner behavior.

D. A stale password-change request must fail rather than overwrite newer credential state.

E. The mutation must be tenant-bound.

F. The mutation must update password state atomically.

G. mustChangePassword changes must occur atomically with the password update.

Do not use an unconditional final update by userId after verifying an old password outside the transaction.

==================================================
PART 5 — CURRENT PASSWORD VERIFICATION
==================================================

The authenticated Teacher must prove knowledge of the current password.

However, verification must be race-safe.

Preferred safe design:

1. Begin database transaction.
2. Lock the canonical Teacher user row with an appropriate row lock.
3. Re-read the current password hash while holding the lock.
4. Validate:
   - user exists
   - school matches authenticated school
   - role is Teacher
   - account is active according to canonical active state
5. Verify the supplied currentPassword against the password hash currently held by the locked row.
6. Check authentication/revocation authority as required by the existing session-revocation design.
7. Perform the new password hash/update while the row remains protected.
8. Update mustChangePassword atomically.
9. Commit.

This ordering is important.

Do not:

- verify the old password using a stale hash
- release the row lock
- then unconditionally update the password

==================================================
PART 6 — RECOVERY RESET RACE
==================================================

The critical race is:

Authenticated password change
VS
Forgot Password reset

The implementation must ensure that the two operations cannot silently overwrite one another.

Use the existing recovery transaction/row-lock behavior as the compatibility reference.

If both operations target the same canonical user row:

- they must serialize safely
- whichever mutation commits first establishes the new password state
- the stale competing operation must re-read current state and fail safely
- no operation may silently overwrite a newer password

Do not change the accepted recovery reset implementation unless strictly required.
