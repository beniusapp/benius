# VERY IMPORTANT — SHARED SCHOOL DATA

Support Staff must operate on the SAME school-owned data that Principal/Admin uses.

Example:

```text
Support Staff — School A
Teacher Registry granted
        ↓
Adds Teacher
        ↓
School A shared Teacher data
        ↓
Principal/Admin sees same Teacher
```

There must NOT be separate Support Staff registry data.

The same applies to:

- Faculty Mapping
- Teacher Registry
- Student Registry

---

# TENANT ISOLATION

This is NON-NEGOTIABLE.

Support Staff belongs to one authenticated school.

Example:

```text
Support Staff — School A

School A Teachers       ✅
School A Students       ✅
School A Faculty Mapping ✅

School B Teachers       ❌
School B Students       ❌
School B Faculty Mapping ❌
```

All reads and writes must derive/validate school ownership from the authenticated server-side identity.

Do NOT trust client-supplied:

- schoolId
- teacherId
- studentId
- mapping IDs

without validating ownership.

An object ID belonging to School B must never allow School A Support Staff to read or mutate that object.

---

# TEACHER / STUDENT DEACTIVATION

Support Staff with the corresponding parent grant must be able to deactivate same-school records exactly according to the existing Principal/Admin business rules.

But do NOT bypass:

- school ownership
- existing validation
- dependency checks
- existing password/PIN/security confirmation requirements, if genuinely part of the Principal workflow

Do NOT try to resolve Support Staff as an Admin using the negative compatibility `userId`.

If Principal authentication logic currently assumes an Admin `users.id`, adapt the authorization safely for the authenticated Support Staff identity rather than using `-staffId` as an Admin ID.

---

# NEGATIVE SUPPORT STAFF ID

The previous audit found Registry operations that could fail because older Web routes attempted to use:

`userId = -staffId`

as though it were an Admin `users.id`.

Correct this where necessary for these three modules.

DO NOT:

- create a fake Admin
- convert Support Staff into Admin
- write negative Support Staff IDs into Admin foreign keys
- bypass tenant checks
- falsely attribute actions to Principal

Use the authenticated:

- positive `staffId`
- role = `support_staff`
- authenticated school

where appropriate.

---

# ACTOR ATTRIBUTION

When Support Staff performs actions such as:

- teacher registration
- teacher edit/deactivation
- student registration
- student edit/deactivation
- Faculty Mapping changes

the operational data remains owned by the SCHOOL.

Where BENIUS records actor/audit information, preserve the actual actor as Support Staff.

Prefer existing role-aware audit infrastructure:

```text
Actor:
positive staffId
role = support_staff

Owner:
authenticated school
```

Do not falsely record Principal/Admin as the actor.
