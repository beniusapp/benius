# BENIUS — PROMOTION STAGE 2

## EXPLICIT TARGET ACADEMIC SESSION + TARGET ENROLLMENT

This is an IMPLEMENTATION task.

Stage 1 is complete:
- strict source-session enforcement
- tenant isolation
- historical read-only protection
- source-session decision/history scoping

Stage 1B is complete:

Now implement **Stage 2 only**.

---

# STAGE 2 PRODUCT CONTRACT

Promotion must represent movement:

```text
SOURCE Academic Session
        ↓
TARGET Academic Session
```

Example:

```text
Source Session:
2026–27 ACTIVE

MIS-0003
Class 2/A
Roll 3
```

Promotion decision:

```text
Target Session:
2027–28

Target Class:
3

Target Section:
A
```

After Promotion execution, while 2026–27 remains active:

```text
Student Registry
→ Class 2/A, Roll 3
→ UNCHANGED

2026–27 Enrollment
→ Class 2/A, Roll 3
→ UNCHANGED

2027–28 Enrollment
→ Class 3/A
→ CREATED/PREPARED
```

Promotion must **NOT** immediately make the future placement current.

---

# CRITICAL CHANGE FROM CURRENT BEHAVIOR

Current Stage 1 Promotion still directly updates:

```text
students.class
students.section
students.idCardPendingReissue
```

Stage 2 must stop changing current Student placement during future-session Promotion.

Specifically:

```text
students.class
students.section
students.roll_number
```

must remain unchanged when Promotion is preparing a target-session enrollment.

The source-session enrollment must also remain unchanged.

Stage 3 will later synchronize Student Registry current placement when the target Academic Session becomes active.

Do NOT implement Stage 3 now.

---

# PERMANENT PLACEMENT MODEL

BENIUS placement architecture is:

```text
Student Registry
=
CURRENT Student placement

Academic Session Enrollment
=
Student placement for a particular Academic Session
```

Therefore:

```text
Promotion into future Session
=
create/prepare future Enrollment
```

NOT:

```text
Promotion
=
immediately rewrite current Student Registry
```

# TASK 1 — EXPLICIT TARGET ACADEMIC SESSION

Promotion execution must now have:

```text
sourceSessionId
targetSessionId
```

Source Session continues to come from the validated BENIUS selected-session context established in Stage 1.

Target Session must be explicit.

Do NOT infer target session from:

- current active session
- session name/year text
- next database ID
- class
- term
- Student profile
- most recently created session

The user/Promotion flow must explicitly identify the intended target Academic Session.

---

# TASK 2 — TARGET SESSION VALIDATION

Before Promotion execution, validate:

```text
target session exists
AND
target session belongs to authenticated school
AND
target session != source session
```

The source session must remain the valid writable/current source session according to Stage 1 rules.

The target session may be a **future/draft/inactive same-school Academic Session**, because Promotion preparation occurs before activation.

Do NOT require the target session to already be active.

Reject:

```text
missing target session
foreign-school target session
source == target
nonexistent target session
invalid lifecycle target
```

Do not silently substitute another session.

# TASK 6 — EXISTING TARGET ENROLLMENT

Handle three cases explicitly.

## Case A — No target enrollment

Create it.

```text
2027–28
Student X
3/A
→ CREATE
```

## Case B — Existing matching target enrollment

If the existing enrollment represents exactly the same intended target placement:

```text
same school
same Student
same target session
same class
same section
same roll where applicable
same valid status
```

treat the operation safely/idempotently.

Do NOT create a duplicate.

Do NOT fail simply because the exact desired enrollment already exists if it can safely be recognized as the same prepared result.

## Case C — Existing conflicting target enrollment

Example:

```text
Promotion wants:
2027–28 → 3/A

Existing enrollment:
2027–28 → 3/B
```

Do NOT overwrite it silently.

Reject with an explicit conflict such as:

```text
409 TARGET_ENROLLMENT_CONFLICT
```

Return enough safe information for the Admin to understand that the Student already has a different target-session placement.

Do not expose sensitive cross-school information.

# TASK 11 — PROMOTION OUTCOMES

Use the actual supported BENIUS Promotion outcomes found in the audit.

Do not create a target enrollment for a Student who is not supposed to advance unless the existing product semantics explicitly require an enrollment in the target session.

At minimum carefully distinguish the actual existing behavior for:

```text
Promoted
Retained
Grace Pass
Fail / Repeat
```

The audit found that some statuses currently collapse into retain behavior in the Admin UI.

Do NOT silently redefine examination policy in this task.

Instead:

1. preserve existing decision semantics where clear;
2. map only genuine advancement outcomes to target placement;
3. if retained/repeat Students need target-session enrollment in the same class for the new Academic Session, implement that only if supported by existing intended behavior;
4. otherwise report the ambiguity rather than inventing policy.

The important principle is:

```text
Target enrollment
=
the Student's intended placement in the target Academic Session
```

not automatically "next class" for every Student.
