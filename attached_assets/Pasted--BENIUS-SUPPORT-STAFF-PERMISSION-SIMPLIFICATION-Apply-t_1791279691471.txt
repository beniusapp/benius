# SIMPLE AUTHORIZATION RULE

For EACH of these five modules:

## Parent module GRANTED

Support Staff gets the complete normal operational functionality available to Principal/Admin inside that module.

## Parent module NOT GRANTED

Support Staff gets ZERO access:

- dashboard tile hidden
- direct URL blocked
- protected APIs rejected
- no read/write/action access

The parent module checkbox is the authorization boundary.

---

# 1. PERFORMANCE ANALYTICS

When granted:

Support Staff gets the complete normal Principal/Admin Performance Analytics functionality.

This includes normal viewing/filtering/reporting/analytics functionality available inside the module.

Preserve:

- authenticated school isolation
- Academic Session scoping
- examination/session rules

Support Staff of School A must never access School B analytics.

---

# 2. AUDIT LOGS

When granted:

Support Staff gets the normal Principal/Admin Audit Logs viewing functionality.

IMPORTANT:

Audit Logs remain an audit/history module.

Granting Audit Logs does NOT allow Support Staff to modify, delete, rewrite or manipulate audit history if Principal/Admin cannot normally do so.

Support Staff should see the school's appropriate audit records using the same normal module behavior as Principal/Admin.

Preserve school/session scoping where applicable.

---

# 3. VISITOR LOG

When granted:

Support Staff gets the complete normal Principal/Admin Visitor Log operational functionality, including the normal:

- active visitors
- visitor history
- check-in
- check-out
- other existing Visitor Log operations

Preserve tenant isolation.

School A Support Staff must only operate on School A visitors.

Do not allow a manipulated visitor ID, school ID or request value to operate on another school's record.

Preserve existing session rules where applicable.

---

# 4. ID CARD GEN

When granted:

Support Staff gets the complete normal Principal/Admin ID Card Generation functionality.

This includes the normal search/generation/reissue/print functionality that exists inside the module.

Support Staff must operate only on records belonging to their authenticated school.

School A Support Staff must never generate/reissue/access ID cards using School B records.

---

# 5. ASSETS & INVENTORY

This includes the existing normal:

- delete

and other existing operational actions inside the module.

Preserve authenticated school ownership.

School A Support Staff must never view/create/edit/delete School B assets.

# IMPORTANT — FULL ACCESS LIKE PRINCIPAL

“Full access like Principal” means:

> Normal operational functionality inside the granted module.

It does NOT mean Support Staff becomes an Admin.

Do NOT bypass:

- school/tenant isolation
- Academic Session isolation
- historical-session read-only rules
- server-side validation
- data integrity rules
- normal module business rules

Support Staff remains a separate Support Staff actor.

# ACTOR ATTRIBUTION / NEGATIVE ID

The previous shared-data audit found some actor-attribution and negative Support Staff ID problems, particularly around Visitor Log and Assets.

While enabling full module access, DO NOT write `userId = -staffId` into a foreign-key field that expects a real Admin `users.id`.

Do NOT falsely record a Support Staff action as though the Principal personally performed it.

Where the existing architecture already supports Support Staff actor attribution, preserve/use it.

If proper attribution cannot be safely implemented without a larger schema/business-logic change, do NOT invent a workaround.

Report the limitation instead.

The operational school data must still belong to the authenticated school.
