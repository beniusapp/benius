# CORE UX

Expected behavior:

```text
New relevant activity for Teacher
        ↓
Teacher Dashboard
        ↓
Relevant module shows 🔴
        ↓
Teacher opens that module
        ↓
Dot disappears immediately
        ↓
Seen state persists
        ↓
Refresh/relogin keeps it cleared
        ↓
Another NEW relevant activity
        ↓
Dot appears again
```

This is a MODULE-LEVEL red dot.

Do NOT design:

- per-item red dots
- notification counts
- notification center
- push notifications
- email notifications
- popup notifications

unless an existing count must remain untouched.

---

# IMPORTANT CLEARING RULE

When the Teacher opens the module, the dashboard dot should disappear.

The Teacher does NOT need to:

- open every individual item
- approve/reject every item
- resolve every complaint
- read every Notice

just to clear the dashboard red dot.

The red dot means:

> "Something new has happened in this module since I last opened it."

It does NOT mean:

> "There are still unresolved/pending items."

These concepts must remain separate.

# VERY IMPORTANT — PENDING VS NEW

Do not confuse:

**pending**

with:

**new since last opened**

Example:

Teacher has 3 Student Leave Requests.

Teacher opens Leave.

🔴 disappears.

Teacher does NOT process the requests.

Teacher returns to Dashboard.

There should still be:

NO RED DOT.

The requests are still pending, but they are no longer NEW to that Teacher.

Then another Student submits a Leave Request:

🔴 returns.

This rule applies to all four modules.

# RACE CONDITION

Use the same safe principle as Student dots.

Do NOT recommend blindly saving:

`server now()`

when the Teacher opens a module.


`timestamp + source record ID`

or another deterministic cursor.
