==================================================
NON-NEGOTIABLE PROJECT REQUIREMENTS
==================================================

1. MULTI-TENANCY
Every Attendance operation must be strictly isolated to the authenticated school/tenant.

Authenticated school/tenant context is authoritative.

Never trust browser-supplied:
- schoolId
- tenantId
- teacherId
- studentId
- session ownership

to establish tenant ownership.

No Attendance read, write, calculation, correction, history, analytics, summary, or synchronization may cross schools.

2. ACADEMIC SESSION ISOLATION
Attendance is Academic-Session-specific.

Every Attendance operation that reads, writes, calculates, summarizes, corrects, or displays Attendance must use the selected/validated Academic Session where applicable.

Switching Academic Session must isolate the Attendance data.

A previous Session's Attendance must never leak into another Session.

3. STUDENT REGISTRY
Student Registry is global/current master data.

It must NOT reset, recreate, or become session-specific merely because an Academic Session changes.

Historical Attendance must remain readable even when a historical student no longer exists in the current Student Registry.

4. ENROLLMENT
Enrollment is NOT an Attendance gate.

Attendance must not require current Enrollment merely to allow Attendance marking.

For historical Attendance identity:
- selected-session Enrollment may provide identity when available
- otherwise Attendance snapshot/history data must preserve the historical identity

Do not introduce Enrollment restrictions.

5. FACULTY MAPPING
Faculty Mapping must NOT restrict Attendance marking.

Any authenticated teacher belonging to the school may mark Attendance according to the existing Attendance workflow.

Do not introduce class/subject assignment restrictions.

6. WORKING-DAY RULE
The canonical working-day rule from Step 2J is:

For a PARTICULAR:
- school
- Academic Session
- class
- section

a working Attendance day exists when at least one Attendance record exists for that exact class + section + date, and the date is within the selected Academic Session start/end boundaries.

Therefore:
- Attendance in Class 7 must NOT make the same date applicable to Class 6.
- If 20 of 30 students have Attendance records, the date is applicable and the remaining 10 are Missing.
- If no Attendance record exists for the class/section/date, that date is not applicable.
- Sunday/holiday does NOT automatically exclude the date if Attendance exists for that class/section.
- Calendar events are NOT the Attendance denominator authority unless existing code already uses them for a separate legitimate purpose.

7. ATTENDANCE STATUS WEIGHTS
The canonical Student Attendance calculation from Step 2I is:

Present = 1.0
Late = 1.0
Approved Leave = 1.0
Halfday / half_day = 0.5
Absent = 0
Unknown = 0
Missing / not marked = 0 and remains distinguishable from explicit Absent.

Student/Admin/Teacher Student Attendance calculations must use the same authoritative calculation.

8. TIMEZONE
Application Attendance business dates and timestamps must consistently use:
Asia/Kolkata / IST.

DATE-only Attendance dates must not accidentally pass through JavaScript Date timezone conversion.

Instants/timestamps must use the canonical project IST utilities.

9. HISTORICAL READS
Historical Attendance must use historical class/section/student identity correctly.

Current Student Registry values must not incorrectly rewrite historical Attendance identity.

10. ATTENDANCE HISTORY
Historical Attendance must remain readable.

Historical records must not become editable merely because the user switches to a previous Academic Session.

11. ADMIN / TEACHER / STUDENT CONSISTENCY
Admin, Teacher, and Student Attendance surfaces must use the same authoritative Attendance records and calculation rules.

They must not silently use different denominator or status logic.

12. TEACHER SELF-ATTENDANCE
Teacher self-attendance must remain isolated by:

authenticated teacher
+ authenticated school
+ selected Academic Session
+ attendance date

Legacy NULL-session rows must not be included in new Session-scoped operations.

SPECIAL CHECKS
==================================================

Explicitly verify these scenarios:

1. Same date, same school, different classes:
   Class 6 Attendance must not affect Class 7 working-day denominator.

2. Same student, same school, different Academic Sessions:

3. Historical student:
   Student exists in old Session but no longer exists in current Registry.

4. Partial marking:
   Some students marked, others not marked.
   Marked date is applicable; unmarked students are Missing, not Absent.

5. Explicit Absent:
   Must remain distinguishable from Missing and contribute zero attendance.

6. Approved leave:
   Verify the existing Attendance behavior exactly as currently designed.
   Do not invent new behavior.

7. Sunday/holiday:
   Verify that the Step 2J rule is actually what the code uses.

8. Same teacher, same date, different self-attendance Sessions:
   Must remain isolated.

9. Legacy NULL-session self-attendance:
   Must remain isolated from new Session-scoped operations.

10. Cross-school:
   Identical student/teacher/date/session-like inputs from another school must never expose or mutate data.

11. Session switching:
   Frontend query/cache identity must include Session wherever Attendance data is Session-specific.

12. Historical read-only behavior:
   Verify that previous-session Attendance cannot be modified through current Attendance marking/correction paths unless the existing design explicitly permits it.
