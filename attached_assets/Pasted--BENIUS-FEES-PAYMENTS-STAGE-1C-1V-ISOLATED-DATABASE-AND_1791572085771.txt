The owner authorizes Stage 1C-1V strictly for verification of the already implemented Stage 1C-1 and Stage 1C-1B changes.

## 3. PHASE A — ISOLATED DATABASE PREFLIGHT

Before running database-backed tests, determine whether a suitable isolated PostgreSQL environment already exists.

An earlier BENIUS examination testing stage used a disposable local PostgreSQL environment. You may inspect whether a safe equivalent is available, but do not assume that the earlier database is still present or authorized for this Fees verification.

Verify:

1. Database host and port.
2. Database name.
3. Database user.
4. Whether it is a dedicated disposable test database.
5. Whether it contains only synthetic test data.
6. Whether its connection settings are independent of Development and Production.
7. Whether all test processes use the isolated connection.
8. Whether migration or reset commands can target only this database.
9. Whether application processes, background workers, payment gateways and external services are disabled or mocked.
10. Whether cleanup can be restricted to test-owned resources.

Do not print passwords, connection secrets or sensitive credentials.

Do not use the existing application's default database URL without positively verifying its destination.

Do not use a database merely because its name contains "test".

Do not create, reset, migrate, truncate or seed any database until its isolation is established.

If an isolated database is unavailable, report BLOCKED for database-backed verification. Continue only with safe non-database checks.

- Payment-side NULL Session ID.
- Invalid payment-to-invoice link.
- Multiple payment attempts.
- Fallback payment records.

All fixtures must remain isolated from real school data.

## 5. PHASE C — HISTORICAL PLACEMENT VERIFICATION

Verify that placement is resolved using:

Authenticated School ID + Fee Record Student ID + Fee Record Academic Session ID.

Test:

1. Correct Class/Section for each session.
2. No fallback to current Registry placement.
3. No cross-school placement leakage.
4. No cross-Student placement leakage.
5. No cross-session placement leakage.
6. Missing enrollment displays "Historical placement unavailable".
7. NULL-session records do not inherit current placement.
8. Incomplete placement fails closed.
9. Duplicate enrollment ambiguity fails closed.
10. No duplicate invoice rows from placement joins.

Do not modify enrollment data in the existing application environment.
