# BENIUS — STUDENT PORTAL RED NOTIFICATION DOTS
# IMPLEMENTATION

Implement the Student Web Portal red-dot notification feature based on the completed architecture audit and the confirmed product decisions below.

This stage is:

**STUDENT WEB PORTAL ONLY**

Mobile remains FROZEN.

Teacher Portal notification dots are NOT part of this stage.

Do NOT deploy.

---

# CONFIRMED PRODUCT RULE

Add red notification dots ONLY to these four Student Dashboard modules:

1. Homework
2. Classwork
3. Noticeboard
4. Complaints

DO NOT add this feature to any other Student module.

---

# EXPECTED BASIC BEHAVIOR

```text id="notifbasic"
New relevant activity
        ↓
Student Dashboard
        ↓
Relevant module shows 🔴
        ↓
Student opens that module
        ↓
Dot disappears immediately
        ↓
Seen state persists
        ↓
No dot after refresh/relogin
        ↓
New relevant activity later
        ↓
Dot appears again
```

---

# CONFIRMED SCOPE

Notification state must be:

**School + Student + Academic Session + Module**

Therefore:

Student A opening Homework must NOT clear Student B's Homework dot.

Opening Homework in Session A must NOT clear Homework state for Session B.

Each Academic Session has independent module-seen state.

---

# HISTORICAL ACADEMIC SESSIONS

Historical Academic Sessions may have their own module-seen state.

Writing notification/read-state metadata is allowed because it does NOT mutate historical academic content.

Do NOT modify:

- historical Homework
- historical Classwork
- historical Notices
- historical Complaints
- historical Enrollments

Historical academic content remains read-only.

`notice_reads`

and existing individual Notice unread/count behavior.

DO NOT remove it.

**Teacher/Admin-side Complaint Note**

visible to that Student.

Use the existing Complaint Notes actor/author role.

# COMPLAINT EVENTS THAT MUST NOT TRIGGER DOT

Student creates Complaint:

NO DOT.

Student adds their own Complaint note:

NO DOT.

Status-only change:

NO DOT for this stage.

Resolution/status change without a Teacher/Admin note:

NO DOT.

We are deliberately NOT building Complaint event/history infrastructure in this stage.

Do not change Complaint status architecture.

---

# COMPLAINT VISIBILITY

A Teacher/Admin note can trigger a dot only if:

- Complaint belongs to authenticated school
- Complaint belongs to selected Academic Session
- Student is authorized to see/participate in that Complaint under existing rules
- note belongs to that Complaint
- note author role qualifies

Do not expose another Student's Complaint activity.

---

# PERSISTENT MODULE-SEEN STATE

The audit confirmed no suitable generic persistent state currently exists.

Add the minimum persistent state required.

Conceptually one row should represent:

```text id="seenmodel"
school
student
academic_session
module
seen activity cursor
```

Allowed module keys ONLY:

- homework
- classwork
- noticeboard
- complaints

Use an appropriate unique identity equivalent to:

```text id="seenunique"
school
+
student
+
academic session
+
module
```

Do not create per-item notification records.

Do not create a general notification center.

---

# ACTIVITY CURSOR

Use a reliable cursor representing the newest visible activity.

Prefer:

**timestamp + record ID tie-breaker**

rather than timestamp alone.

This is important if two records have identical timestamps.

Examples:

Homework:
`createdAt + homeworkId`

Classwork:
`createdAt + classworkId`

Noticeboard:
`createdAt + noticeId`

Complaints:
`complaintNote.createdAt + complaintNoteId`

Use the existing timestamp storage convention consistently.

Do NOT use IST date strings as ordering cursors.

IST is for business/display date interpretation.

Activity ordering should use reliable instants/timestamps.

---

# RACE-CONDITION REQUIREMENT

DO NOT mark the module seen using blind:

`server now()`

Example:

```text id="racecase"
Dashboard observes latest Homework A
        ↓
Student clicks Homework
        ↓
Teacher creates Homework B almost simultaneously
```

Student opening Homework must mark seen only through:

**Homework A's observed cursor**

Homework B must remain newer than the saved cursor and therefore still be able to trigger 🔴.

---

# DASHBOARD STATE API

Implement the smallest authenticated Student Web API needed to retrieve the four module states.

Conceptually:

`GET /api/student/module-dot-state`

Return for each module:

- hasNewActivity boolean
- latest visible activity cursor needed for safe marking

Do NOT return unnecessary content.

Do NOT add counts.

Student identity must come from authentication.

School identity must come from authenticated Student.

Selected Academic Session must use the existing Student session context/header and be validated against that school.

---

# MARK-SEEN API

Implement the smallest endpoint needed to persist module seen state.

Conceptually:

`POST /api/student/module-dot-state/seen`

Input should contain only what is necessary, such as:

- module
- observed activity cursor

Do NOT accept Student ID or school ID as authorization input.

Derive them server-side.

Validate module against the four allowed module keys.

Validate the selected Academic Session through existing Student session resolution.

Never allow Student A to update Student B's state.

---

# FIRST-TIME BEHAVIOR

IMPORTANT:

When no module-seen row exists yet:

If relevant activity exists in the selected Academic Session, treat it as NEW and show 🔴.

This means the Student initially sees the dot for existing relevant activity until they open the module.

After opening:

seen cursor is saved.

Dot stays cleared until newer activity exists.

---

# MODULE OPEN / CLEAR BEHAVIOR

When Student clicks a dashboard module card that has a dot:

1. Clear the dot immediately in Web UI.
2. Send the observed latest cursor to mark-seen API.
3. Navigate/open the module.
4. Persist the state.

If persistence fails:

Do not silently permanently lose notification state.

Invalidate/refetch appropriately so server truth can restore the dot.

---

# IMPORTANT — OPENING MODULE DIRECTLY

A Student might enter Homework/Classwork/etc. without clicking the Dashboard card.

The feature should still behave logically.

When the Student successfully opens one of the four module pages, mark that module seen through the latest activity cursor that is actually known/returned for that module.

Do not require Dashboard navigation as the only way to clear the dot.

Avoid duplicate unsafe mark calls.

---

# DASHBOARD REFRESH

Refresh module-dot state:

- on Dashboard load
- selected Academic Session change
- returning/focusing Dashboard
- after mark-seen mutation

A modest polling interval comparable to the existing Notice behavior is acceptable.

Do NOT introduce WebSocket/SSE architecture just for this feature.

Do not overengineer.

---

# ACADEMIC SESSION SWITCHING

Dot state is session-specific.

Example:

```text id="sessionscope"
2026–27 Homework
Student opens
→ cleared for 2026–27

Student switches to 2025–26
→ 2025–26 Homework state evaluated independently
```

Never silently use active session when another selected session is being viewed.

---

# NOTICE COUNT VS RED DOT

Keep existing individual Notice unread count behavior.

The new module dot and existing Notice count have different meanings:

Red dot:
> New Notice activity since I last opened Noticeboard.

Existing Notice unread count:
> Individual Notices not yet marked read under existing Notice behavior.

Do not merge these concepts.
