==================================================
TENANT BINDING
==================================================

The transaction must enforce:

challenge.schoolId = supplied schoolId

AND

users.schoolId = supplied schoolId

AND

teachers.schoolId = supplied schoolId

AND

teachers.userId = users.id

AND

users.role = "teacher"

AND

users.isActive = true

The password update must therefore be explicitly constrained by:

userId + schoolId

and must additionally verify the Teacher relationship.

A Teacher from School A must never be reset through a School B challenge.

Do not rely on client-provided tenant information.

The supplied schoolId is expected to come from trusted server-side recovery state in the future.

==================================================
CHALLENGE REQUIREMENTS
==================================================

The transaction must require:

- exact challenge ID
- exact user ID
- exact school ID
- matching resetTokenHash
- verifiedAt IS NOT NULL
- consumedAt IS NULL
- resetTokenExpiresAt >= current time

The reset token must be compared using the existing secure HMAC/timing-safe mechanism where appropriate.

Do NOT store or accept a plaintext reset token in the database.

The function should receive the appropriate secure representation consistent with the existing Admin implementation.

==================================================
ATOMICITY
==================================================

Everything must occur in ONE database transaction.

Conceptually:

BEGIN

1. Lock/read the challenge securely.

2. Verify challenge identity and security state.

3. Verify the linked Teacher/user belongs to the same school.

4. Verify role = teacher.

5. Verify active user.

6. Verify reset-token HMAC.

7. Verify OTP was already verified.

8. Verify reset token has not expired.

9. Atomically consume the challenge.

10. Update the user's password using userId + schoolId.

11. Set teachers.mustChangePassword = false.

12. Consume any remaining active password-reset challenges for the same user + school.

COMMIT

If ANY validation fails:

ROLLBACK

No password update must occur.

No challenge must be partially consumed.

==================================================
CONCURRENT RESET PROTECTION
==================================================

The implementation MUST prevent two concurrent reset requests from both successfully changing the password using the same challenge.

Inspect the existing Admin transaction and use the same proven database locking/conditional-update pattern where appropriate.

Required behavior:

Request A + valid challenge
Request B + same valid challenge concurrently

Exactly ONE may succeed.

The other MUST fail because the challenge has already been consumed.

This must be enforced by the database transaction, not merely by JavaScript checks.
