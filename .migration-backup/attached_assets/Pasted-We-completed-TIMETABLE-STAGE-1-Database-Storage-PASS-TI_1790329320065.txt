# 1. SESSION MUST BE THE IDENTITY OF THE ADMIN TIMETABLE

The selected Academic Session must be the explicit identity of the Admin Timetable page.

Use the canonical selected Session from the existing Admin Session View context.

Rules:

* selected Session H is authoritative when selected
* active Session A is only the fallback when no selected Session exists
* do not invent another Session-selection mechanism
* do not use mutable global state as a substitute for the selected Session

Where possible, capture the resolved Session ID for each query/request rather than reading a mutable value later.

---

# 2. FIX ALL TIMETABLE QUERY KEYS

Add the resolved Academic Session ID to every Admin Timetable query key that represents Session-owned data.

At minimum:

### Class-view

Current:

`[endpoint, class, section]`

Change conceptually to:

`[endpoint, sessionId, class, section]`

### Structure

Current:

`[endpoint, class]`

Change conceptually to:

`[endpoint, sessionId, class]`

### Status

Current:

`[endpoint]`

Change conceptually to:

`[endpoint, sessionId, ...relevant class/section identity if applicable]`

Do not blindly add Session IDs to genuinely school-global data such as the teacher list.

The purpose is:

Session A cache ≠ Session B cache.

---

# 3. REQUEST MUST USE THE SAME SESSION AS THE QUERY KEY

This is very important.

Do not create a situation where:

* query key says Session A
* request header sends Session B

The Session ID captured for the query must be the same Session ID sent to the API.

For every Timetable request:

* use the selected Session when available
* otherwise use the active Session
* if there is no resolved Session, do not make the Timetable request

This applies to:

* class-view
* structure
* status
* batch save
* structure save
* publish

---

# 4. FIX PUBLISH — HIGH PRIORITY

The current Publish request uses native `fetch()` without the selected-session header.

Replace that with the existing session-aware client transport/helper.

Publish MUST explicitly target the currently resolved selected Session.

Expected:

Admin selects Session B
→ clicks Publish
→ request carries Session B
→ server publishes Session B only.

Do not rely on the server's active-session fallback for Publish.

Do not create a new transport mechanism.

---

# 5. FIX TIMETABLE DRAFT CROSS-SESSION LEAK — HIGH PRIORITY

Current problem:

Admin makes unsaved changes in Session A → switches to Session B → A's draft remains.

This must be prevented.

The safest preferred behavior is:

### When Academic Session changes:

Clear:

* timetable slot drafts
* pending `_delete` entries
* dirty timetable state
* unsaved structure changes
* dirty structure state
* any open Timetable editor/popover state

Do NOT carry unsaved changes from Session A into Session B.

Do not attempt to merge drafts between Sessions.

---

# 6. ALSO PROTECT AGAINST A STALE SAVE

Clearing on session switch is required, but also add a small defensive guard.

A save operation must not submit a draft if that draft belongs to a different Session from the current resolved Session.

If the existing draft structure can safely be changed to include its originating `sessionId`, do so minimally.

Expected:

```text
Draft created in Session A
Current Session = A
→ Save allowed

Draft created in Session A
Current Session = B
→ Save must NOT submit A draft to B
```

If the draft is already cleared synchronously on Session switch, the guard is still preferred where it can be implemented without unnecessary refactoring.

Do NOT introduce a large state-management redesign.

---

# 7. FIX STRUCTURE DRAFT CROSS-SESSION LEAK — HIGH PRIORITY

The same protection applies to period/bell structure.

When Session changes:

* clear dirty structure rows
* clear structure dirty state
* clear local structure edits
* ensure the next structure display comes from the newly selected Session

A dirty structure originating from Session A must never replace Session B's structure.

If a structure save occurs:

* it must use the current Session
* it must save only the current Session's structure

---

# 8. SESSION SWITCH CLEANUP

When Academic Session changes:

1. clear timetable drafts
2. clear pending deletes
3. clear structure drafts
4. close timetable editor/popover if appropriate
5. reset dirty state
6. ensure queries use the new Session ID
7. ensure old Session data cannot remain as the active editor state

Do not unnecessarily reset unrelated Admin page state.

Class/section can remain selected if that is safe.

# 10. QUERY INVALIDATION

Make invalidation Session-aware.

After successful batch timetable save/delete:

invalidate/refetch the current Session's:

* class-view
* relevant status query

After successful structure save/delete:

invalidate/refetch the current Session's:

* structure
* class-view, because class-view includes structure information

After Publish:

refresh the current Session's status.

Do not invalidate unrelated Sessions.

Do not invalidate all Timetable Sessions unnecessarily.

# 11. NO-SESSION / REQUEST FAILURE HANDLING

Do not treat a missing Session or failed Timetable request as a genuine empty timetable.

If there is no resolved Session:

* do not make the Timetable API request
* show/use the existing loading/empty/error mechanism appropriately
* do not create drafts against a null Session

If a Timetable request returns a non-OK response:

* preserve the existing error handling pattern if available
* do not silently convert the failure into valid empty Timetable data

Do not redesign the application's global error system.
