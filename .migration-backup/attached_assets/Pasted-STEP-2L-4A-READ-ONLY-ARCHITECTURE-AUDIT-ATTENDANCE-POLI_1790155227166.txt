==================================================
PROJECT CONTEXT / ALREADY-FINALIZED ATTENDANCE RULES
==================================================

This is a strict multi-tenant school MIS.

1. Every school is a separate tenant.
2. Attendance data must never cross school/tenant boundaries.
3. Attendance is Academic-Session-specific.
4. Historical Attendance must remain readable when an older Academic Session is selected.
5. Student Registry is global/current and must never be reset/recreated merely because an Academic Session changes.
6. Historical Attendance class/section identity must use selected-Session historical identity:
   - selected-Session Enrollment first;
   - historical Attendance snapshot fallback.
7. Enrollment is NOT an Attendance prerequisite.
8. Faculty Mapping is NOT an Attendance restriction.
9. Attendance working-day authority is already finalized:
   A working Attendance day for:
     SCHOOL + ACADEMIC SESSION + CLASS + SECTION
   exists when at least one Attendance record exists for that exact
   class/section/date and the date is within the selected Session start/end.
10. Attendance status weights are already finalized.
11. Attendance business dates are IST / Asia-Kolkata date-only values.
12. Student Attendance now uses the shared selected Academic Session as its Session authority.
13. Student Monthly approved-leave Session isolation has already been fixed.
14. Archived Teacher self-attendance GET status-healing persistence has already been fixed:
   - active Session may persist canonical healing;
   - archived Session may recalculate only for the response and must not modify DB.
15. These decisions MUST NOT be changed during this audit.

==================================================
CURRENT STEP 2L-4 FINDINGS
==================================================

The previous read-only audit confirmed:

A. Student historical Attendance records, working-day calculations,
   and percentages are correctly Session-scoped and use historical
   class/section identity.

B. Student policy endpoint is NOT historically safe:

   GET /api/student/attendance-policy

   currently resolves policy using:

   student.class

   which is the current Student Registry class.

C. attendance_policies has no session_id and is currently modeled as
   school-wide/shared configuration.

D. Teacher self-attendance historical status recalculation can use
   the current active policy and current teacher assignedClass.

E. Admin Student Attendance target resolution can omit the viewed
   class and selected Session.

F. The Attendance policy engine itself receives:

   policies
   targetRole
   className

   and does not receive:

   school
   academicSession
   section
   Attendance date
   policy version/effective date

G. Existing Session creation/copy logic reportedly classifies Attendance
   policy as:

   "shared across all sessions"

This audit must now determine whether that "shared across all sessions"
behavior is an intentional product/design rule or merely an implementation
choice that has not been revisited.

PART 4 — CRITICAL QUESTION: WHAT IS THE AUTHORITATIVE MEANING OF POLICY?
==================================================

Determine from the existing implementation what Attendance policy actually means.

There are two fundamentally different possible meanings:

MODEL A — CURRENT SCHOOL POLICY

The policy is a current school-wide rule.

Example:
- School changes late threshold from 15 minutes to 10 minutes.
- The new policy immediately applies to future Attendance processing.
- Historical Attendance may be recalculated/displayed under the current rule.

MODEL B — HISTORICAL POLICY

The policy is the rule that applied to a particular Academic Session/time period.

Example:
- Session 2024–25 had one late threshold.
- Session 2025–26 has another.
- Historical Session 2024–25 must continue using its historical policy.

Determine which model the CURRENT APPLICATION actually behaves like.

Do not decide which model is better.
Do not recommend one yet.

Report concrete evidence.
