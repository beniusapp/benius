GOAL

Establish ONE authoritative, shared, testable calculation engine/contract for Teacher Portal → Examination results.

The engine must use the policy belonging to the relevant school/session.

Conceptually:

    School's marks/data
             +
    School's configured Examination policy
             +
    School's grading rules
             +
    School's pass percentage/rules
             ↓
    ONE authoritative calculation engine
             ↓
    Examination result

School A and School B may have different policies.

The engine must NOT contain hardcoded School A/School B rules.

Instead, it must receive the applicable school's configured policy as input.

MULTI-TENANT REQUIREMENT

This is mandatory.

The calculation engine must never mix data or policy between schools.

For a calculation:

    authenticated teacher school
            ↓
    selected/validated academic session
            ↓
    that school's policy
            ↓
    that school's students/scores
            ↓
    calculation

Do not allow School A data to be calculated with School B policy.

IMPORTANT SCOPE FOR THIS FIX

The purpose of this step is primarily to establish the single calculation brain and its contract WITHOUT changing the current calculation behavior yet.

Do NOT attempt to fix all existing calculation inconsistencies in this step.

Specifically, DO NOT yet change:

- 33% vs 35% vs configurable pass thresholds
- absent vs missing behavior
- promotion fail-count interpretation
- cumulative weighting behavior
- rounding differences
- negative marks
- fractional mark handling
- total marks validation
- attendance calculation
- Faculty Mapping authorization
- Enrollment requirements
- Student Registry roster logic
- score uniqueness
- session isolation fixes
- tenant/security fixes outside what is strictly necessary for the calculation input boundary
- UI redesign
- School Setup policy redesign

Those will be separate later fixes.

AUTHORITATIVE ENGINE

Create or establish one shared calculation module/service for academic Examination result calculations.

Use a clear name appropriate to the existing architecture, for example:

    ExaminationCalculationEngine

or another equivalent name if the repository conventions indicate a better choice.

The engine should be pure/testable as much as practical.

It should NOT directly fetch arbitrary database data.

Instead, calculation inputs should be supplied to it.

The engine should be responsible for calculation, while route/storage/UI layers remain responsible for retrieving and validating data.

MINIMUM INPUT CONTRACT

Define a clear input contract representing:

- school context / schoolId where appropriate
- academic session context/sessionId
- student
- exam scores for the student
- applicable Examination policy
- applicable grading rules
- applicable pass percentage/rule configuration

Use the repository's existing types/configuration structures where practical.

Do not create duplicate policy formats if an existing policy structure already exists.

MINIMUM OUTPUT CONTRACT

The authoritative calculation result should have a clear structure capable of representing:

- subject result
- subject percentage
- subject pass/fail status
- grade
- term result / term average
- cumulative/annual result where configured

It must also be possible to represent states that the existing implementation already distinguishes, such as:

- scored
- missing
- absent
- incomplete

Do NOT change how these states behave yet unless necessary to establish the contract.

PRESERVE CURRENT POLICY CONFIGURATION

The engine must read/use the existing school's configured policy structure.

Example:

School A:

    passPercentage = 35
    grading rules = School A rules
    exam weights = School A weights

School B:

    passPercentage = 40
    grading rules = School B rules
    exam weights = School B weights

The SAME engine calculates both.

Do NOT hardcode these example values.

Do NOT change the actual values currently configured in the database/application.
