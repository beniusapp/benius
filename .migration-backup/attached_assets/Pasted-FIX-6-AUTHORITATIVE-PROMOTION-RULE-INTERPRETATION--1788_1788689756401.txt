====================================================
TENANT ISOLATION — NON-NEGOTIABLE
====================================================

This is a 1,000+ tenant SaaS application.

Promotion policy MUST be tenant-owned.

The authoritative flow must be:

Authenticated user
        ↓
Authenticated user's school/tenant
        ↓
Validated Academic Session belonging to that tenant
        ↓
Validated student belonging to that tenant
        ↓
Promotion policy belonging to that tenant
        ↓
Tenant + session scoped examination/result data
        ↓
Promotion evaluation

A client-supplied schoolId MUST NOT select the promotion policy.

For example:

Authenticated user = School A

Client attempts to request:

schoolId = School B

The server MUST continue using School A as the tenant authority.

It must NEVER load School B's promotion policy.

It must NEVER evaluate School A students using School B policy.

It must NEVER combine School A result data with School B policy.

It must NEVER expose whether another school's promotion policy/data exists.

If a supplied promotion policy belongs to another tenant:
- reject it, or
- treat it as invalid configuration,

according to the existing secure architecture.

NEVER fall back to:
- universal policy
- default policy belonging to another tenant
- first available policy
- another school's policy
- client-selected policy.
