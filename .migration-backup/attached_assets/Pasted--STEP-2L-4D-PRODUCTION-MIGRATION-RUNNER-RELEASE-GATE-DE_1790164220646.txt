# STEP 2L-4D — PRODUCTION MIGRATION RUNNER & RELEASE-GATE DESIGN/IMPLEMENTATION

## CONTEXT

This application is currently in the **BUILDING / DEVELOPMENT phase**.

Do NOT perform any production migration, production database write, production deployment, or production schema change as part of this task.

This task is only to inspect, design, implement, and test the migration/release mechanism in the repository and isolated development/test environments so that a later, separately authorized production migration can be performed safely.

This work follows:

* Step 2L-1 — server-authoritative Academic Session for Attendance writes — ACCEPTED
* Step 2L-2 — Academic Session date boundaries — ACCEPTED
* Step 2L-3 — marked Sunday Attendance display/count — ACCEPTED
* Step 2L-4B — historical Attendance survives physical Student deletion — ACCEPTED FOR DEVELOPMENT WITH PRODUCTION ROLLOUT CONDITION
* Step 2L-4C — Production Migration & Rollout Readiness Audit — NOT SAFE TO ROLLOUT

The 2L-4C audit established that the current production release process cannot guarantee the required migration ordering before incompatible application code serves traffic.

The known required schema chain is currently:

**012 → 014 → 015 → compatible application code**

Important: inspect the actual contents and prerequisites of migration 012 before implementing the runner. Do NOT blindly assume that migration 012 contains only the Attendance prerequisite. If 012 contains additional schema changes, document exactly what it does and verify its compatibility with the current production baseline before including it in the ordered manifest.

---

# PRIMARY OBJECTIVE

Build a controlled, explicit migration runner and release gate that can later execute the required migration chain in a deterministic order:

**012 → 014 → 015**

The mechanism must NOT depend on:

* `drizzle-kit push`
* `drizzle-kit push --force`
* an empty/incomplete Drizzle migration journal
* implicit startup schema synchronization
* application startup automatically running production migrations
* migration filename ordering alone
* undocumented manual assumptions

The future production process must have an explicit migration history, ordering, locking, validation, failure behavior, and application compatibility gate.

For this task, implement and test that mechanism only in DEVELOPMENT/TEST environments.

# PHASE D — MIGRATION BOOKKEEPING

Implement a dedicated migration bookkeeping mechanism.

Do NOT rely on the existing empty/incomplete Drizzle migration journal for production rollout ordering.

Create a dedicated migration history table, using an appropriately project-specific name.

It should retain enough information to determine:

* migration version
* migration filename
* checksum
* applied timestamp
* execution status if needed
* runner/version metadata if useful

Use a timezone-aware timestamp where appropriate.

The migration history must allow the runner to detect:

### Case 1 — Migration never applied

Execute it if all prerequisites are satisfied.

### Case 2 — Migration already applied with identical checksum

Treat it as already applied and continue safely.

### Case 3 — Migration already applied with different checksum

FAIL CLOSED.

Do not silently execute the modified migration.

Do not overwrite the historical checksum.

### Case 4 — Later migration recorded as applied while an earlier required migration is missing

FAIL CLOSED.

Example:

015 recorded as applied but 014 is absent.

Do not attempt to guess or repair automatically.

### Case 5 — Migration partially failed

The runner must leave the database in a state that can be safely diagnosed and retried according to the migration's transaction behavior.

Do not mark a migration successful unless the complete migration transaction succeeds.

---

# PHASE E — MIGRATION SERIALIZATION / LOCKING

Implement database-level serialization so that two migration runners cannot execute the same migration chain concurrently.

Use an appropriate PostgreSQL advisory lock or equivalent database-level mechanism.

Requirements:

* lock acquisition occurs before migration execution
* lock is held for the complete migration-runner operation
* second concurrent runner must wait or fail deterministically
* only one runner may modify migration bookkeeping at a time
* lock is released reliably on success
* lock is released reliably on failure
* connection errors must not leave a permanent logical lock

Prefer a database-native advisory lock over an application-memory lock.

Do NOT implement this using a JavaScript boolean/global variable because that does not protect multiple application processes or machines.

# PHASE I — TRANSACTION BEHAVIOR

Use transactions appropriately.

Each numbered migration should execute atomically if the SQL supports transactional execution.

Do not claim that 012 + 014 + 015 are one single transaction unless the actual implementation can guarantee that.

The preferred model is:

* acquire migration lock
* validate environment
* validate migration history
* execute migration 012 in its own transaction
* verify 012 postconditions
* record 012 success
* execute migration 014 in its own transaction
* verify 014 postconditions
* record 014 success
* execute migration 015 in its own transaction
* verify 015 postconditions
* record 015 success
* release lock

If a migration fails:

* do not record it as successful
* stop immediately
* do not continue to later migrations
* report exactly which migration failed
* preserve the database for diagnosis/retry

Do not automatically roll back already-successful predecessor migrations unless there is a technically safe and explicitly implemented rollback mechanism. Do not invent down migrations.
