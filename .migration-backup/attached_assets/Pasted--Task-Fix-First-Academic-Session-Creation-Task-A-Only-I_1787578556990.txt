### Task: Fix First Academic Session Creation — Task A Only

**IMPORTANT: DO NOT MODIFY ANY CODE YET.**
First inspect the existing implementation and confirm the current behavior described below. Only after confirming it, implement this **single scoped fix**.

### Current problem

For a brand-new school:

* The school has **zero academic sessions**.
* Principal creates the first session, e.g. **2026–2027**.
* The current UI sends `status: "draft"` and `setAsActive: false`.
* The session is therefore created as inactive/draft.
* The Admin Portal treats every inactive session as Archive/read-only.
* This can leave the administrator stuck because the normal Activate action is unavailable.

This is incorrect for a school's **first-ever academic session**.

### Required behavior

If the school currently has **ZERO academic sessions**:

1. Admin creates the first academic session, e.g. `2026–2027`.
2. That session must automatically be created as:

   * `isActive = true`
   * `status = "active"`
3. The Admin Portal must immediately recognize it as the **current active academic session**.
4. The top session indicator should show:
   **2026–2027 (Active)**
5. The admin must NOT see the newly created first session as:

   * Draft
   * Archived
   * Read-only
6. The admin must be able to immediately use the normal Admin Portal with that session active.

### Important distinction

This rule applies **ONLY when the school has no previous academic session**.

For schools that already have one or more sessions:

* Do NOT change the existing multi-session creation behavior.
* Do NOT change existing archive/active switching rules.
* Do NOT automatically alter historical sessions.
* Do NOT change session-copy behavior.
* Do NOT change financial/session isolation logic.

Do not simply change the global default from draft/inactive to active, because that could alter existing-school behavior.
