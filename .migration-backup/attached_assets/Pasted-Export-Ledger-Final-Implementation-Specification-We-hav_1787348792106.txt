Export Ledger — Final Implementation Specification

We have completed a full technical audit of the current Export Ledger implementation.

The existing filter system is already correct and must be preserved.

Now bring Export Ledger to the same production-quality architecture and behavior as the already-completed Ledger PDF and Transaction Report PDF.

1. Primary Goal

The Export Ledger CSV must behave consistently with the Ledger UI, Ledger PDF, and Transaction Report PDF.

It must:

- Respect the exact current Ledger filters.
- Respect explicit invoice/record selection.
- Respect "Select All Matching".
- Respect exclusions from "Select All Matching".
- Export all matching records when nothing is selected.
- Never export records outside the current school.
- Never export records outside the current academic session.
- Include the important columns that currently exist in the Ledger/PDF but are missing from CSV.
- Preserve the existing CSV quality and formatting.
- Work correctly with both small and large filter sets.
- Avoid duplicating filter/query logic unnecessarily.

Do not redesign the Ledger filtering system. It is already working correctly.

The existing Excel-style Ledger filtering is already implemented and verified.

Do NOT modify:

- "shared/ledger-filters.ts"
- Existing Ledger filter state

- Existing Transaction Report PDF GET/POST behavior

4. ADD SELECTION SUPPORT

This is the most important missing feature.

Export Ledger currently ignores Ledger selection state.

Bring it into parity with Ledger PDF and Transaction Report PDF.

It must support:

A. No selection

If the user has not selected anything:

Export Ledger
→ export ALL records matching the current filters/session

B. Individual selection

If the user selects specific invoices/records:

Select 3 records
→ Export Ledger
→ export ONLY those 3 selected records

Do not export the entire filtered dataset.

C. Select All Matching

If the user selects:

Select All Matching

then:

Export Ledger
→ export every record matching the current filters

D. Select All Matching + exclusions

If the user selects all matching and then excludes specific records:

Select All Matching
Excluded:
INV-0008
INV-0012

then:

Export Ledger
→ export every matching record EXCEPT the excluded records

E. Multiple-page selection

Selection must work correctly even when matching records span multiple pages.

Do not rely on the currently visible table page.

Selection must be based on the actual record/invoice IDs.

---

Use the already-established selection model:

The semantics must be identical to Ledger PDF POST and Transaction Report PDF POST.

The backend must correctly distinguish:

1. No selection

4. Select All Matching + exclusions

Use the exact existing project conventions/types where available rather than duplicating types.

12. SECURITY — DO NOT WEAKEN THIS

Tenant isolation is currently correct.

Preserve it exactly.

"schoolId" MUST continue to come from:

req.session.schoolId

Never trust:

schoolId

from query parameters or request body.

The query must remain school-scoped.

Student joins must remain school-scoped.

Payment record aggregation must remain school-scoped.

Academic session isolation must remain enforced by the existing server-side session context.

Do not allow:

selectedIds

to bypass school/session filtering.

A malicious user must not be able to select an ID belonging to another school and receive it in the export.

Selection is an additional restriction, never a replacement for tenant/session predicates.

Export Ledger is read-only.

Therefore the new:

must be treated like the existing read-only POST export routes.

It must NOT be blocked by the archived-session mutation guard merely because the HTTP method is POST.

Follow the same established pattern already used by:

- Ledger PDF POST
- Transaction Report PDF POST

Do not weaken any actual mutation protection.
