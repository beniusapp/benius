11. IDEMPOTENCY — VERY IMPORTANT

The Admin must not accidentally create two refunds because of:

- double click
- page refresh
- browser retry
- network timeout
- API timeout
- duplicate frontend request
- two browser windows
- two Admins attempting overlapping refunds

Implement server-side idempotency.

Persist the request before calling Razorpay.

If the same request is received again:

return the existing refund request/result rather than creating another refund.

Also enforce provider refund ID uniqueness.

12. CONCURRENCY PROTECTION

This is extremely important.

Example:

Payment = ₹10,000

Admin A tries to refund ₹7,000.

At the same time Admin B tries to refund ₹5,000.

The system must NOT allow both simply because both saw ₹10,000 refundable.

Use a transaction/row lock/advisory lock appropriate to the existing database architecture.

Calculate:

Captured amount
− Successfully processed refunds
− Reserved/in-flight refund amounts

Currently refundable amount

Then reserve the requested amount before calling Razorpay.

Do not allow total active refund reservations to exceed the refundable amount.

13. IMPORTANT NETWORK FAILURE CASE

Handle this scenario carefully:

Admin clicks Refund.

Your server sends request to Razorpay.

Razorpay accepts the refund.

Then the network connection fails before your server receives the response.

The UI must NOT simply say:

"Refund failed."

because the refund may actually have succeeded.

Instead:

- retain the local refund request
- mark it as pending/reconciliation-required
- do NOT create another refund automatically
- reconcile using Razorpay refund/payment information
- allow webhook processing to complete the lifecycle
- use provider refund ID when available
- maintain an immutable audit trail

This is critical to prevent duplicate refunds.
