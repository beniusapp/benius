# CORE BUSINESS RULE

All Attendance mutation paths must obey the same fundamental invariants.

For Attendance belonging to a normal Student Attendance record:

### School

The authenticated user's school/tenant is authoritative.

### Academic Session

The Attendance mutation must belong to the **currently active Academic Session for that school**.

A browser-provided Session ID/header must not be able to select another Session.

A server-stored object such as a leave request must NOT become an exception to this rule.

### Archived Session

Archived Session Attendance is **read-only**.

No Attendance mutation may modify or insert Attendance for an archived Session.

### Date

The existing Attendance correction rule remains:

> An active Session Teacher Attendance correction/marking may operate only within the existing **7-day correction window**, subject to the existing future-date, Session-boundary, and holiday rules.

Do NOT redefine the 7-day window.

Do NOT change the existing direct Teacher behavior.

Instead, ensure indirect Attendance mutation paths obey the same rules.

### School Holiday

Attendance must not be automatically created or modified on a school holiday.

Do NOT remove or weaken the existing direct Teacher holiday lock.

# PHASE C — ACTIVE ACADEMIC SESSION ENFORCEMENT

For Attendance mutations performed through leave approval:

The server must determine whether the target Session is currently active for the authenticated school.

A leave record's stored Session ID is **not sufficient authorization** to mutate Attendance.

Example:

* Leave was created while Session A was active.
* Session A later becomes archived.
* Leave is approved after Session A is archived.

The approval must NOT mutate Attendance for Session A.

Required behavior:

**Reject the Attendance mutation.**

Do not silently redirect it to the new active Session.

Do not rewrite the leave record to another Session.

Do not create the Attendance record in another Session.

Do not guess.

---

# PHASE D — ARCHIVED SESSION PROTECTION

Explicitly enforce:

> Attendance mutation for an archived Academic Session is forbidden.

This must be enforced server-side.

Do not depend on:

* `x-view-session-id`
* UI state
* archived-view headers
* client-side controls

A request must not become safe merely because a browser supplies or omits a view header.

The authoritative Session state must come from the server/database.

# PHASE H — CLASS/SECTION DATA INTEGRITY

The audit found two related but distinct data-integrity concerns.

## H1 — Leave-created Attendance

Fix this.

* existing Attendance context

Do not insert a partially populated Attendance record.

# H2 — DIRECT TEACHER MARKING

The audit also found:

> Direct Teacher Attendance accepts a client-supplied class/section that may be unrelated to the submitted Students.

This is a data-integrity problem.

Fix it WITHOUT changing the authorization model.

### DO NOT DO THIS:

Do not require Faculty Mapping.

Do not require Subject Mapping.

Do not restrict Teachers to specific classes.

Do not change the requirement:

> Any authenticated same-school Teacher may mark Attendance.

### Required fix

The submitted class/section must be validated against the submitted Students' authoritative Session enrollment/context.

The client cannot simply submit:

`class = Class A`

while submitting Students whose active Session enrollment is:

`Class B`

and cause Attendance to be stored under Class A.

Use the server-side authoritative Student/Session enrollment information.

If the submitted Students do not belong to the submitted class/section context:

**Reject the mutation.**

Do not silently rewrite the class/section to something else unless the existing application contract already explicitly does that.

Do not modify Student enrollment as a side effect.
