==================================================
3. INTENDED USER FLOW
==================================================

The final flow should be:

STEP 1
Principal selects:

Forgot password?

STEP 2
Principal enters:

Recovery Email
School Code

STEP 3
System validates the recovery request.

IMPORTANT:

The response must NOT reveal whether:

- the email exists
- the school code exists
- the email belongs to that school
- the account exists
- the account is active/inactive

Always return a generic response such as:

"If those details match, an OTP has been sent to your recovery email. Please check and try again."

This prevents account/tenant enumeration.

STEP 4
If the supplied details actually match an eligible account:

Generate a secure OTP.

Send the OTP to the configured recovery email.

STEP 5
Show OTP verification UI.

User enters OTP.

STEP 6
If OTP is valid:

Allow the user to set a new password.

STEP 7
Validate the new password according to the application's existing password policy.

STEP 8
Hash the new password using the application's existing secure password hashing mechanism.

Never store a plaintext password.

STEP 9
Invalidate the OTP/reset token immediately after successful password reset.

STEP 10
Invalidate any other active password-reset tokens for that account.

STEP 11
Redirect the user to Principal Login.

Do not automatically log the user in unless the existing authentication architecture explicitly requires that behavior.

==================================================
4. MULTI-TENANT REQUIREMENT — CRITICAL
==================================================

This application is a TRUE MULTI-TENANT SaaS platform.

School/tenant isolation must be preserved throughout password recovery.

The recovery identity must be resolved using the correct combination of:

- recovery email
- school code
- authenticated/registered school ownership

Do NOT perform a global email-only password reset.

A user from School A must never be able to reset:

- School B's principal account
- School B's teacher account
- School B's student account
- School B's admin account
- any other School B credential

School code must act as a tenant boundary.

Do not trust a client-provided schoolId as authorization.

Do not allow a user to submit a School A email and School B school code and receive information about either account.

==================================================
7. OTP SECURITY
==================================================

OTP must be cryptographically secure.

Do NOT use:

Math.random()

Do NOT generate predictable OTPs.

Use the project's existing secure random/crypto mechanism or Node's cryptographic random facilities.

Use an appropriate numeric OTP format consistent with the existing UI.

Recommended:

6-digit OTP

unless the existing application already defines another format.

==================================================
8. OTP STORAGE
==================================================

Inspect whether the application already has a password-reset/OTP storage mechanism.

If one exists:

Reuse it.

If one does NOT exist:

Implement the smallest appropriate persistence mechanism required by the existing architecture.

Do NOT store plaintext OTPs if avoidable.

Prefer storing a secure hash of the OTP.

Store enough metadata to enforce:

- account identity
- school/tenant identity
- OTP expiry
- used/consumed status
- creation time
- attempt count if supported
- purpose = password reset

Do not reuse an unrelated OTP mechanism unless its security and lifecycle are appropriate.

==================================================
9. OTP EXPIRATION
==================================================

OTP must expire after a short period.

Use an existing application policy if one already exists.

If no policy exists, use:

10 minutes

as the password-reset OTP lifetime.

Do not allow expired OTPs to reset passwords.

==================================================
10. OTP SINGLE USE
==================================================

An OTP must be single-use.

After successful verification/reset:

- mark it consumed OR
- invalidate/delete it according to the application's persistence architecture.

A previously used OTP must never work again.

==================================================
11. OTP ATTEMPT LIMIT
==================================================

Inspect whether an existing OTP attempt/rate-limit system exists.

If one exists, reuse it.

If not, implement a reasonable server-side attempt limit.

Do not allow unlimited OTP guessing.

Use a bounded number of verification attempts.

If the limit is reached, invalidate the OTP/reset challenge and require a new OTP.

Do not expose internal security details to the user.

==================================================
12. RATE LIMITING
==================================================

Password recovery is security-sensitive.

Inspect the existing authentication/rate-limiting infrastructure.

Apply the existing rate-limiting mechanism if available.

At minimum, protect:

- OTP request endpoint
- OTP verification endpoint
- password reset endpoint

Do not introduce a second incompatible rate-limiter if one already exists.

Avoid allowing unlimited OTP email requests.

==================================================
13. GENERIC RESPONSE / ENUMERATION PROTECTION
==================================================

This is mandatory.

For an invalid combination:

Recovery Email + School Code

do NOT respond with:

- "Email not found"
- "School not found"
- "Invalid school code"
- "No account exists"
- "Recovery email does not match"

Instead return the same generic recovery response used by the current UI.

The attacker must not be able to determine whether a principal account exists.
