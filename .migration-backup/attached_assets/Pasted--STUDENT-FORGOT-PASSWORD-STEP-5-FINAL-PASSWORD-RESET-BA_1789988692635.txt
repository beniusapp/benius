J. ATOMIC RESET
==================================================

The password reset must be atomic.

The following logical operations must have a safe concurrency boundary:

1. Validate the recovery challenge/reset authority.
2. Update the Student password hash.
3. Consume the reset authority.
4. Revoke/invalidate the Student's authenticated sessions as required.

Do NOT implement:

→
update password
→
later consume challenge

as unrelated independent operations that allow two concurrent requests to both reset the password.

Use the existing PostgreSQL transaction conventions.

If necessary, use row-level locking on the reset challenge / Student record.

==================================================
K. CONCURRENT RESET ATTACK
==================================================

This exact race MUST be tested:

Request A:
- valid password_reset session
- new password A

Request B:
- same valid password_reset authority
- new password B
- arrives concurrently

Required:

- exactly ONE reset succeeds
- exactly ONE password update occurs
- reset authority is consumed exactly once
- the losing request fails safely
- no partially completed reset
- no reset-token replay

The final password must correspond to the winning transaction only.

Do NOT assume sequential tests are sufficient.

Use real PostgreSQL-backed concurrency tests.
