Perform a **READ-ONLY ARCHITECTURE AUDIT** of the entire School MIS application.

## MAIN OBJECTIVE

Determine exactly which modules/data in the application are:

### A. GLOBAL / SESSION-INDEPENDENT

Meaning:

* Data belongs to the School/Tenant.
* Creating a new Academic Session does NOT recreate/reset it.
* Switching Academic Session does NOT change it.
* Deleting/archiving an Academic Session does NOT delete it.
* The data continues across Academic Sessions unless there is an explicit separate business rule.

Example concept:
Student Registry.

### B. ACADEMIC-SESSION-BASED

Meaning:

* Data belongs to a specific School/Tenant + Academic Session.
* A new Academic Session gets fresh/isolated operational data.
* Switching Session changes the data being viewed/used.
* Previous Session data remains attached to that previous Session.
* Previous Session data must not leak into the new Session.

### C. MIXED / UNCLEAR

Use this category when:

* part of a module is global and another part is Session-based, OR
* the current implementation is inconsistent, OR
* the business rule cannot be determined from the code.

DO NOT GUESS.

---

# MULTI-TENANT REQUIREMENT

For EVERY module/data category, also determine:

* Is it explicitly scoped to authenticated `schoolId` / tenant?
* Can one school's data be accessed from another school?
* Is tenant isolation enforced in reads?
* Is tenant isolation enforced in writes?
* Is the data global only WITHIN a school, rather than globally across all schools?

Important distinction:

"Global" means:

> GLOBAL ACROSS ACADEMIC SESSIONS WITHIN THE SAME SCHOOL.

It does NOT mean:

> shared between different schools.

Never recommend cross-school shared data.

# VERY IMPORTANT: LOOK FOR MIXED MODULES

Pay special attention to modules where:

* UI appears Session-based but database data is global.
* Database contains `academicSessionId` but some APIs ignore it.
* Some tables are Session-based while related metadata is global.
* New Session incorrectly reuses previous Session operational data.
* Old Session data is accidentally modified when the current Session is changed.
* Session switching changes something that should be global.
* Session deletion could delete something that should survive.
* Session creation incorrectly copies previous operational data.

Identify these clearly.
