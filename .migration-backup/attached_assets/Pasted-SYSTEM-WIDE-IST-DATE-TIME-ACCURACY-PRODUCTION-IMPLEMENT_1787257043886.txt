SYSTEM-WIDE IST DATE & TIME ACCURACY — PRODUCTION IMPLEMENTATION

You are working on a multi-tenant school ERP application deployed for Indian schools.

The attached/read-only IST Date & Time Audit has identified multiple areas where the application currently depends on UTC server time, PostgreSQL session time, browser-local timezone, or unsafe JavaScript "Date" parsing.

PRIMARY OBJECTIVE

Make the entire application deterministic and accurate for India Standard Time (IST / Asia/Kolkata) for all school-facing dates, times, business-day calculations, reports, receipts, dashboards, attendance, fees, payments, Razorpay events, notifications, and administrative history.

The same event must display the same date and time regardless of the administrator's, teacher's, student's, or browser/device timezone.

For this India deployment, the canonical presentation/business timezone is:

"Asia/Kolkata"

Do NOT solve this by changing the server OS timezone or PostgreSQL global timezone.

The application must explicitly handle timezone behavior.

---

VERY IMPORTANT SAFETY RULES

1. DO NOT blindly migrate historical timestamps

Do NOT:

- convert every existing timestamp by adding/subtracting 5:30;
- rewrite historical timestamps;
- change existing database values simply because they are "timestamp without time zone";
- assume every historical timestamp has identical provenance;
- run a mass "AT TIME ZONE" conversion;
- backfill historical timestamps without first proving their meaning.

Existing historical data must remain untouched until its provenance is understood.

If a database migration from "timestamp without time zone" to "timestamptz" is eventually recommended, prepare it as a separate migration proposal only after sampling and validating historical records.

---

2. DO NOT use browser timezone for school-facing timestamps

Any user-facing date/time must NOT depend on:

new Date().toLocaleString()
new Date().toLocaleDateString()
new Date().toLocaleTimeString()

unless an explicit:

timeZone: "Asia/Kolkata"

is supplied.

The application must behave identically when the browser timezone is:

- Asia/Kolkata
- America/New_York
- America/Los_Angeles
- Europe/London
- UTC
- any other timezone.

---

3. DATE-ONLY VALUES ARE NOT TIMESTAMPS

Fields representing calendar dates must remain calendar dates.

Examples:

- Date of Birth
- Attendance date
- Academic session start/end
- Homework due date
- Fee due date
- Fee period
- Leave start/end date
- Calendar date
- Holiday date
- Asset purchase date
- Warranty date
- Cheque date
- Offline deposit date
- Payment received business date

Do NOT convert these through:

new Date("YYYY-MM-DD")

and then format them.

That can cause calendar-day shifts.

For example:

2026-04-01

must always display as:

01 Apr 2026

regardless of browser timezone.

Use this everywhere the application needs the Indian school business date.
