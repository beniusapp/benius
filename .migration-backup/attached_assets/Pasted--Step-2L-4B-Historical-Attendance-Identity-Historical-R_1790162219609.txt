# NON-NEGOTIABLE PROJECT RULES

These rules remain permanent:

### 1. Multi-tenant / school isolation

This is a multi-school MIS.

Every school-scoped Attendance read, write, lookup, calculation, history query, summary, migration backfill, identity lookup, and authorization path must remain constrained to the authenticated/current school.

Never allow Attendance belonging to School A to appear in School B.

A matching UUID, numeric Student ID, digital ID, name, or other identity value must never be sufficient by itself to cross a school boundary.

### 2. Student Registry is GLOBAL / PERMANENT

Students are global Registry entities.

Do not recreate/reset the Student Registry per Academic Session.

Do not make Enrollment a prerequisite for historical Attendance preservation.

Physical Student deletion must remain possible.

* historical Attendance rows must remain;
* historical Attendance must retain its original Student identity;

* school and Academic Session must remain;

* the deleted Student must not reappear in the current/live marking roster.

Preserve that fundamental design.

### 4. Academic Session isolation

Attendance remains strongly Academic Session-specific.

Historical Attendance must remain associated with its original Academic Session.

Never move Attendance between Sessions.

Never allow a historical Attendance row from Session A to appear in Session B.

### 5. Sunday behavior

If Attendance was deliberately marked on Sunday, it is a valid Attendance record and must behave exactly like the corresponding stored weekday status.

Do not introduce Sunday-specific Attendance business rules.

### 6. Existing Teacher authorization

Any authenticated same-school Teacher may mark Attendance.

Do not introduce Faculty Mapping/class/subject restrictions into Attendance unless an existing security check already requires them.

### 7. Active Session correction rules

Preserve the existing Attendance correction behavior:

* Step 2L-1 server-authoritative active Session behavior remains intact;

Do not weaken or replace these controls.

### 8. Application timezone

All application/business/display date and timestamp logic must use:

**IST / Asia/Kolkata**

Do not introduce BST, UTC-derived business dates, browser-local date calculations, or another local timezone for Attendance business logic.

### 9. Minimal-change principle

Make the smallest safe changes necessary.

Do not refactor unrelated Attendance code.

Do not rename unrelated APIs.

Do not redesign Student Registry.

Do not redesign Academic Sessions.

Do not redesign Teacher Attendance.

# STEP 2 — FIX STUDENT ATTENDANCE IDENTITY KEY ENFORCEMENT

## Objective

`students.attendance_identity_key` must become a protected identity for the Student's Attendance history.

It must not be possible for an application/database write to intentionally or accidentally make Student B inherit Student A's Attendance identity key.

### Required properties

For every Student:

* `attendance_identity_key` is present;
* it is generated automatically for new Students;
* it is unique among Students;
* it is immutable after Student creation;
* it remains associated with that Student for the lifetime of that Student Registry row;
* deleting the Student does not transfer the key to another Student;
* a newly created replacement Student receives a new key.

### Database enforcement

Prefer database-level enforcement rather than relying only on application code.

Implement the smallest safe database mechanism available in the current PostgreSQL design.

At minimum:

1. Add/enforce a UNIQUE constraint or unique index on:

`students(attendance_identity_key)`

2. Ensure the column remains NOT NULL.

3. Prevent changing an existing non-null `attendance_identity_key`.

Use a narrowly scoped PostgreSQL trigger or equivalent database constraint mechanism if necessary.

The immutability rule should allow the initial value to be generated/set during INSERT but reject attempts to change it afterward.

Do not implement a mechanism that prevents ordinary Student updates unrelated to the identity key.

For example, changing:

* name,
* class,
* section,
* contact information,
* status,

must remain possible if those changes are otherwise permitted.

Only changing `attendance_identity_key` should be blocked.

### Important

Do not use probabilistic uniqueness as the acceptance criterion.

`gen_random_uuid()` being extremely unlikely to collide is not sufficient.

The database must enforce uniqueness.

# STEP 3 — PROTECT ATTENDANCE HISTORICAL IDENTITY FROM LIVE STUDENT REASSIGNMENT

The Step 2L-4A audit identified another risk:

The Attendance snapshot identity is immutable, but `attendance_records.student_id` may still be mutable.

Audit the current Attendance INSERT/UPDATE triggers and application upsert path.

The desired invariant is:

### For an existing Attendance row

The historical identity must never silently become associated with a different Student.

Do not permit this sequence:

Student A creates Attendance

→ Attendance stores A's historical identity

→ existing Attendance row is updated so `student_id = Student B`

→ snapshots still identify Student A

That creates a contradictory Attendance row.

Implement the smallest safe protection.

Preferred behavior:

* On INSERT, existing validation remains.
* On UPDATE of an existing Attendance row, if `student_id` is being changed:

  * either reject the reassignment;
  * or only allow it when the new Student's `attendance_identity_key` exactly matches the immutable historical `identity_key`, which in normal operation means no actual Student change is possible.

Prefer **rejecting reassignment** unless there is a demonstrated existing application workflow that legitimately requires it.

Do not break ordinary Attendance status updates.

For example, changing:

* Present → Absent,
* Absent → Present,
* Late,
* Half Day,
* Leave,

must continue to work according to the existing Attendance rules.

Only changing the Student association on an existing Attendance row should be protected.

Also preserve:

* school isolation;
* Session isolation;
* date uniqueness;
* existing correction window;
* archived-session protection.

# STEP 4 — FIX ADMIN / TEACHER HISTORICAL DAILY SUMMARY

This is a blocking issue.

Current behavior identified by Step 2L-4A:

`getDailyAttendanceSummary()` uses the live Student roster and matches Attendance by nullable `student_id`.

After physical deletion:

`attendance_records.student_id = NULL`

Therefore the Attendance row survives but can disappear from the daily summary.

That is not acceptable.

## Required behavior

For a historical date/session:

If Attendance exists for a physically deleted Student, the summary must still include that Student's historical Attendance using the saved snapshot identity.

The summary must not require the Student to still exist in the live `students` table.

### However

Do NOT simply replace the live roster with all historical Attendance rows.

The system must preserve the distinction between:

1. Current/live Students eligible for Attendance marking.
2. Historical Students whose old Attendance must remain visible.

### Required model

For historical reporting:

* start with the appropriate school + Academic Session + date scope;
* include applicable live Students;
* include applicable preserved Attendance snapshot entries even when `student_id IS NULL`;
* match existing Students safely;
* avoid duplicates when a live Student already corresponds to an Attendance row;
* use historical snapshot identity as the fallback for deleted Students.

The deleted Student must appear only because a historical Attendance record exists.

A physically deleted Student must **not** be recreated in the live roster.

### Identity matching

Do not match historical Attendance using only:

* numeric Student ID;
* digital ID;
* name.

Use the immutable Attendance `identity_key` as the canonical historical identity.

For live Students, their `attendance_identity_key` can be used to match the Attendance record.

School and Academic Session must remain mandatory query scopes.

### Preserve existing status semantics

The summary must preserve the existing status values and calculations:

* Present
* Absent
* Late
* Half Day
* Leave

Do not introduce different weighting or Sunday behavior.

### Check all callers

After fixing `getDailyAttendanceSummary`, inspect every caller.

Determine whether the caller expects:

* live roster only;
* historical report roster;
* daily summary;
* marking roster.

Do not globally change live marking behavior.

The current/live marking roster must continue to use live Students.

Deleted Students must never return to the marking UI simply because historical Attendance exists.
