The blocker is a genuine concurrency/security gap in Step 3:

Affected file:

server/student-password-recovery-session.ts

Affected helpers:

- startStudentPasswordRecoverySession
- clearStudentPasswordRecoverySession

Current problem:

1. startStudentPasswordRecoverySession refuses to replace an active recovery identity.
2. clearStudentPasswordRecoverySession clears recovery state unconditionally.
3. There is no conditional compare-and-clear operation bound to:
   - challengeId
   - studentId
   - schoolId

This creates an unsafe race:

Request A:
  challenge A created
  session A started
  delivery A delayed

Request B:
  challenge B created
  challenge A invalidated
  session B needs to replace session A

Later:
  delivery A fails

If A blindly clears recovery state, it can destroy B's newer recovery state.

DO NOT work around this in Step 4.

Fix ONLY the Step 3 session foundation.
