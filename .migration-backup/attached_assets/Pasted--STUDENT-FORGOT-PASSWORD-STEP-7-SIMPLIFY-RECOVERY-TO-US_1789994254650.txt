==================================================

Removing the separate recovery-contact layer does NOT mean removing security.

Keep all of the following:

1. School Code resolves the tenant.
2. DSID is searched only within that resolved school.
3. Browser never supplies schoolId as authority.
4. Browser never supplies studentId as authority.
5. Student must be active.
6. Student must be activated.
7. Student must have a valid non-empty email.
8. Student email must be read from the authoritative Student row.
9. Student/school identity must be revalidated inside the locked transaction.
10. Student email must be revalidated inside the locked transaction.
11. OTP remains cryptographically generated.
12. OTP is stored only as an HMAC/hash.
13. OTP remains time-limited.
14. OTP attempt limit remains.
15. OTP verification remains atomic/concurrency-safe.
16. Reset token remains server-bound.
17. Reset token remains hashed in the database.
18. Recovery session remains server-bound.
19. Password reset remains atomic.
20. Successful reset revokes existing Student sessions.
21. Email-change invalidation remains atomic.
22. School-specific notification configuration remains mandatory.
23. No global/Admin/Teacher/other-school email fallback.
24. Anti-enumeration remains intact.
25. Delivery failure cleanup remains intact.

Do NOT weaken any of these protections.

==================================================
F. FORGOT PASSWORD ROUTE
==================================================

Update:

server/student-password-recovery-routes.ts

In:

registerStudentPasswordRecoveryRoutes

Change the forgot-password flow.

Current obsolete behavior:

1. Resolve school.
2. Resolve Student.
3. Check active/activated.
4. Require verified recovery contact.
5. Compare recovery contact to Student email.
6. Create contact-bound challenge.
7. Send email.

New behavior:

1. Resolve school from School Code.
2. Resolve Student by DSID within that school.
3. Require Student active.
4. Require Student activated.
5. Read Student's authoritative `students.email`.
6. Validate that email is present and syntactically valid.
7. Create password-reset challenge bound directly to:
   - schoolId
   - studentId
8. Generate OTP.
9. Send OTP to `student.email`.
10. Maintain existing generic anti-enumeration response.

Remove:

- getVerifiedRecoveryContact dependency
- recovery-contact lookup
- recovery-contact/current-email comparison
- contactId challenge dependency

Do NOT change:

- School Code normalization
- tenant isolation
- DSID lookup rules
- anti-enumeration
- challenge replacement behavior
- delivery failure cleanup
- server-bound recovery session
- notification configuration lookup
