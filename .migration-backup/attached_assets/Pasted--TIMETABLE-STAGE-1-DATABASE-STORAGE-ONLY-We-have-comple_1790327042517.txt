## TIMETABLE — STAGE 1

## DATABASE + STORAGE ONLY

We have completed the final read-only audit.

The final architecture is:

> **The entire Timetable must be 100% Academic Session-based.**

This stage must implement ONLY the **Database + Storage layer**.

Do NOT modify Admin, Teacher, or Student UI yet.

---

# 1. DATABASE — `timetable_entries`

Change `timetable_entries` so Academic Session is mandatory.

### Required

`session_id` must become:

* NOT NULL
* FK → `academic_sessions(id)`
* no `ON DELETE SET NULL`

A timetable entry must always belong to one Academic Session.

### Unique constraint

Current:

```text
school_id + class + section + day_of_week + period
```

Replace it with:

```text
school_id
+ session_id
+ class
+ section
+ day_of_week
+ period
```

This is important because:

```text
2025–26 + Class 5A + Monday + Period 1
```

and

```text
2026–27 + Class 5A + Monday + Period 1
```

must both be allowed.

---

# 2. DATABASE — `timetable_structure`

Add:

```text
session_id
```

It must be:

* NOT NULL
* FK → `academic_sessions(id)`
* no `ON DELETE SET NULL`

The structure is now Session-owned.

This includes:

* periods
* bell timings
* labels
* breaks
* ordering

### Structure identity

Ensure the database can store the same:

```text
School + Class + Period
```

in different Academic Sessions.

The exact unique constraint must include `session_id`.

For example:

```text
school_id
+ session_id
+ class
+ period_number
```

If the existing break representation requires a different safe uniqueness design, inspect the current data model and choose the smallest correct constraint. Do not invent unnecessary schema.

---

# 3. SCHOOL + SESSION OWNERSHIP

A timetable must never connect:

```text
School A
+
School B's Academic Session
```

Therefore, inspect the existing database relationships and add the smallest practical database-level protection available in this project.

The final invariant must be:

```text
timetable.school_id
=
academic_session.school_id
```

Do not weaken multi-tenant isolation.

If the current schema cannot enforce this through a simple foreign key/constraint without a large redesign, document that limitation and enforce it at the Storage layer instead.

# 5. STORAGE LAYER

Update all timetable storage methods so Session ID is **required**, not optional.

Audit every timetable storage function.

Any method currently accepting:

```text
schoolId
```

must be reviewed and changed to require:

```text
schoolId + sessionId
```

where the operation is session-specific.

This includes at minimum:

* timetable entry reads
* timetable entry creation
* timetable entry update
* timetable entry deletion
* batch save
* batch delete
* class timetable
* teacher timetable
* student timetable
* slot lookup
* collision checking
* publish/status
* structure reads
* structure save/replacement

Do NOT change API/UI in this stage.

Only make the Storage contract correct.

---

# 6. NO OPTIONAL SESSION FILTER

Remove the old pattern where:

```text
sessionId = null
```

means:

> return all Sessions.

That behavior must no longer exist for Timetable.

Timetable storage operations must require an explicit Session.

If Session is missing:

```text
REJECT
```

Do not silently return school-wide timetable data.

---

# 7. SESSION OWNERSHIP VALIDATION

At the Storage boundary, verify:

```text
sessionId belongs to schoolId
```

If not:

```text
REJECT
```

Do not allow a caller to use another school's Academic Session.

Do not trust client-supplied school/session combinations.

---

# 8. ARCHIVED SESSION

For mutation methods, Storage must not allow writes to an archived/inactive Session.

At minimum apply this to:

* create
* update
* delete
* batch save
* batch delete
* structure save/replacement
* publish/status mutation

Use the project's existing Academic Session active/writable convention.

Do not create a second competing Session-state system.
