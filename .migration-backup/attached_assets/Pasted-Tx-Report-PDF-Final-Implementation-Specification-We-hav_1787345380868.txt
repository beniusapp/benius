Do NOT modify or redesign the working Ledger filtering implementation.

Now implement/fix the Tx Report PDF so that it becomes fully consistent with the current Ledger filtering architecture and the actual payment/transaction data.

Before changing any code, inspect the existing implementation carefully.

2. CORE REQUIREMENT

The Tx Report PDF must represent the same filtered invoice population selected by the Ledger.

For example:

If the user filters:

- Class = 6
- Fee Name = Math Book
- Frequency = One-Time

then:

Ledger table → same invoice population

Ledger PDF → same invoice population

Tx Report PDF → transactions belonging to that exact invoice population

Export Ledger → same invoice population

There must never be a situation where the Ledger shows one set of invoices while Tx Report PDF contains unrelated invoices.

5. FILTER COMBINATION LOGIC

Preserve the existing verified filter semantics.

Within the same column:

OR

Example:

Frequency:

- One-Time
- Monthly

means:

"Frequency = One-Time OR Frequency = Monthly"

Across different columns:

AND

Example:

Class = 6

AND

Fee Name = Math Book

AND

Frequency = One-Time

means the invoice must satisfy all three conditions.

Do not alter the already-tested filter behavior.

---

6. TRANSACTION-SPECIFIC BEHAVIOR

This is the most important difference between Ledger PDF and Tx Report PDF.

The Ledger is invoice-oriented.

The Tx Report PDF is transaction/payment-oriented.

Therefore:

One invoice with multiple payments

If one invoice has:

- Payment 1
- Payment 2
- Payment 3

the Tx Report must show all applicable payment transactions individually.

Do NOT collapse multiple payments into one transaction row.

Example:

Invoice INV-0001

Payment 1 = ₹2,000 — Online

Payment 2 = ₹500 — Cash

The Tx Report must contain two transaction rows.

---

7. IMPORTANT SESSION FIX

A transaction must not be incorrectly excluded merely because the individual payment record contains a different/stamped session value.

The authoritative relationship for determining whether a transaction belongs to the report should be:

Transaction → Payment Record → Invoice/Fee Record → Invoice's Academic Session

The invoice's session must be used to determine report scope.

Do NOT accidentally require every payment row's own session field to independently match the selected academic session if that would exclude a legitimate payment belonging to an invoice in that session.

This specifically addresses the architectural issue previously identified during review.

---

8. TENANT / SCHOOL SECURITY

Tenant isolation is mandatory.

The Tx Report PDF must always enforce:

- authenticated "school_id"
- authenticated/validated academic session
- existing server-side tenant security

Never trust:

- school ID from the browser
- arbitrary invoice IDs
- arbitrary transaction IDs
- arbitrary session IDs supplied by the client

A user from School A must never be able to retrieve transactions belonging to School B.

---

9. SELECTED INVOICES

If the Ledger supports selection-aware export, preserve the existing selection semantics.

Individual selection

If the user selects:

Invoice A
Invoice B
Invoice C

then Tx Report PDF must contain transactions only for those selected invoices.

Select All Matching

If:

"selectAllMatching = true"

then Tx Report PDF should contain transactions belonging to all invoices matching the current filters.

Exclusions

If:

"selectAllMatching = true"

and some invoices are excluded, those excluded invoices must not contribute transactions to the Tx Report PDF.

Critical rule

Selection must be applied to the invoice population first.

Then retrieve transactions belonging to that invoice population.

Do not independently select arbitrary payment records.

---

10. NO PAGINATION BUG

The PDF export must not depend on the current browser page.

If the Ledger currently displays page 2 of 5, the Tx Report PDF must still export the complete filtered result.

Do NOT send:

- current page
- page size
- visible rows only

unless the existing architecture explicitly requires it for something unrelated to export.

The SQL used for PDF generation must not accidentally contain the table's UI pagination "LIMIT/OFFSET".

12. PAYMENT STATUS

The report must distinguish transaction states correctly.

Do not treat every payment record as simply "Paid".

Inspect the existing payment model and correctly represent applicable states such as:

- Captured
- Authorized
- Failed
- Refunded
- Partially refunded
- Cancelled
- Pending

Use the application's actual status values and mapping.

Do not invent new payment statuses.

---

13. FAILED PAYMENTS

Failed transactions are important audit information.

If a failed payment transaction exists for an invoice, it should not disappear merely because the invoice itself is currently unpaid.

Where available, show:

- transaction/payment ID
- amount
- method
- date/time
- status
- failure reason

Do not overwrite failed attempts with successful attempts.

Every genuine payment attempt should remain independently represented according to the existing transaction data model.

---

14. MULTIPLE PAYMENT METHODS

If an invoice has multiple payment transactions, show each transaction separately.

Example:

Invoice INV-0008

Payment| Amount| Method
Payment 1| ₹2,000| Online
Payment 2| ₹1,000| Cash

The Tx Report must show both rows.

Do not aggregate these into:

"Multiple"

That "Multiple" behavior belongs to the invoice-oriented Ledger where appropriate.

The transaction report should preserve transaction-level detail.

---

15. PAYMENT IDs / REFERENCE NUMBERS

Long identifiers must NEVER overlap into another column.

Examples:

- Razorpay payment IDs
- Order IDs
- Reference numbers
- UTR/reference values
- authorization codes

Use the same reliable PDF wrapping strategy already established for Ledger PDF:

- calculate actual text width using the PDF renderer's font metrics
- wrap at word boundaries wherever possible
- use character-level breaking only when a token itself is too long to fit
- increase row height dynamically
- never clip text
- never allow text from one cell to visually enter another cell

A long ID may become:

"pay_TS9NVI"

"ayHcXKJ"

if necessary.

That is acceptable.

What is NOT acceptable:

- clipping
- overlapping another column
- writing outside the table
- disappearing text

19. TOTALS

The Tx Report should have a professional totals section at the end.

Do NOT blindly reuse Ledger totals because Tx Report is transaction-oriented.

First determine what totals are meaningful based on the actual transaction states.

At minimum, where supported by the data:

- Total Transaction Amount
- Total Successful/Captured Amount
- Total Failed Amount

If refunds are present and meaningful:

- Total Refunded Amount

The totals must not double-count transactions.

Most importantly:

Do not sum the same invoice amount multiple times merely because an invoice has multiple payment records.

Transaction totals and invoice totals are different concepts.

Calculate them according to the report's actual meaning.
